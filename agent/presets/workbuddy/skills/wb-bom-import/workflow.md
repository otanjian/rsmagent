# BOM 导入 · 基线核对

## 用途

把一份新到的 BOM 与现行基线核对，产出四份东西：

1. **来源一致性报告** —— 同一版本的多个来源（Excel / PDF / 邮件）之间是否自相矛盾
2. **脏数据体检报告** —— 疑似重复料、单位混用、空值、层级孤儿件、版本缺失
3. **差异清单** —— 按类型分组，每条附旧值、新值、判断依据
4. **变更影响与待澄清清单** —— 每条改动牵动的工单/在途/库存金额，以及明确拿不准的项

## 定位（重要）

**这个 Skill 的目标不是"把 BOM 自动导进ERP"，而是"把 BOM 里的雷找出来，并算清每颗雷值多少钱"。**

原因：AI 解析图纸与表格的准确率上限在九成上下，追求全自动写入等于把错误也一起自动化。
而**比对场景对准确率的容忍度高得多** —— 差异摆在眼前，人一看就知道对不对。

因此：
- 绝不因为"看起来更合理"就替用户选一个值
- 拿不准的一律单列，不混进确定性差异
- 每条判断都写出依据，供人推翻并留痕

## 输入

**不要求任何格式**，因为现实就是"对方想怎么发就怎么发"。

| 形态 | 处理方式 |
|---|---|
| Excel / CSV | 直接读表；编码自动识别 |
| PDF（表格型） | 提取表格结构 |
| PDF（扫描件）/ 图片 / 截图 | 视觉识别提取表格 |
| 邮件正文（文本/ HTML） | 提取表格 + **正文段落一并读入，作为判断依据** |
| Word | 表格 + 正文段落 |

**列名容错**：料号 / 物料号 / 物料编码 / 件号 / Part No / P/N 均识别为料号；用量 / 数量 / Qty 同理。

## 执行流程

### Step 1 · 识别角色并解析

自动判断哪份是基线、哪份是新版，依据优先级：文件内的版本字段 → 文件名关键词（基线/新版/送审）→ 导出或发送时间。

把每一份来源独立解析成统一结构：`料号 + 名称 + 用量 + 单位 + 版本 + 替代料 + 供应商 + 备注`。

### Step 2 · 来源交叉核对（同一版本有多个来源时必做）

**这一步不能跳过。**当同一个版本同时给了 Excel 和 PDF（或截图）时，先把这些来源互相对一遍。

发现不一致时：**标为阻塞项，不得自行选值**。理由——研发自己发出的两份文件都对不上，只能由研发确认。

重点核对字段：用量、单位、版本号、替代料、供应商。

> 单位类冲突要特别标出。单位错误的特点是**不会报错，会安静地一路生效**到采购下单和发料。行业里有过"一个零件单位由个写成箱，几十万物料闲置半年"的教训。

### Step 3 · 脏数据体检（比对前先扫一遍）

不需要判得多准，**只需把可疑项捞出来给人看** —— 人一眼就能确认，而命中一条就省一次损失。

| 检查项 | 判定线索 |
|---|---|
| **疑似重复料** | 描述高度相似但料号不同（如相差一个 0、多一个后缀）；同供应商同规格 |
| 单位可疑 | 同一料号在不同来源/基线中单位不一致；同类物料单位不统一 |
| 用量异常 | 空值、0、非数值、数量级明显偏离同类件 |
| 层级孤儿件 | 有父项引用但自身不存在，或反之 |
| 替代料未标 | 关键件无替代料且基线中原本有 |
| 版本号缺失 | 新增件无版本号（影响后续追溯） |

> 疑似重复料是这一步最有价值的产出。行业里"一物多码"极普遍，后果很具体：多个编码多个库存账，系统显示无货去紧急采购，回头盘点发现仓库还压着一批。

### Step 4 · 差异分类

按**行业通行的五类**分组，不要笼统地"标出不同之处"：

| 类型 | 判定 |
|---|---|
| **新增** |仅在新版存在 |
| **删除** | 仅在基线存在 |
| **替换** | 一增一减且功能对应（描述相近、或备注/邮件中说明了替代关系） |
| **用量变化** | 料号一致，用量或单位变化 |
| **信息修订** | 料号与用量一致，版本/供应商/替代料/备注等字段变化 |

**每条差异必须写出判断依据**（如"基线中查无此料号"、"新版中不存在且邮件已说明废弃"）。

**料号匹配按置信度分三档**：
- 高：料号完全一致，或一增一减且邮件明确说明替代关系 → 直接归类
- 中：描述相似度高但料号不同 → 归类同时标注待确认
- 低：无法可靠对应 → **列入待澄清，不猜**

### Step 5 · 变更影响面展开

对每一条差异，展开它牵动的东西——**这是唯一能让管理者也听懂的一层**：

| 维度 | 要查什么 |
|---|---|
| 未完工工单 | 有几张、共多少台在用这颗料 |
| 已下采购 / 在途 | 已下单数量、在途数量、能否退改 |
| 旧料库存 | 剩余数量 ×单价 = **金额敞口** |
| 配套件 | 是否有需要同步变更的关联件 |
| 要做的事 | 旧料怎么处理、什么时候切版本 |

> 变更评审真正要拍的板不是"同不同意改"，而是**旧料怎么处理、在途怎么办、何时切版本**。没有这张表，评审会就是各部门凭印象争。

### Step 6 · 待澄清与阻塞判定

**触发待澄清的典型情形**：

| 情形 | 为什么不能自行决定 |
|---|---|
| 替代料字段原有值被清空 | 可能是漏填，也可能是**有意留空在等对方接话**——性质完全相反 |
| 同版本多来源冲突 | 只能由出具方确认 |
| 关键件的备注或关键标记消失 | 可能涉及降级 |
| 供应商变更但无任何说明 | 可能涉及认证与质量口径 |
| 版本号跳跃（如 v1.2 → v1.4） | 中间版本可能有未同步的变更 |

**必须结合正文文字判断，不要只看表格字段。**邮件或备注里的一句"这颗料供货紧张，请评估"，
配合"替代料字段被清空"这个事实，含义就从"漏填"变成"对方在等你重新定义替代关系"。
按漏填处理会把一个已经不成立的替代关系带过审批，等采购下单才发现走不通。

**输出时把能推进的与卡住的分开**：
- 依据清楚的差异 → 可直接写入变更单送审
- 阻塞项 → 汇总成**一张问题清单一次问完**，不要发现一个问一次
- 体检发现的、与本次变更无关的问题（如重复料）→ 单列为"顺手要处理的"

## 输出结构

```markdown
## BOM 核对报告 · [产品] [基线版本] → [新版版本]

### 一、来源一致性
（同版本多来源的冲突项，或"三份来源一致"）

### 二、脏数据体检
（可疑项表：类型 / 命中项 / 为什么可疑 / 建议）

### 三、差异清单
（按新增 / 删除 / 替换 / 用量变化 / 信息修订分组，每条附依据与置信度）

### 四、变更影响
（每条差异牵动的工单 / 在途 / 旧料金额 / 要做的事）

### 五、结论
可先送审的：…
必须先澄清的：…（附给对方的问题清单）
顺手要处理的：…
```

## 常见问题

**怎么知道哪份是基线** —— 优先看文件内版本字段，其次文件名关键词，最后时间戳。都判断不了就直接问用户，不猜。

**截图很模糊怎么办** —— 能读的部分照读，读不准的字段标注"图像不清晰，需确认"，并主动请用户提供原始文件。**不要用猜测填补模糊字段。**

**能比三个版本以上吗** —— 两两比对。多版本演进分批做（v1.1 vs v1.2，再 v1.2 vs v1.3），最后汇总累计变化。

**基线本身就是脏的怎么办** —— 很常见。体检步骤同时扫基线，把基线自身的问题（如重复料）单列为"存量问题"，与本次变更区分开，不要混在差异清单里。

**用户要求"直接帮我导入 ERP"** —— 先出核对报告并说明阻塞项。存在阻塞项时不建议直接导入，理由要讲清楚（哪几项没定、影响多少钱）。
