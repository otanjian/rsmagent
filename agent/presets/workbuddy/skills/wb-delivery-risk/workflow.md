# 出货前交付风险评估 · 放行判定 Skill

> 品质工程师岗位场景 7.2 专用 · 从检验记录 + 订单交期 + 客户质量协议 + 返工产能 + 先例台账 → 硬拦截红线筛查 → AQL 档位复核 → 五档处置结论 → 待确认事项清单 + 可会签决策单

---

## 1. 用途

出货前查出批次异常，真正的难题不是"合格不合格"，而是**这批到底能不能放，不能放有没有别的路**。这个 Skill 一次做完六件事：

1. **五源材料对齐**：出货前检验记录 + 待出货订单与交期 + 客户质量协议摘录 + 返工能力与产能 + 历史让步先例台账，按「交货批号」和「客户」两个键拼成全景
2. **硬拦截红线筛查**（必须最先做）：安全/特殊特性超差、合同写明零缺陷、影响无法评估 —— 命中任一即禁止让步，不做裁量
3. **缺陷等级重判+ AQL 档位复核**：把检验员的口语化描述对齐到实测值与图纸要求，按 CR/MA/MI 重新归类，用对应 AQL 档位重算接收数 Ac，**识别出"被错判为不合格"的批次**
4. **五档处置判定**：放行 / 返工后复检 / 暂缓放行 / 让步接收 / 拒收隔离，每档带前置条件与关闭条件
5. **两边代价对称呈现**：放行的风险（客户投诉、索赔条款、评分降级）与不放行的代价（违约金、客户上线受影响）**必须同时给出**
6. **待确认事项清单 + 先例台账沉淀**：拿不到的判据明确列出问谁问什么，本次处置追加进台账

**这个 Skill 解决的真实痛点**：中小企业里这一批发不发，最终是老板或业务拍板，品质工程师的真实角色是把判断依据凑齐让能签字的人签。但决定让步能不能走的《客户质量协议》原件在销售手里（合同附件），品质部平时不持有；历史让步先例没有台账，经手人一离职就归零；返工来不来得及的数据只在班组长嘴里。于是判断只能靠"上次好像这么发过"。

## 2. 触发方式

### 2.1 用户一句话触发（推荐）

```
明天开始有三批货要发，OQC 都报了不合格，材料我放一起了。
帮我看下每一批到底能不能放 —— 能放的直接说能放，不能放的告诉我卡在哪、
有没有别的路走。客户质量协议那份是我刚从销售那儿要来的，
让步能不能走以协议为准，别只看技术上行不行。
拿不准的别硬写，列出来我去问。别替我做放行的决定。
```

### 2.2 输入材料清单

| # | 材料 | 必需 | 缺失时的降级策略 |
|---|---|---|---|
| 1 | 出货前检验记录（含抽样与判定标准） | **必需** | 无此项无法运行，需先取得实测值与图纸要求 |
| 2 | 待出货订单与交期 | **必需** | 无此项则无法算交期压力，只能出技术结论 |
| 3 | **客户质量协议摘录** | 强烈建议 | **缺失时一律不得输出"让步接收"结论**，改为「让步可行性待确认（需向销售索取协议附件）」 |
| 4 | 返工能力与产能 | 建议 | 缺失时"返工后复检"档需标注「返工可行性未经确认」 |
| 5 | 历史让步先例台账 | 可选 | 缺失时在输出中提示「本厂无先例台账，建议自本次起建立」 |

**关键原则：材料 3 缺失是常态**（品质部通常不持有客户协议）。此时 Skill 的第一个动作就是提示用户去销售部索取，并说明"没有这份文件，让步这条路无法判定"。

## 3. 六步法工作流程

### STEP 1 · 读齐材料并对齐口径

- 检验员的缺陷描述通常是口语化的（"有几条细的加工痕""偏了一点点""以前收过类似的"），**不能直接采信其判定结论**
- 必须做的对齐：缺陷描述 → 实测值 → 图纸要求 → 是否真的超差
- 输出一句判断前提说明：哪几项是主观表述、哪几项的缺陷等级判定可能有误

### STEP 2 · 硬拦截红线筛查（一票否决，必须在所有取舍之前）

| 红线 | 判定依据 | 命中后果 |
|---|---|---|
| ① 安全 / 特殊特性超差 | 图纸上的安全特性符号项、法规强制项| 禁止让步，禁止放行，直接进拒收隔离 |
| ② 合同写明零缺陷 | 客户质量协议 / 质量保证协议明文条款（引用条款编号 + 版本号） | **让步路径直接关闭**，只能走返工/暂缓/拒收 |
| ③ 影响无法评估 | 缺陷的功能影响无图纸、无DFMEA、无检验标准可依据 | 禁止让步，需先补齐评估依据 |

**顺序绝不能反。** 先做红线筛查再谈可能性，否则会出现"先想好怎么放行、再去找理由"的倒推。

### STEP 3 · 缺陷等级重判 + AQL 档位复核

缺陷分级标准：

| 等级 | 定义 | 适用 AQL | 处置原则 |
|---|---|---|---|
| **CR 致命** | 影响安全、法规、导致功能完全失效 | 0（不允许） | 一律拒收，禁止让步 |
| **MA 主要** | 影响功能、可靠性、装配互换性 | AQL 1.0 | 需工程评估，可申请让步 |
| **MI 次要** | 仅影响外观，不影响功能与寿命 | AQL 2.5 | 可让步，需客户书面确认 |

抽样接收数对照（GB/T 2828.1 一般检验水平 II，正常检验一次抽样）：

| 批量范围 | 样本量 n | AQL 1.0 Ac/Re | AQL 2.5 Ac/Re | AQL 4.0 Ac/Re |
|---|---|---|---|---|
| 151~280 | 32 | 1 / 2 | 2 / 3 | 3 / 4 |
| 281~500 | 50 | 1 / 2 | 3 / 4 | 5 / 6 |
| 501~1200 | 80 | 2 / 3 | 5 / 6 | 7 / 8 |

**这一步最有价值的产出是"排除性结论"**：现场常见错误是一把尺子量到底，把只影响外观的次要缺陷按主要缺陷的接收数判不合格。复核后若不良数 ≤ 对应档位的 Ac，**必须明确输出「本批可以排除，依据是缺陷等级应归类为 X而非 Y」**，并引用协议中对该缺陷类型的定性条款。

若客户协议对某类缺陷有特别约定（如"所有尺寸类缺陷均视为主要缺陷"），**以协议约定优先于通用分级标准**。

### STEP 4 · 五档处置判定

| 档位 | 前置条件 | 必须写明 |
|---|---|---|
| 🟢 **放行** | 按正确档位判定合格；或协议明文可让+ 有同类先例 | 送货单备注内容、让步清单、留存凭证方式 |
| 🔵 **返工后复检** | 返工技术可行 且 能在交期前完成 | 返工方式与工时、可投人力、完成日、**返工本身的风险**、复检项目与范围 |
| 🟡 **暂缓放行** | 让步路径关闭或返工不可行，但仍有协商空间 | **暂缓原因、责任人、关闭条件、预计关闭时间** |
|⚪ **让步接收** | 协议允许 且 已取得或可取得客户书面回函 | 回函要求与周期、使用条件与限用范围、追溯方式；**未获回函前不得发货** |
| 🔴 **拒收隔离** | 命中红线① 或 ③；或不良率远超可接受范围 | 标识隔离方式、全批去向追溯、后续处置责任人 |

**「暂缓放行」是本Skill 的关键设计，不可省略。** 中小企业真实处境往往不是"能发/不能发"，而是"现在还不能发，但有条路能救"。把它写成暂缓并带上关闭条件和责任人，比含糊拖着强得多。

**判返工前必须验算交期**：返工总工时 ÷ 可投人力 → 完成日，与约定交货日比较。外协返工须计入来回运输天数。若完成日晚于交货日，**不得判"返工后复检"，应转"暂缓放行"并给出协商建议**。

**成品库存兜底检查**：判断是否有同图纸版本的已检合格库存可部分顶替，实现"先发一部分保客户上线，缺口后补"。这一步经常被忽略，但往往是唯一能同时保住质量和交期的路。

### STEP 5 · 两边代价对称呈现

每一档结论都必须同时给出：

- **按此结论执行的风险**：客户端投诉概率、协议约定的索赔/罚则条款（引用原文与金额口径）、供应商评分影响
- **不按此结论执行的代价**：交期违约金条款、客户产线上线受影响的日期、内部返工与挑选成本

**为什么必须对称**：现场往往只算得清一边——交期违约是明天就要面对的，客户投诉是一个月后的事，于是天然倾向放行。把两边代价并列摆出来，才是完整的决策依据。

### STEP 6 · 待确认事项清单 + 先例台账追加

待确认事项每条必须包含四要素：**问谁 · 要确认什么 · 为什么必须确认 · 建议话术**。

必须列入待确认的典型情形：
- 客户协议是否有更新版本或补充约定（摘录版本可能过期）
- 图纸版本号与公差带（决定返工目标值，修磨类返工尤其关键）
- 返工产能数据的口头来源（"赶得上"这个结论的唯一支点）
- 客户是否需要单独回函（协议约定可能只要求送货单备注）
- 历史缺失的先例记录能否从财务返工费用凭证反推补录

**先例台账追加**：本次每批处置写入台账，字段含发生日期、客户、产品、缺陷类别、偏差描述、处置方式、**依据条款编号**、客户是否书面确认、客户后续反应（待回填）、记录人。

## 4. 输出结构（固定，不可缺项）

```
一、判断前提说明（哪些描述是主观的、哪些等级判定被修正）
二、硬拦截红线筛查结果（三条逐条，命中的标明依据条款号+版本号）
三、缺陷等级重判与 AQL 复核表（含复核判定与原判定的差异）
四、逐批五档处置结论（每批：结论 + 依据 + 前置/关闭条件 + 两边代价）
五、待确认事项清单（问谁·确认什么·为什么·建议话术）
六、交付物：出货放行决策单（含会签栏）+ 批次明细与放行状态 + 先例台账（已追加本次）
```

## 5. 硬规则（不可违反）

1. **禁止自行判定放行**。输出的是**建议 + 会签栏**，最终放行须人签字。任何情况下不得输出"可直接发货"这类替人拍板的表述。
2. **红线筛查必须在最前**，且命中红线②时**绝对不输出让步接收档**，即使技术上完全等效。
3. **无客户质量协议时，不得输出"让步接收"结论**，改为「让步可行性待确认」并提示索取协议附件。
4. **判"返工后复检"必须附交期验算**，完成日晚于交货日的一律转"暂缓放行"。
5. **CR 致命缺陷一律拒收**，不进入任何取舍逻辑。
6. **每条结论必须带证据出处**（哪份材料、哪一行、哪条款、哪个版本号）。无出处的判断不得写入结论。
7. **拿不到的数据必须明确写出来**，不得用推测填充。宁可写「XX 保存在销售部合同附件中，本次未取得，建议索取后复核」。
8. **不做根因分析**。根因分析属场景 7.1，本 Skill 只做向前的交付决策。若用户需要根因，提示切换。

## 6. 常见坑

| 坑 | 规避 |
|---|---|
| 直接采信检验单上的"不合格"结论 | 必须按CR/MA/MI 重判等级并用对应 AQL 复核接收数 |
| 只看技术等效性就判可以让步 | 让步是**合同事实**不是技术判断，先查协议条款 |
| 判返工却没算交期 | 返工总工时 ÷ 人力 → 完成日，外协要加来回运输天数 |
| 忘了查成品库存能否部分顶替 | 这往往是唯一能同时保质量和交期的路 |
| 把"暂缓放行"写成"不予放行" | 暂缓必须带关闭条件与责任人，是"先不发"不是"不发" |
| 代价只讲一边 | 放行风险与违约代价必须并列 |
| 客户协议摘录版本过期 | 列入待确认事项，明确摘录日期 |
