# 协调稿与话术模板

三份产出：**对内协调稿（纯文本）+ 异常升级通知单（PDF 1 页）+ 异常台账（Excel 1 sheet）**。

原则：中小企业的沟通载体是微信群。**一份要打开附件才能看的报告，在群里等于没发。**

---

## 一、对内协调稿（可直接粘贴到工作群）

### 硬约束

- **≤300 字**，手机一屏能读完
- **纯文本**，不用附件、不用表格
- 每条必须含五项：**是第几次发生 / 归口 / 责任人 / 今日具体动作 / 时点**
- **末尾单独列P3 项**，明确写"留在现场处理，不占用今日会议"

### 结构模板

```
【{日期} 异常处置 · {N} 项需今日推进】

1️⃣ {事件一句话描述}（{关键影响数据}）
· {是第几次发生 + 前几次的日期与当时处置}
· 归口：{部门}（{责任人}）｜协办：{部门}
· {时点} 前：{具体动作}
· {若涉客户}{谁}{时点}前先回复{客户}，口径见附件

2️⃣ …

3️⃣ …

🟢 另有 {M} 项判为 P3，留在现场处理，不占用今日会议：{简述}
```

### 写法要点

**要点① 第二行永远是"这是第几次"**
这是整份协调稿最有分量的一行。`这是第 3 次（7-03 八台、5-21 一次），前两次都只做了现场修配没查原因` —— 这一句话就把事件从"又来一件麻烦"变成"必须改机制"。

**要点② 动作必须是可验收的**
- ❌ `尽快查明原因`
- ✅ `今日 17:00 前：开 NCR 并给出孔位偏移原因初判`

**要点③ 对外与对内动作分开写**
客户投诉类事件，对内查原因和对外先回复是两件事，时点也不同。销售的回复动作通常要**早于**技术结论出来的时间。

**要点④ P3 项必须出现在协调稿里**
不是省略，是明确写出来"这些不占用今日会议"。**降级判定只有被看见才有意义**——否则老板会以为你漏了。

## 二、对外话术（客户侧）

### 五段式结构（顺序不可乱）

| 段 | 内容 | 为什么在这个位置 |
|---|---|---|
| 1 | **先给确定的承诺** | 客户现在最急的是眼前的产线，不是改进措施 |
| 2 | **认责不推** | 若责任在我方，明确说"责任在我们，我们不推" |
| 3 | **若历史重复过，主动说出来** + 这次不一样在哪 | 客户往往自己就知道（会说"上个月也有过"） |
| 4 | **具体的预防动作** | 不能是"加强管理""加强培训" |
| 5 | 致歉 + 联系方式 | |

### 关于第 3 段（最关键）

客户说"这个问题上个月也有过"的时候，说明他记得。**这时候回避比承认更伤信任。**

对比：

❌ `我们会加强质量管控，避免类似问题再次发生。`
✅ `我们查了记录，这个部位今年确实反复出现过，之前每次都是现场修配了就过去了，没有从根上查。这次我们开了正式的问题单，会给您一份原因分析和改进措施，本周五前发您。`

第二种写法承认了一件不好听的事实，但同时给出了**"这次不一样在哪"的具体证据**（开正式问题单、给原因分析、有时点）。

### 关于第 4 段

预防动作要具体到"多做了哪个动作"：

- ❌ `加强出货检验`
- ✅ `后续同型号的机箱，我们会在出货前增加门锁装配的实物核对，不只看图纸尺寸`

## 三、异常升级通知单（PDF 1 页）

### 决策包五要素（缺一不可）

一次没有信息包的升级，等于把判断责任转移给了信息最少的那个人。所以每件 P1 必须给齐：

| # | 要素 | 说明 |
|---|---|---|
| 1 | **问题描述与影响范围** | 涉及工单号、订单金额、客户、是否停线 |
| 2 | **已采取的临时围堵措施** | 现场已经做了什么（很多时候现场已处置，只是没人汇总） |
| 3 | **证据** | 工单号、检验记录号、**历史记录索引**（第几次发生的依据） |
| 4 | **可选方案与代价对比** | 至少两个方案，各自的代价、周期、风险 |
| 5 | **建议决策与责任人** | 建议怎么做、谁做、什么时候之前 |

### 抬头与签署

- 单据编号：`ES-{YYYYMMDD}-{流水}`
- 分级、来源入口、发生时间、上报人
- SLA 到期时点（按分级自动算）
- **总经理签署栏** + 日期

### 页脚

> 本单为升级建议，归口部门与最终处置由管理层确认。

这句话对应 SKILL 的硬规则——不替管理层派活。

## 四、异常台账（Excel 1 sheet）

### 列结构

`事件编号 | 来源入口 | 发生时间 | 上报人 | 事件描述 | 涉及客户 | 涉及订单/工单 | 等级 | 建议归口 | 责任人 | SLA到期 | 是否重复发生（第几次） | 前次发生日期 | 状态 | 闭环日期`

### 关键设计

**「是否重复发生（第几次）」是这张表存在的理由。**

这一列在任何 ERP/MES 里都没有。它必须靠人工或Agent 检索填入。而一旦这张表持续积累，**下一次同类问题进来时，重复性判据就不用再靠谁的记忆了**。

**「前次发生日期」单独一列**，方便直接跳查。

### 技术要点

```python
ws.freeze_panes = 'A2'
ws.auto_filter.ref = f'A1:O{last_row}'
ws.sheet_view.showGridLines = False
# 按等级填色：P1 红底 / P2 黄底 / P3 绿底
# SLA 到期 = 发生时间 + 分级对应响应时限
```

### 自检断言

```python
assert p1 + p2 + p3 == 合并后事件数, '分级数与事件数不符'
assert 原始上报数 >= 合并后事件数, '合并后不应多于原始'
# 每条 P1 必须有责任人与SLA
for r in p1_rows:
    assert r['责任人'] and r['SLA到期'], 'P1 必须有责任人与SLA'
```
