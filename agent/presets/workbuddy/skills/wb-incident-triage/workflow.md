# 异常分级与升级归口 Skill

> 管理层岗位场景 2.2 专用 · 一套引擎吃三类入口 → 合并重复上报 → 反向检索历史判重复性 → 三级分级 → 归口建议 + 排除理由 → 可贴群协调稿 + 对外话术 + SLA 台账

---

## 1. 用途

中小企业没有"升级机制"，只有老板的微信。所有异常最后都汇到同一个人，而他没有筛子。这个 Skill 一次做完六件事：

1. **三类入口统一吃**：客户投诉/加急改单、现场停线/批量不良、跨部门久拖不决 —— 输入是微信原话、电话口头转述、周会记录，**不要求结构化**
2. **合并重复上报**：同一问题的多次上报、以及"升级信号"（如客户说要找老板）必须合并成一个事件，否则同一问题占用两次升级通道
3. **反向检索历史判重复性**：按设备号、部位、客户、工序交叉检索历史处置记录，判断这是第几次发生 —— **这是最有分量、也是唯一没有数据字段的判据**
4. **三级分级**：P1 / P2 / P3，**含降级**。价值在把不该占用管理层的挡回去，不在报警
5. **归口建议 + 排除理由**：输出"建议归 X，因为不是 Y 也不是 Z"，**不替管理层派活**
6. **三份可直接用的产出**：对内协调稿（≤300 字可贴群）、异常升级通知单（含决策包五要素）、异常台账（含"是否重复发生"列）

**这个 Skill 解决的真实痛点**：一线上报时倾向把问题说重（说轻了怕没人管），于是群里每条都"很急"，老板只能凭语气判轻重。而"这个问题上次也有过"——上次是什么时候、怎么处理的，没有任何系统字段能回答，只能靠人翻记录回忆。结果同一台设备半年漏三次油、同一个客户三次投诉同一个部位，每次都被当成新问题处理一遍。

## 2. 触发方式

### 2.1 用户一句话触发（推荐）

```
上周五到今天群里的异常我让行政摘出来了，客户投诉、车间停线、周会上拖着的都在里面。
帮我理一下：哪几件今天必须我管，哪几件让他们自己处理就行。
重复发生过的重点标出来 —— 我要知道哪些是老问题又犯了。
每件给个建议归口，但别直接派活，理由写清楚我自己判断。
再给我一段能直接发群里的，和一段销售回客户用的。
跨部门那种谁都不认的，别硬塞给某个部门。
```

### 2.2 输入材料清单

| # | 材料 | 必需 | 缺失时的降级策略 |
|---|---|---|---|
| 1 | 异常事件原始记录（三类入口汇总，原文照录即可） | **必需** | 无此项无法运行 |
| 2 | **历史异常处置记录** | 强烈建议 | **缺失时不得判定"重复发生"**，所有事件按首次处理，并提示「本厂无历史台账，建议自本次起建立，重复性判据本次不可用」 |
| 3 | 客户与订单背景（客户等级、采购额占比、涉及工单金额与交期） | 建议 | 缺失时无法判断商业权重，A/B/C 级客户一律按B 级处理并标注 |
| 4 | 分级与归口规则（企业自己的） | 可选 | 缺失时用本Skill 内置默认规则，并提示企业应自行校准阈值 |

## 3. 六步法工作流程

### STEP 1 · 读原文并合并重复上报

- 输入是口语化原话，**语气与事实混在一起**。先剥离语气，提取事实：涉及什么产品/工序、数量、是否已停线、客户是谁、发生时间
- **合并判定**：以下情形必须合并为一个事件
  - 同一问题的多次上报（不同人、不同时间报同一件事）
  - **升级信号**（如"客户要找老板谈""这事没人管"）——它是既有事件的状态变化，不是新事件
  - 同一根因的多个表现（如同一台设备的漏油与停机）
- 合并后明确写出"原始 N 条 → 合并为 M 件事"

### STEP 2 · 反向检索历史，判这是第几次

检索键（按优先级）：
1. **设备编号**（如"2 号折弯机"）
2. **产品 + 部位**（如"P-CAB-11 门锁"）
3. **客户 + 问题类型**
4. **工序 + 现象**（如"喷涂 + 返工率"）

对每一条命中，必须提取：
- 发生日期
- 当时的归口部门（**若为"未明确"，这本身就是重要信号**）
- 当时的处置措施（**特别注意"临时""现场修配""口头提醒""未做原因分析"这类字样**）
- 是否闭环

**输出形态**：`本次为第 N 次发生`，并列出前 N-1 次的日期与当时处置。

**这一步最有价值的发现**：前几次的处置方式往往就是本次发生的原因。例如"4 月那次临时补漏未换密封件"直接导致 8 月再次漏油。**这类因果链必须显式指出。**

### STEP 3 · 四维判据分级

| 判据 | 取数来源 | 说明 |
|---|---|---|
| **影响面** | 涉及工单数、订单金额、是否停线 | 客观可算 |
| **紧迫度** | 客户上线日、交货日、已拖天数 | 客观可算 |
| **复杂度** | 涉及几个部门 | 从原文中数|
| **是否重复发生** | STEP 2 检索结果 | **无字段，靠检索** |

默认三级规则（企业可改）：

| 等级 | 判定条件（满足任一） | 响应 | 决策 | 升级层级 |
|---|---|---|---|---|
| **P1 紧急** | ① 已致或将致客户停线 ② A 级客户明确要求升级 ③ 影响 3 张以上在制工单 ④ **同一问题第 3 次以上** | 2 小时 | 24h 内出临时方案 | L3 总经理 |
| **P2 重要** | ① 影响单张工单交期 ② B/C 级客户投诉但未停线 ③ 同一问题第 2 次 ④ 跨 2 个部门 | 当日 | 3 个工作日出方案 | L2 部门经理 |
| **P3 一般** | ① 客户提醒改进但已验收 ② 现场可自行消化 ③ 首次发生且影响面单一 | 3 个工作日 | 1 周内闭环 | L1 班组/主管 |

**为什么是三级而不是四象限**：某企业导入初期把 80% 问题判为最高级，资源被摊平，真正紧急的反而没人管；后来把最高级压到 15% 左右，满意度反而上升。**级别设计得越复杂，一线越倾向全部往高的填。三级 + 三层是中小企业真正维持得住的粒度。**

**必须做降级判定**：对每一条上报，明确标出"与上报预期一致 / 降级 / 升级"。降级要给足理由，因为这是最容易被质疑的输出。

典型该降级的情形：
- 按"客户投诉"上报，但 C 级客户 + 已验收 + 客户仅表示"提醒改进"
- 按"现场停线"上报，但实为排班/人员问题，且现场已自行妥善处置
- 按"批量不良"上报，但数量与影响面均单一且首次发生

### STEP 4 · 归口建议 + 排除理由

**硬规则：只建议，不派活。** 输出格式固定为：

```
建议归口：X 部门
为什么是 X：（判据）
为什么不是 Y：（排除理由）
为什么不是 Z：（排除理由）
协办部门：…
```

归口参考逻辑：

| 问题特征 | 建议归口 | 排除逻辑要点 |
|---|---|---|
| 尺寸/孔位类不良，**工艺文件有明确要求** | 生产部 | 属执行偏差；若工艺文件本身无要求或有矛盾则改归工艺部 |
| 设备故障，**同类重复发生** | 设备科 | 首次属维修范畴；重复发生指向预防性维护与备件策略缺失，仍归设备科但性质从"修好"变成"改机制" |
| **来料与标准争议并存，多部门互相归因** | **需管理层指定** | 本质是"标准空白"而非某部门失职，**不得硬派** |
| 包装/运输类客户提醒 | 仓库 | 属出货作业范畴；若为包装设计问题则归工艺部 |
| 人员技能/排班导致产能不足 | 车间自行消化 | 属现场管理；若影响交期则同步 PMC |

**"需管理层指定"这一档必须保留。** 遇到跨 3 个以上部门、各方说法都成立、且历史上已多次无结论的问题，正确做法是指出**"要拍的不是责任，是标准归属"**，并把它转化为具体的待拍板问题（如"板材来料清洁度标准归谁定、喷房温湿度范围归谁定，请本周内指定"）。

### STEP 5 · 对内协调稿（可直接贴群）

硬约束：
- **≤300 字**，手机一屏能读完
- 每条必须含：**是第几次发生 / 归口 / 责任人 / 今日具体动作 / 时点**
- 末尾**单独列出 P3 项**，明确写"留在现场处理，不占用今日会议"——这一句是降级判定的落地
- 不用附件，纯文本

### STEP 6 · 对外话术（如涉及客户）

结构（顺序不可乱）：
1. **先给确定的承诺**（客户最急的是眼前的产线，不是改进措施）
2. **认责不推**（若责任在我方）
3. **若历史上重复发生过，主动说出来**并说明"这次不一样在哪"
4. **具体的预防动作**（不是"加强管理"）
5. 致歉与联系方式

**关于第 3 点**：客户往往自己就知道这个问题反复出现过（会说"上个月也有过"）。既然客户知道，**主动承认并给出"这次不一样在哪"，比含糊道歉有效得多。**

## 4. 输出结构（固定，不可缺项）

```
一、原始上报 N 条 → 合并为 M 件事（列出合并了哪几条、为什么）
二、重复性检索结果（每件：本次为第几次 + 前几次的日期与当时处置）
三、三级分级表（每件：命中判据 + 分级 + 与上报预期一致/降级/升级）
四、归口建议（每件：建议归 X + 为什么不是 Y/Z + 协办 + 本次特别要解决的）
五、对内协调稿（≤300 字，可直接粘贴）
六、对外话术（如涉及客户）
七、交付物：异常升级通知单（决策包五要素 + 签署栏）+ 异常台账
```

---

## 5. 硬规则（不可违反）

1. **不替管理层派活**。归口只输出"建议 + 排除理由"，指派部门是组织权力。
2. **跨部门谁都不认的问题，不得硬派某个部门**。必须判为"需管理层指定"，并转化为具体的待拍板问题（定标准归属，而非定责任）。
3. **必须做降级判定并给足理由**。分级的价值在降级，不在报警。不允许把所有事件都判为 P1。
4. **无历史台账时不得判定"重复发生"**，改为提示建立台账。
5. **重复上报必须合并**。同一问题的升级信号不算新事件。
6. **协调稿必须 ≤300 字**且每条带责任人与时点。超长即失效——群里没人看长文。
7. **每条结论必须带判据出处**（哪条原文、哪条历史记录、哪个客户等级）。
8. **不做根因分析**。归因属品质异常分析场景（9.1），本Skill 只做分级与归口。
9. **P2 可以为零**。分级不是为了填满每一格。

## 6. 常见坑

| 坑 | 规避 |
|---|---|
| 按上报条数逐条处理 | 先合并重复上报与升级信号 |
| 因为语气急就判高级别 | 剥离语气提取事实，按四维判据判 |
| 全部判P1 | 强制做降级判定，P1 占比过高会让资源摊平 |
| 硬派跨部门问题给品质部 | 判"需管理层指定"，把问题转化为"标准归谁定" |
| 忽略"前几次怎么处置的" | 前几次的临时处置往往就是本次的原因，必须显式指出因果链 |
| 协调稿写成长报告 | ≤300 字，手机一屏，纯文本 |
| 对外话术回避历史重复 | 客户往往已经知道，主动说并给"这次不一样在哪" |
| 台账只记"已处理" | 必须含归口、责任人、SLA 到期、是否重复发生（第几次） |
