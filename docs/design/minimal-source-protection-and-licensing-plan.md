# 最简源码保护与授权方案：保留结构，按文件保护

设计日期：2026-09-25。目标：客户可继续做场景二开，我方保护少量核心源码并提供基础离线授权。状态：设计完成；未修改运行代码、未安装保护工具、未验证保护产物。

**当前推荐：交付一份保持现有目录结构的“部分源码发行包”，仅把保护清单中的 Python 文件换成 PyArmor 产物，其余允许二开的代码保留源码。**

此前提出的扩展清单、统一插件入口、专用 SDK、外部场景发现及覆盖机制，均不作为第一版要求。客户沿用当前开发方式，新增场景时允许修改现有场景登记、路由和前端组装文件。第一版优先用普通 Python / Docker 交付二开环境。

**为什么这样更简单**

用户要求是保护核心且允许二开，并没有要求“客户只能通过插件扩展”“核心与场景必须完全解耦”或“升级自动无冲突”。保留现有耦合关系，可以先完成交付保护，把平台架构重构推迟到确实需要时。

Python 模块的相对路径和公开类、函数调用方式尽量保持原样；客户看到的业务代码仍按原路径导入核心。保护后的 `.py` 是运行时引导与受保护载荷，不是需要客户编辑的核心源码。使用允许明文模块调用公开对象的基础保护配置；不对这些边界启用 `--private`、`--restrict` 或要求所有客户回调已受保护的断言。运行兼容性必须用项目实测确认。[PyArmor 保护选项](https://pyarmor.readthedocs.io/en/latest/tutorial/obfuscation.html#more-options-to-protect-package)

**只分两类代码**

| 分类 | 项目中的范围 | 交付方式 |
| --- | --- | --- |
| 保护清单内 | 首轮候选：`agent/protocol/agent.py`、`agent/protocol/agent_stream.py`、`bridge/agent_bridge.py`、`auth/service.py` 中需要保护的模块；也可包含其他自有核心实现 | 原路径放保护产物，附运行时 |
| 明确开放二开 | `Scene/`（包含 `_shared/` 接入代码）、`scenes/`、场景相关 Web 入口和路由、页面、技能、插件及必要接口定义 | 保留可编辑源码 |

候选文件根据商业价值、客户修改频率和实测兼容性收敛，不代表以上文件已经选定或全部属于专有实现。公开上游已经提供的等价实现，不应当作不可替代的授权屏障。按文件列清单，不递归保护整个 `agent/`、`channel/` 或 `auth/`，也不为保护而搬目录。

第一版接受开放接入代码的实现可被客户阅读。核心身份服务的保护不等于同进程代码安全隔离；业务权限仍按原体系实现与验证，不能依靠混淆保证权限正确。

**客户如何二开：沿用现有步骤**

| 二开内容 | 沿用的操作 |
| --- | --- |
| 修改场景业务、页面、提示词、技能 | 编辑 `Scene/<scene_id>/` 对应文件，重启服务清理现有模块及前端缓存 |
| 新增通用场景 | 新建场景目录、维护 `Scene/catalog.json` 及需要的技能映射 |
| 新增专用 Python 接口 | 按现有方式登记 handler、场景模块映射及 `channel/web/route_registry.py`；入口按需在 `channel/web/web_channel.py` 导出 |
| 新增专用页面与资源 | 沿用 `Scene/_shared/frontend.py` 等现有组装及资源白名单；当前资源清单包含 `source-manifest.json`，需要同步维护 |
| 增加第三方依赖 | 在普通 Python 环境安装，或在客户 Docker 镜像中安装 |

已核对的接缝包括 `Scene/_shared/original.py` 的 `MODULES`、`Scene/_shared/http.py` 的 `HANDLERS`、前端资源组装与 Web 路由登记。因此这些文件保持可编辑，比新建一套扩展协议更省改造。不是“新建文件夹就自动接入”，而是继续按项目原来的步骤接入。

现有 `source-manifest.json` 还承载上游迁移来源与哈希记录。客户修改业务源码后，不能继续宣称它与原迁移源码逐字节一致；保留原版来源记录，在客户分支记录改动，功能与权限验证照常执行。

客户对开放源码的修改不需要 PyArmor，也不需要我方重新加密或重新签发授权。客户可以重新组装 Docker 镜像，但使用我方提供的受保护核心，不能重建其原始实现。

**授权只使用一个外置文件**

继续采用 PyArmor 的 `pyarmor.rkey`，签发时指定设备和期限，续期替换文件并重启。构建注册材料仅在我方；客户获得运行时和客户授权。开发环境也签发普通授权，不交付免授权版本。[外置授权示例](https://pyarmor.readthedocs.io/en/latest/tutorial/obfuscation.html#using-outer-file-to-store-runtime-key)

授权随真实核心模块的保护运行时生效。不要只新增一个受保护的 `license_check.py`、让全部业务代码保留明文，否则删除该导入便失去基本约束。保护核心实现后，删除启动检查不能直接恢复该实现，但有能力者仍可能替换整个核心。

授权语义明确为：**有效授权允许使用受保护核心；未授权或过期后受保护核心在运行时检查时拒绝执行。** 配置运行时周期检查，检查由受保护函数调用触发，不能承诺截止时刻所有线程立即退出。客户自有独立脚本、静态页面、未依赖该核心的功能不受这份授权强制约束。这是相对前版“到期强制终止整个后端”的主动简化。[周期检查规则](https://pyarmor.readthedocs.io/en/latest/reference/man.html#cmdoption-pyarmor-gen-period)

授权文件放入稳定目录，由进程启动配置的 `PYARMOR_RKEY` 指向该目录；避免在其他搜索位置放备用授权。Docker 的设备标识在实际容器中验证重建稳定性，固定 MAC 只是可复制的基础绑定，不能宣传为强防复制。设备绑定、到期和查找路径使用工具原生能力。[命令参考](https://pyarmor.readthedocs.io/en/latest/reference/man.html#pyarmor-gen-key)

不增加授权数据库、授权页面、自建签名算法、在线激活服务、全局停机守护线程或每个业务接口的授权装饰器。界面暂时沿用现有错误提示和日志。

**发布过程仅增加一段处理**

```text
我方完整开发源码
    → 生成干净发布目录
    → 按清单替换核心模块为保护产物
    → 加入对应平台的 PyArmor runtime
    → 交付部分源码包 / 从该目录构建 Docker 镜像
    → 另行签发客户 pyarmor.rkey
```

1. 新增一份保护文件清单和一个发布脚本。保持目录、模块名及包结构不变，验证工具输出的相对路径映射，不能按文件名平铺产物。
2. 发布目录只收集运行文件；开放业务代码可原样复制，受保护源码及其原始字节码、备份不能进入最终发布包。排除 `.git`、真实配置、数据和我方注册材料。
3. Docker 使用干净发布目录作为构建输入，保留现有运行入口。完整开发仓库不能进入交付镜像任意一层；不要先写入原始核心源码再删除。
4. 启动仍用 `python app.py`，我方不改变正常开发源码。客户版本固定 Python、PyArmor runtime、操作系统和架构兼容组合；客户新增依赖需要与该组合兼容。
5. 为便于二开，优先交付普通 Python / Docker 版本。现有桌面包可另行复用发布产物，但不把“桌面随意增加依赖而无需重打包”纳入最简方案。

构建脚本和保护清单必须检查：目标文件有保护产物时才交付；失败时中止，不能悄悄回退到明文。还要检查同一模块是否在归档、数据文件、旧副本或镜像层中重复携带原始实现。

**升级与维护的真实代价**

更新采用“标准发行基线 + 客户二开分支”。我方负责标准包、兼容说明和数据迁移说明；客户或实施团队负责合并二开、验证并部署。第一版用 Git 和完整发布包即可，不增加在线更新服务。

首次交付就保存我方未修改发行包作为基线，再从它建立客户分支。例如标准版 `vendor-v1.0.0`，客户基于它开发 `customer-a`；我方发布 `vendor-v1.1.0` 后，将该版本合入客户的升级分支，验收后标记 `customer-a-v1.1.0-r1`。版本名为示例，两个编号分别表示平台版本与客户修订，不拆成各模块独立版本。

客户维护的 Git 仓库只记录可交付发行文件和客户改动，不能由我方含原始核心源码的开发仓库直接克隆或保留其历史。后续标准包导入同一条 vendor 历史；不要每次新建无关仓库，否则会丢失合并基线。部署不包含客户 Git 仓库、授权及真实配置提交历史。

| 更新对象 | 处理规则 |
| --- | --- |
| 保护清单内的核心和 PyArmor runtime | 采用新版本完整配套产物，不对密文做行级合并；删除新清单已移除的旧文件，防止旧实现被继续导入 |
| 双方都能修改的源码、路由、模板和场景 | 以旧标准版为共同基线，合并新标准版与客户改动；冲突人工处理，无文本冲突也需功能验证 |
| 客户自行新增且无命名冲突的场景文件 | 保留；新增同名文件、标准版删改客户已改文件时，按冲突处理 |
| 实际配置、授权、凭据主密钥、工作区和数据库 | 放在代码发布目录外并沿用；不使用新版本模板直接覆盖真实配置，数据格式变化通过迁移处理 |

三方合并使用 Git 的已有能力，不自建合并算法。[Git 合并说明](https://git-scm.com/docs/git-merge)

每次发布随包提供一份轻量版本清单及更新说明：版本号、允许升级的起始版本、Python/平台/runtime 组合、受保护文件与校验值、接口变化、数据迁移及回退条件。新增/移除保护文件、将原开放文件转为保护文件，必须明确说明；若客户修改了该文件，先迁移二开逻辑，不能直接覆盖丢弃。

保护模块、开放调用方及依赖版本应配套发布，不能只替换几个核心文件便认定升级完成。客户改过的公开接口若与新版核心不兼容，需要在升级分支适配。

**一次升级的具体流程**

1. 保存客户当前改动和运行版本标签，导入新的标准发行包；在独立升级分支中合并，保留生产版本继续运行。
2. 整套采用新版保护产物和 runtime，合并开放代码，安装对应依赖，构建有明确版本标签的客户镜像或完整运行目录。
3. 使用数据副本在隔离验证环境演练迁移，检查授权、登录、聊天、二开场景及新增接口权限。关闭该验证实例的外部渠道和定时任务，防止与生产实例重复处理业务。绑定设备的授权需要覆盖验证设备。
4. 进入维护窗口，停止业务写入和后台任务，对真实配置、所有相关数据库、工作区、授权及所需密钥做一致性备份；记录旧镜像/代码版本和依赖环境。
5. 切换到验证过的客户版本，执行该版本要求的迁移，再做最小验收，通过后恢复业务；失败按回退条件处理。

Docker 更新的是合并二开后生成的客户镜像，使用固定版本标签或摘要，并继续挂载原数据卷。客户改动若只存在于旧容器可写层，重建会丢失，因此必须先纳入客户分支和构建产物。普通 Python 部署使用新的完整代码目录与配套虚拟环境，验证后切换服务启动路径；避免在正在运行的目录逐个覆盖文件。

升级与续期分开。普通版本更新以沿用现有有效授权为目标，我方须验证旧授权对新产物的兼容性；保护工具、产品注册配置、runtime 或设备环境变化时不能直接承诺兼容，应在上线前确认并在必要时补发。原授权文件保留在发布目录之外。

**回退边界**

只有确认新数据格式与旧版兼容时，才可以直接切回旧代码/镜像。若新版本已经执行了不兼容的数据库或文件迁移，需要恢复旧代码、旧依赖及与之配套的升级前数据快照。项目 `auth/store.py` 已有 `schema_migrations`，`app.py` 启动还会触发会话等迁移，不能把“切回旧镜像”等同于完整回滚。

在重新开放业务之前完成验收可缩小回退损失。若新版已接受新的业务写入，恢复旧快照会丢失这些新数据；必须先处理数据导出、补偿或兼容迁移，不能宣称无损一键回退。

**现有更新入口需适配**

当前 `cli/update_service.py` 的版本检查固定查询 `zhayujie/CowAgent`，源码更新执行 `git pull`，依赖失败后还会尝试 `git reset --hard`。因此带客户 Git 仓库的部分源码发行包不能直接沿用当前 `cow update` / Web 一键源码更新。

第一版最小调整是：以发布标识识别二开发行包，在 CLI 和 Web 的更新执行入口统一拒绝直接源码更新，提示按发行包升级流程处理；版本检查不再把上游 CowAgent 发布认作本产品更新。仅隐藏按钮不足以约束 CLI。此项尚未实施。

桌面已有 `desktop/src/main/updater.ts` 的安装包更新逻辑，但当前方案未提供安装包内客户改动的自动合并。标准桌面版按我方配套包更新；客户定制桌面版应走专属构建和对应更新来源，不能直接覆盖为标准版。普通 Python / Docker 仍是第一版二开的默认交付方式。

平台需交付一页二开说明、保护文件清单、现有调用接口说明和授权放置说明即可。无需先实现新的 SDK；客户需要调试受保护核心内部时由我方协助。

**三种选择的取舍**

| 方案 | 初始工作 | 二开影响 | 结论 |
| --- | --- | --- | --- |
| 全部交源码、靠合同管理使用 | 最少 | 最自由 | 缺少技术源码保护和运行授权，不满足已明确目标 |
| 少量核心文件保护、其余源码、内置离线授权 | 小；发布处理与兼容验证 | 沿用现有二开，升级需合并 | 当前推荐 |
| 核心包 + 标准场景插件协议 | 较大；加载器、接口与版本维护 | 扩展边界更清晰 | 需要多客户统一升级、独立插件交付时再做 |

只打包为可执行程序、只交原始 Python 字节码，或仅保护一个入口检查，不作为本方案的替代。重新引入编译工具链和自建授权协议也不能减少第一版工作。

**最小验收**

- 从干净发行目录运行：核心正常，原始核心源码及缓存没有被夹带。
- 有效、缺失、损坏、过期、错误设备授权：直接导入和调用受保护核心的结果符合预期，不能只测试启动器。
- 常驻运行跨到期时间：在实际核心调用处验证周期检查与报错，确认未宣称的独立功能可继续运行。
- 客户不安装 PyArmor 构建工具：修改一个业务场景，并新增一个页面与接口，沿用现有登记方式可运行。
- 明文模块可调用受保护实现，实际使用的反射、动态导入、工具注册、模型调用和场景加载通过。
- 新增接口继续声明路由策略并复用身份、租户和写请求校验；现有路由覆盖及场景功能检查通过。
- 续期和更新核心版本可操作；客户开放源码改动及业务数据未被静默覆盖。

**保护边界**：这是基础商业保护，开放源码、提示词和客户场景不保密。客户拥有主机权限且能执行同进程 Python，可能回拨时间、伪造设备、修改进程或用公开代码替换核心。方案提升读取和直接复用我方核心实现的成本，不承诺防住专业逆向、强制关闭所有二开程序或实时吊销离线授权。
