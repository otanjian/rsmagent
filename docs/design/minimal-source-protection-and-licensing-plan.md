# 最简源码保护与授权方案

设计日期：2026-09-25。目标：客户私有部署后，提高读取、修改核心源码和直接复制使用的成本，支持离线到期授权，同时允许客户开发和修改场景应用。本文为设计，尚未修改构建或运行逻辑，也未验证受保护安装包。

**推荐：PyArmor 保护核心平台 + 开放场景业务源码及扩展接口 + 外置 `pyarmor.rkey` 授权文件。** 桌面端继续使用 PyInstaller / Electron；服务器交付受保护核心镜像，场景扩展从外部目录加载。第一版按部署实例授权，只控制核心平台的设备与期限。客户修改场景无需我方重新加密、签发授权或重新打包核心。

采用工具内置授权，省去自建授权服务器、签名协议、授权数据库和管理页面。运行所需的 PyArmor runtime 随产品交付；构建工具及其注册材料仅留在我方。客户运行不需要验证我方的 PyArmor 构建许可证。[官方许可说明](https://pyarmor.readthedocs.io/en/latest/licenses.html)

| 位置 | 已确认的现状 | 设计调整 |
| --- | --- | --- |
| `desktop/build/build-backend.sh` | 已有 PyInstaller onedir 构建 | 接入 PyArmor 保护及打包步骤，沿用产物目录 |

| `app.py:run()` | 常驻循环只调用 `time.sleep(1)` | 增加受保护的检查触发函数，覆盖长期运行后的到期检查 |
| `plugins/plugin_manager.py` | 扫描磁盘 `__init__.py`，再动态导入 | 保留目录布局与保护后的 `.py` 引导文件，验证加载及重载 |
| `agent/tools/tool_manager.py` | 动态导入并使用 `inspect.signature` | 第一版采用基础保护，验证工具注册和依赖注入 |

| `Scene/catalog.py` | 场景根目录固定在包目录；目录与技能发现已有实现 | 增加外部场景目录解析，保留内置场景作为默认值 |
| `Scene/_shared/{original,http,frontend}.py` | 后端模块与处理器映射写死；前端资源依赖迁移清单 | 为客户场景增加声明式注册，旧场景兼容逻辑保留 |

仓库根目录的 `Dockerfile` 只继承上游镜像，不能直接作为本项目受保护版本的交付构建入口。

**保护范围**

建立一份发布清单，给每个交付文件标记“受保护核心”“可二开源码”或“公开资源”。保护范围按明确文件清单确定，不对整个 `Scene/`、`skills/`、`plugins/` 一刀切保护。第三方依赖与公开上游模块按原有方式分发。

| 层次 | 范围示例 | 客户使用方式 |
| --- | --- | --- |
| 受保护核心 | 平台入口、授权、身份与权限、Agent 引擎、模型接入、平台数据访问、核心 Web 路由 | 使用我方发布包，通过公开接口调用 |
| 受保护场景宿主 | `Scene/catalog.py`、`Scene/_shared/host.py`、`http.py`、`original.py`、`frontend.py` 等宿主适配代码 | 负责注册、身份上下文及资源加载，作为平台升级 |
| 开放业务层 | `Scene/<scene_id>/scene.json`、`backend/`、`frontend/`、`skills/`、`assets/` | 交付可编辑源码，支持复制、新建、修改及部署 |
| 开发接口 | 场景接口说明、类型/函数签名、示例场景、可复用业务辅助代码 | 提供明确的调用约定，客户不必阅读核心实现 |

`Scene/_shared/backend/` 中的公共业务处理器逐项划分：上传、连接管理等涉及平台权限的能力保留在核心；可复用业务算法可以开放。核心中的专有算法如需供客户使用，单独提供可调用接口；客户自有算法保持源码形式。

`.py` 后缀可以保留：保护后的文件是运行时引导及受保护载荷，不应按“存在 `.py` 文件”判断泄漏。也不能只保护入口，核心模块必须进入同一保护清单。

HTML、CSS、浏览器 JavaScript、`SKILL.md`、提示词和 JSON 资源保持可读可改。开放给客户二开的业务源码也不再承担保密目标。需要保密的专有逻辑留在核心模块，向业务层提供调用接口；交给模型的文本仍可能被观察。

**客户二开的最小接入设计**

客户在外部 `extensions/scenes/<scene_id>/` 中维护 `scene.json`、`frontend/`、`backend/`、`skills/`、`assets/`，并增加一个小型 `extension.json`，声明场景 ID、接口版本、后端入口、允许的 HTTP 方法及相对路径、前端入口和静态资源。名称和字段均为待实现约定，不代表已有插件协议。

沿用现有模块加载方式，在核心中补齐以下接入点，不引入插件商店或独立扩展服务：

1. **目录解析。** 新增 `COW_SCENE_DIR` 指定外部场景根目录。它是业务文件搜索路径，不加入通用 `sys.path`；禁止用它覆盖 `Scene/_shared`、`auth` 或其他核心包。场景 ID 和资源路径必须校验，加载模块使用独立命名空间。
2. **场景发现。** 合并内置和外部场景、技能映射及前端资源。不同 ID 注册为新场景；同 ID 只有在清单明确声明覆盖对应内置业务场景时才替换，重复或歧义配置拒绝加载。`source-manifest.json` 继续用于原始迁移校验，客户扩展不需要修改该文件。
3. **后端入口。** 新增一个注册到现有路由权威清单的通用入口，例如 `/api/scenes/extensions/<scene_id>/<action>`，由受保护宿主解析清单并调用客户 handler。旧场景继续沿用现有地址。新增客户接口无需修改核心路由表。
4. **统一上下文。** 宿主在分发前检查平台授权、登录、租户及对应操作权限，写请求沿用来源/CSRF 校验。通过明确接口向业务代码提供当前身份、工作区以及获准使用的模型、工具和文件能力；前端传入的用户或租户 ID 不作为身份来源。
5. **开发约定。** 为新场景交付一个可直接运行的模板和 v1 接口文档，封装现有 `host` 能力，客户新代码不依赖 `channel.web.web_channel` 等私有实现。首版修改后重启服务生效，清理模块及前端组合缓存，无需实现热更新。

现有系统已能按目录读取场景及技能，但上述外部目录、通用扩展路由和清单协议仍需开发。仅将 `Scene/` 排除加密，不能实现完整的“新增场景免核心改动”。

核心使用允许明文扩展调用公开接口的保护配置。第一版不在扩展接口上启用阻止明文调用的 `--private` / `--restrict`，也不对客户回调使用“必须已经混淆”的断言；这类选项会影响接口互操作。[PyArmor 保护选项说明](https://pyarmor.readthedocs.io/en/latest/tutorial/obfuscation.html#more-options-to-protect-package)

交付给客户的内容是“核心运行包 + 开放场景源码与模板 + 接口文档 + 开发/生产环境各自授权”。客户为独立开发机领取普通设备绑定授权，不提供生产包中的免授权开关，也不提供我方 PyArmor 注册材料。客户可以用自己的 Dockerfile 基于核心镜像安装场景依赖；只需新增场景文件时，挂载后重启即可。

桌面扩展放在用户数据目录，不能修改已签名安装目录。Python 场景仅使用打包时已有依赖即可直接加载；新增第三方 Python 包或原生库不承诺可直接注入 PyInstaller 包。首版二开以 Docker/服务器环境为主，桌面新增依赖需要我方更新运行包。模板须覆盖明文模块调用受保护核心的实际运行验证。

**离线授权与续期**

交付链路：我方生成保护产物 → 获取客户目标环境的设备标识 → 签发设备及期限受限的授权文件 → 客户放入授权目录 → 启动服务。

1. 首版每个实例签发一份授权，限制设备及截止日期；客户编号保存在我方签发台账，不承担校验功能。
2. 桌面或固定服务器优先使用目标环境验证过的机器标识；硬件更换后重新签发。
3. Docker 必须在实际运行容器内采集标识，并验证重建稳定性。最简可采用固定容器 MAC，但它可被复制或伪造，只提供基础限制，不代表强硬件绑定。不要直接绑定随机容器 ID、临时 IP。
4. 续期时用同一产品的构建注册环境生成新文件，客户替换文件并重启。安装包与客户授权分开交付；升级后授权兼容性列入验收。
5. 授权文件不存在、损坏、设备不符或过期时拒绝启动；不允许回退到无授权模式。
6. 授权校验位于受保护核心，客户场景不负责验签或保存签发材料。修改场景文件不使授权失效，不用场景源码哈希锁定授权。平台到期后停止平台能力，客户场景源码及业务数据保留；可独立运行的客户脚本不受本授权强制约束。

授权目录建议放在数据目录下的 `license/`。桌面启动器、容器入口在 Python 启动前设置 `PYARMOR_RKEY` 指向该绝对目录。安装目录和工作目录中不放备用授权，避免搜索顺序选中旧文件。外置授权与查找规则使用 PyArmor 内置能力。[命令参考](https://pyarmor.readthedocs.io/en/latest/reference/man.html#pyarmor-gen-key)

以下只演示工具接口，不是已经适配本仓库的完整构建脚本。`protection-files.txt` 为待生成的文件清单，`TARGET_DEVICE_ID` 为实际设备标识；构建和签发必须使用同一产品注册环境。

```bash
# 在我方构建机保护清单内代码；公开资源由发布脚本另行复制
pyarmor gen --outer --period 1 -r -O release/protected @protection-files.txt

# 为一台设备签发示例授权；日期应使用实际合同截止日期
pyarmor gen key --period 1 -e 2027-09-25 -b "${TARGET_DEVICE_ID}" -O release/customer-license
```

默认外置授权文件名为 `pyarmor.rkey`；续期可替换该文件。[外置授权示例](https://pyarmor.readthedocs.io/en/latest/tutorial/obfuscation.html#using-outer-file-to-store-runtime-key)

**长期运行行为**

保护入口及核心模块，让授权校验由保护运行时触发。另在 `app.py` 主循环调用一个被保护的轻量函数，确保空闲状态下也有受保护函数调用。配置约每小时复查；周期检查依赖受保护函数调用，不能仅在主循环中睡眠。[周期检查说明](https://pyarmor.readthedocs.io/en/latest/reference/man.html#cmdoption-pyarmor-gen-period)

过期错误需要记录清楚原因并终止整个后端，以非零状态退出，不能被现有通用异常处理吞掉后留下渠道线程继续工作。桌面使用现有错误展示机制提示“授权已过期，请更新授权后重启”；容器运维从退出状态和日志识别。续期应提前安排，避免到期中断正在执行的任务。具体检查延迟与退出行为须用打包产物实测。

**构建接入方式**

| 交付方式 | 最小实施方式 |
| --- | --- |
| Docker | 在可信构建环境生成干净发布目录；最终镜像复制受保护核心、runtime 及声明开放的场景源码和资源；客户扩展独立挂载，授权只读挂载 |
| 桌面 | 使用 PyArmor 对现有 `.spec` 的集成，保留原始代码用于依赖分析、用保护结果替换核心模块；`datas` 按分层清单收集，客户扩展从数据目录加载 |

PyArmor 支持现有 `.spec`，但该方式只保护显式列出的脚本和包，不能依赖自动发现覆盖所有动态模块。[打包集成说明](https://pyarmor.readthedocs.io/en/latest/topic/repack.html#using-specfile)

发布过程必须满足以下约束：

- 原始仓库只用于开发和构建分析；最终归档及松散文件中的目标模块均来自保护产物。
- 镜像最终阶段从未写入受保护核心的原始源码，不能先复制再删除；开放场景源码可以正常分发，逐层检查发布镜像。
- `.git`、测试、开发缓存、原始 `.pyc`、真实配置及备份、构建注册材料均不进入发布包。
- 第一版保留现有 Python 版本选择，分别固定并验证 Docker、Windows、macOS 的 Python / PyArmor / PyInstaller 版本组合，按平台构建。
- 初次接入只使用基础保护；现有动态导入、插件重载、反射和资源路径通过后，再考虑增强模式。

**验收条件**

| 检查 | 预期结果 |
| --- | --- |
| 无授权、损坏授权、过期授权、错误设备 | 启动失败，业务端口和定时任务不可用 |
| 有效授权、无外网 | 可启动，允许离线执行的业务正常；外部模型调用仍取决于模型网络 |
| 运行期间跨越到期时间 | 在约定复查窗口内检测并终止后端，不残留可用业务线程 |
| 续期 | 替换授权并重启恢复，业务数据保留 |
| 复制到另一台不同标识的机器 | 原授权不能直接使用 |
| 容器重建 / 客户端升级 | 预定稳定标识和现有授权仍有效 |
| 发布包检查 | 保护清单中的每个文件均受保护，归档、镜像层及松散资源无原始副本 |
| 功能冒烟 | 登录、聊天、工具注册、场景加载、插件加载、定时任务、文件和配置保存正常 |
| 新场景二开 | 增加包含页面、Python 接口和技能的场景，重启后发现并可用，无需修改或重新打包核心 |
| 修改现有场景 | 显式业务覆盖生效，授权不失效；取消覆盖恢复内置场景 |
| 核心升级 | 客户外部场景与数据不被覆盖；v1 接口兼容，或加载时明确报告不兼容版本 |
| 扩展入口 | 沿用登录、租户、权限及写请求校验；扩展清单不能覆盖核心路由或核心包 |
| 二开环境 | 合法开发授权可调试场景；明文代码可调用公开核心接口；客户无需安装 PyArmor 构建工具 |

**能力边界**：这是增加逆向和复制成本的最小方案。客户控制机器时，可以回拨系统时间、伪造标识或攻击运行时；离线方案不能可靠实时撤销已发授权，也不承诺不可破解。第一版不限制用户数、租户数、并发或功能套餐。若未来要求强防复制、防时钟回拨或实时吊销，再引入在线租约校验；不把这些能力算入本次离线方案。

同进程 Python 二开按可信扩展对待，具有进程内代码执行能力。宿主的路由与目录约束用于正常扩展的正确接入，不构成对恶意 Python 代码的沙箱，也不能承诺阻止客户修改进程状态或攻击授权检查。如果以后需要同时开放不可信扩展并加强隔离，应改为独立进程通过受控 API 调用核心；该隔离也不消除客户拥有主机管理权限带来的逆向风险。
