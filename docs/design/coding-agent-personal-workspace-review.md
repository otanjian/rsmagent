# Code 类智能体个人文件夹方案审查与改进建议

日期：2026-10-10。审查对象：[原方案](coding-agent-personal-workspace-plan.md)。状态：静态设计审查及修订建议，尚未实施。

原方案的目录规则、账号身份绑定、远端存储定位和附件先落盘方向合理，但把文件管理、执行沙箱、文件资产管理和存量会话迁移绑定在一次发布中，实施范围偏大。建议采用“统一个人工作区绑定，复用文件面板协议，增加远端文件适配”的方案，将强执行隔离作为独立能力，把旧会话过渡作为明确的发布选择。

建议保留 `<coding_project_dir>/user/<username>/`，以及文件面板、上传和新 Code 会话工作目录一致的原则。优化应减少重复系统与不必要的行为改变，不能退化为只改按钮路径、模型继续向公共目录输出。

## 1 审查发现

| 优先级 | 原方案位置 | 问题及影响 | 建议 |
| --- | --- | --- | --- |
| P1 | 第 7 节及第 12 节 | 把新建用户级执行沙箱作为上线前置，甚至要求沙箱未完成时禁用 Shell，会改变现有外部 Code 接入的能力和交付边界 | 文件接口实施归属与路径校验；运行目录统一到个人目录；沿用已授权的外部执行边界。需要抵抗任意脚本越界时再交付强隔离，不以默认 cwd 冒充隔离 |
| P1 | 第 10 节 | 默认把所有旧会话变为只读并创建新会话，超出原始文件夹需求，可能中断任务和 SAP 场景状态 | 区分兼容期与完整切换；保留旧会话的过渡行为需显式标识，切换方案另行选择，不静默锁定或改绑 |
| P1 | 第 5 节和第 8 节 | 承诺任意文件重命名后 `file_id` 仍可定位，却只说明更新索引。Shell、插件和外部编辑会绕过文件 API，索引与真实文件可能不一致 | 普通文件采用工作区内相对路径和版本；上传附件与交付结果才建立持久引用。没有可靠全量追踪前，不承诺任意重命名后旧链接保持可用 |
| P2 | 第 5 节 | 新建完整浏览器文件 API 和前端分支，但未充分利用已有文件来源适配与 DTO，容易出现普通目录和 Code 目录两套维护逻辑 | 复用现有面板协议和操作形状，后端按来源分派；远端仍需要真实文件服务，但无须另建整套文件管理产品 |
| P2 | 第 3 节和第 8 节 | 目录登记扩展为全局项目注册，并一律禁止跨租户配置同一 P，可能改变既有明确授权的共享项目语义 | 首期只登记个人目录绑定；对同一实际 U 的跨用户、跨租户归属冲突拒绝。不要自动重定义整个项目的租户归属 |
| P1 | 第 7 节及验收表 | 未明确个人文件如何避免进入项目 Git 提交，也未处理 Git 忽略规则对搜索、快照的副作用 | 分开定义公共项目 Git 范围、个人文件列表、个人文件搜索与文件恢复能力，并加入端到端验证 |
| P2 | 第 6 节及发布设计 | 缺少共享个人目录下并发修改、配额和临时载荷的明确策略 | 任务级文件名空间、编辑版本冲突、上传容量限制及可配置临时清理策略纳入首期 |

P1 表示实施前应解决或明确产品决策；P2 表示可以在收敛接口和实现设计时补齐。

沙箱判断有明确仓库依据：[execution-isolation/spec.md 第 66 行](../../openspec/specs/execution-isolation/spec.md#L66)为外部共享 OpenCode 单独规定入口控制边界，不以建设租户或用户运行环境隔离为接入前置。配套 bash 工具使用宿主权限这一事实依然成立，所以推荐修订并不承诺任意脚本绝对不能访问其他路径。

已有来源适配可参考 `channel/web/static/js/fork/project-source.js` 和 `channel/web/fork/handlers/workspace.py` 的 `_panel_source`、`_panel_service`。这些现有实现仍有本机文件假设，不能只替换一个 root 字符串就用于远端，需要补适配器分派，并检查上传 XHR 和预览下载的独立入口。

配套源码的 `packages/core/src/snapshot.ts` 已使用 Location 相对范围采集，并沿用源仓库忽略规则；`ripgrep.ts` 的文件查找使用 `rg --files`。因此应复用已有范围能力并验证忽略行为，而不是先假定所有 Git 与工具模块都需要重写。

## 2 更合适的方案比较

| 方案 | 能否满足个人文件存储 | 主要代价 | 判断 |
| --- | --- | --- | --- |
| 只修改顶部文件按钮 | 只能改变展示，不能保证附件和输出位置 | 最小 | 不采用 |
| 保留会话在 P，仅给模型提示输出到 U | 上传可以落盘，普通相对路径和脚本仍容易落到 P | 较小，但一致性较差 | 不作为完整方案 |
| 新会话运行在 U，保留 P 的项目配置来源，复用文件协议和远端适配 | 可形成上传、处理、结果查看的完整业务闭环 | 平台与 RSMCode 均需有限修改 | 推荐 |
| 原方案全量实施 | 在配套沙箱、索引与迁移均完成后提供更强边界 | 涉及执行平台和文件资产平台建设 | 超出当前第一阶段需要 |
| 每个用户复制项目或创建独立运行实例 | 可提供独立代码环境，仍需附件和文件面板接入 | 代码同步、依赖安装、运行资源和升级成本较高 | 适合以后明确需要独立开发环境的场景 |

推荐方案以当前需求为准：项目提供智能体配置和公共资源，交互形成的业务文件写入 U。若某个 Code 智能体的职责是直接修改 P 下已有源码，则这一职责与“全部业务文件只在 U”存在产品冲突；实施前应为该用途选择独立代码工作副本或明确项目编辑模式，不能无提示改变它的构建和编辑基准。

## 3 推荐修订版的结构

```text
项目配置根 P = 智能体的 coding_project_dir
个人业务根 U = P/user/<身份库中的 username>

顶部文件按钮 ──┐
输入框附件   ──┼── 统一工作区上下文 ── 平台鉴权 ── RSMCode 文件适配 ── U
预览与下载   ──┘

新 Code 会话 Location = U
项目工具和公共配置来源 = P 中原有的可信配置
```

工作区上下文可命名为 `CodingWorkspaceContext`，只负责提供一致的身份与目录答案：

```text
workspace_id
service_id
tenant_id
user_id
username_at_creation
base_project_dir
effective_directory
source = coding_remote
layout_version
```

账号名由服务端查询，浏览器只提交智能体、会话和相对路径。文件操作、会话创建、附件处理复用这一上下文；不能各自根据当前账号或 Agent 配置重新推算不同的根。

新会话绑定 U；已有个人模式会话复用绑定快照。切换智能体配置的项目根只影响新会话。项目根的真实路径由 OpenCode 主机确认，平台不在本机解析或创建同名目录。

## 4 首期数据与接口可以更少

首期新增一张受保护的 `coding_user_workspaces` 绑定表即可，记录工作区上下文和准备状态。以服务、租户、规范项目路径、用户 ID 取得绑定，再对服务和规范个人路径建立唯一占用约束；同一个 U 不能被另一个租户或用户自动认领。若发现身份冲突，应要求调整项目配置或显式处理旧数据。

会话关联表新增 `workspace_id` 和布局模式，原有 `project_dir` 仍保存实际创建远端会话时使用的目录。项目根和账号快照从不可变的绑定记录读取；项目改变时创建新绑定，不修改历史绑定。这可以避免独立项目表以及多处重复的目录版本字段。

浏览器尽量复用现有 `/api/workspace/*` 的操作和响应形状，后端 fork handler 根据已经授权的会话选择 `server`、`desktop` 或 `coding_remote`。新增的范围集中在：工作区准备、远端传输适配以及 coding 附件准入。

复用协议不代表沿用普通 Agent 的路径鉴权：coding 来源必须独立解析 U。既有 `abs_path`、平台 `/api/file?path=...`、系统文件 fallback 和本机 `os.path` 逻辑都不能直接用于远端文件。上传 XHR、下载 URL、预览、回收站和文本编辑必须一并进入来源分派。

在现有 RSMCode 服务内增加受服务认证保护的目录准备和文件操作扩展，复用已有服务端连接认证与版本检查；浏览器继续只访问平台。无需为了本次功能先引入独立常驻文件服务进程和逐操作签名票据系统。远端接口仍只能接收已登记的工作区及相对路径，不能开放任意绝对路径读写。

文件列表直接读取 U，不以全量数据库索引作为可见性前提。普通文件的引用为 `workspace_id + relative_path + version`，路径仍需每次鉴权。附件和结果可以复用消息元数据的载荷存储扩展来源描述；现有桌面来源协议不可伪装成 coding 来源，也不能未经协议版本验证直接复用桌面字段。

首期接受清晰的链接语义：文件被删除或改名时，旧引用显示不存在；内容被替换时显示版本已变化，不能悄悄返回同名新文件。需要长期不变的交付结果时，为该结果单独保存不可变副本，副本仍在 U 内，而非为所有文件建设自动追踪系统。

## 5 文件落盘和执行范围

目录保留 `uploads`、`outputs`、`work`。按真实的平台会话 ID 和已有的消息或执行 ID 分组，避免再引入一套含义不明的任务身份；没有合适执行 ID 时才生成文件操作 ID。

所有对话附件先持久化再准入消息，图片与 PDF 可从持久化文件生成模型所需内容；失败时保留输入框草稿，不带着缺失附件启动任务。面板选择当前子目录上传时尊重用户选择，不再同时复制一份到默认 uploads。

新会话的文件工具和命令默认工作目录为 U；输入、输出和中间目录作为本次调用上下文传给执行器。不能修改共享进程的全局 `cwd` 或全局环境变量，否则并发会话可能把文件写入另一任务目录。

平台文件 API 和可控的文件工具实施范围检查，拒绝伪造账号、路径穿越及链接跳转；已支持的外部目录权限可按个人业务模式收紧，但可信项目配置读取仍应可用。SAP 工具安装继续在 P，场景绑定校验拆分项目根与会话目录，这部分原方案的改动应保留。

Shell、插件及远端 MCP 的执行权限沿用已有外部部署边界。首期对业务链路的承诺是：平台上传、已接入的生成与导出入口持久化到 U，默认执行在 U，交付文件必须经 U 内的文件引用返回。对任意第三方脚本或远端服务擅自向其他路径写入，不作 OS 级阻断承诺。若要求这种绝对约束，推荐方案需要增加独立沙箱交付，不能把它作为已经实现的能力。

保持这一边界意味着首期的两个账号测试分别验证文件 API、面板和附件的归属隔离，以及实际业务任务的落点一致；不能用这些用例宣称任意脚本访问其他目录也已被隔离。

## 6 补齐 Git 搜索和并发规则

P 如果是 Git 仓库，个人交互文件应从公共项目的普通提交范围排除，防止一个账号的上传文件被公共代码提交带走。实施前先检查现有 `user/` 是否包含已跟踪源码或其他用途；有冲突时报告，不能直接改忽略规则或删除既有内容。仅对符合布局条件的未跟踪业务树建立适当排除策略。

个人文件面板直接按 U 枚举，不以 Git 是否跟踪决定可见性；`@文件` 和个人文件搜索使用 U 范围的查找入口，并明确其忽略策略。公共项目提交忽略个人文件，不应导致用户找不到刚上传的附件。禁用父级 Git 忽略时仍要保留 U 边界和缓存、临时区过滤。

现有 Git 快照会考虑忽略规则，且对未跟踪文件存在大小限制，因此不能把它当作个人文件的完整备份或保证所有报告可撤销。首期保留项目已有代码差异能力；个人目录文件的编辑冲突用版本检查处理，需要恢复的用户删除进入个人回收站。若还要求个人生成文件的逐版本撤销，再追加独立设计，不能通过删除 Git 忽略来让个人资料进入公共项目。

同一账号多会话可并发运行，每次生成使用会话及消息或执行子目录。面板编辑和已接入的文件工具对同一文件进行版本检查；冲突提示重新读取，不自动覆盖。Shell 修改已有文件仍受外部执行语义约束，不能声称版本检查能拦住所有宿主进程。

上传大小、并发数、个人容量和未完成载荷保留期统一由服务端配置并下发。完整附件即使尚未发送也保留；仅中断上传和明确标记的临时载荷自动清理。代码目录、正式结果和输入附件不因普通临时清理被移除。

## 7 旧会话需要明确的过渡选择

已检查的 V2 Session 接口暴露了创建、模型切换、提示提交等操作，未提供可直接使用的 Location 原地迁移接口。这不足以断言整个部署不可能迁移，但不能把“更新平台的 project_dir”当成可用迁移方案。

推荐先区分两种发布目标：

| 发布目标 | 旧会话处理 | 能够声明的范围 |
| --- | --- | --- |
| 兼容试运行 | 新会话使用个人目录；旧会话保持现有位置并显示旧模式说明，提供进入个人会话的操作 | 完成新会话和个人文件入口的试运行，尚未覆盖全部存量会话 |
| 全部交互切换完成 | 停止旧任务后，逐个切换为个人会话，保留原历史入口和关联；或者先实现并验证远端原地迁移 | 切换后的所有交互统一使用个人目录 |

第二种才满足对存量与新交互一并生效的完整口径。兼容试运行不应被包装为原需求已经全部完成；另一方面，升级程序也不应未经明确发布选择就把旧会话全部变成只读。

旧文件不必与目录入口改造同步批量迁移。先保留现有授权链接；用户选择带入个人会话的附件，仅按可信归属复制，并记录来源。无法确认归属的文件不自动纳入个人目录。若需要批量整理，再以只读预检和迁移清单实施。

## 8 实施前先完成一个真实验证闭环

先用一个临时测试项目和两个测试账号验证核心路径，再扩展 UI 操作和迁移工具：

1. 远端创建 `P/user/<username>`，重复打开得到同一绑定。
2. 在 U 创建 Code 会话，确认真实文件工具及命令的默认目录。
3. 确认原项目技能、MCP 与 SAP 场景工具可正常加载和调用。
4. 从面板及 iframe 输入框各上传一份文件，确认原件确实在远端 U。
5. 生成一个结果，文件面板、@引用和下载都指向同一份内容。
6. 验证 Git 排除后个人搜索仍能看到文件；验证无 Git 项目也正常。
7. 同时打开两个账号及同账号两个会话，检查目录、消息、上传、事件及取消操作不会串到别的上下文。
8. 选择并验证旧会话过渡路径，然后明确此次发布覆盖范围。

如果技能发现或 SAP 在 U 无法工作，应先补有限的配置来源适配；如果需要大幅重构 OpenCode 的配置、快照或执行器，再重新评估范围和路线。这样比在核心链路未验证前同时开发文件索引、全量迁移和沙箱更容易判断成本与风险。

本次保留原方案不变，审查建议尚未替换其行为契约。业务代码、运行环境、账号和历史文件均未修改；上述结论来自仓库规范与本地源码审查，运行兼容性仍需通过该验证闭环确认。
