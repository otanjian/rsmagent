The Web Console is 容大AI's default channel. It runs automatically once started, letting you chat with the Agent in a browser and manage models, skills, memory, channels, and other configuration online.

## Configuration

```json
{
  "channel_type": "web",
  "web_host": "0.0.0.0",
  "web_port": 9899,
  "identity_mode": "database",
  "enable_thinking": false
}
```

| Parameter | Description | Default |
| --- | --- | --- |
| `channel_type` | Set to `web` | `web` |
| `web_host` | Web service listen address. Defaults to `127.0.0.1` (local only); set to `0.0.0.0` for public access | `""` |
| `web_port` | Web service listen port | `9899` |
| `identity_mode` | Identity mode. Only `database` is supported; explicit `legacy` refuses to start | `"database"` |
| `web_session_expire_days` | Login session validity in days | `30` |
| `web_file_serve_root` | Root directory the web console can directly read/send files from. Defaults to the user home dir and agent workspace only; set to `/` to allow the whole filesystem | `"~"` |
| `enable_thinking` | Whether to enable deep thinking mode | `false` |

Access requires a database account (username + password). On first start the platform admin is bootstrapped and the one-time initial password is printed to the console (and a protected file). The login session is kept for 30 days by default via an HttpOnly `cow_session` cookie. Desktop and other programmatic clients use the same session value as `Authorization: Bearer`. There is no shared `web_password`.

### Instance Branding

The Web Console can carry your own branding: the brand name, a short logo
description, and a custom logo (plus a derived browser favicon). Branding is
instance-scoped (single Web deploy), untouched by the desktop client or the
documentation site.

Open **System settings → Branding** after logging in to edit and save. No
separate feature switch is required; the old `branding_enabled` setting is ignored.

- **Scope**: Instance-wide. Brand data lives under `<data_root>/branding/`; it is
  never written into `config.json`.
- **Authorization**: Brand writes require a platform administrator with
  `branding.manage`. Shared passwords and anonymous access cannot authorize edits.
- **API authentication**: Writes accept verified Authorization Bearer (same
  `cow_session` value) or login cookies with origin/CSRF checks. Cookie clients
  obtain `csrf_token` from `/api/branding` and send it as `X-Branding-CSRF` on
  same-origin save/reset requests. The UI does this automatically. Query-token
  auth is rejected.
- **Damaged settings**: Missing or damaged published metadata is a read-only recovery
  preview. An explicit restore preserves the original in `branding/corrupt/` and
  allocates a new revision. Retain the `.revision.json` ledger in the brand directory.
- **Fields / limits**: brand name `1–32` chars, logo description `0–100` chars
  (single line, no control characters), image `PNG / JPG / WebP`, `≤ 2 MiB`,
  `32–4096` px per side, `≤ 16,000,000` px total, no animated images. Uploaded
  images are normalized (EXIF applied, metadata stripped) to a safe PNG and a
  `32×32` favicon is derived.
- **Publish model**: Saving or "Restore all defaults" publishes an atomic new
  revision. Concurrent edits from another tab/browser are detected and reported
  as a conflict rather than silently overwritten.
- **Restore defaults**: The "Restore all defaults" action resets name,
  description, logo and favicon to the built-in defaults and raises the
  revision, after a confirmation prompt.
- **Backup / rollback**: The `cow backup` command stores the current branded
  snapshot and its referenced images; `cow restore` re-publishes them into the
  target data root under a fresh revision. An archive without a branding segment
  never deletes an existing brand — on a fresh instance it falls back to the
  built-in defaults. To roll back an application version, back up the brand
  directory first; old code does not
  consume the new branding data.

<Note>
  The logo served on the login page and sidebar is a public asset, so only
  include content you are comfortable showing to unauthenticated visitors.
</Note>

After starting the project, visit:

- Server: `http://<server-ip>:9899`

## OpenAI-Compatible API

Create a service-account API key (`sak_…`) in the identity console to enable
`POST /v1/chat/completions`. Pass it as `Authorization: Bearer`. This is
independent from Web Console login sessions and replaces the retired
`external_api_token` setting.

The first release accepts text messages and uses 容大AI's configured Agent and
model. The request `model` is required for OpenAI client compatibility and is
echoed in the response; it does not select a 容大AI model. The latest non-empty
user message is submitted to the Agent. Set `conversation_id`, or `user` as a
fallback, to reuse a stable 容大AI session across requests. Requests without
either field use an isolated session.

Non-streaming request:

```bash
curl http://localhost:9899/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "cowagent",
    "conversation_id": "example-conversation",
    "messages": [{"role": "user", "content": "Summarize this workspace."}]
  }'
```

The standard response is returned in `choices[0].message.content`. 容大AI adds
`reasoning_content` and `tool_trace` to the message when those traces are
available.

Streaming request:

```bash
curl -N http://localhost:9899/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "cowagent",
    "stream": true,
    "user": "example-user",
    "messages": [{"role": "user", "content": "Inspect the workspace."}]
  }'
```

Streaming content uses standard `chat.completion.chunk` objects and
`choices[0].delta.content`. Reasoning uses the additive
`choices[0].delta.reasoning_content` field. Reasoning and tool-process chunks
also include a top-level `cow_event` object. The stream ends with `data: [DONE]`.

OpenAI Python clients can use the endpoint by setting the base URL:

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:9899/v1",
    api_key="sak_your-service-account-key",
)
response = client.chat.completions.create(
    model="cowagent",
    messages=[{"role": "user", "content": "Hello from Python."}],
    extra_body={"conversation_id": "python-example"},
)
print(response.choices[0].message.content)
```

The API returns `400` for invalid requests, `401` for invalid or revoked
credentials, and `503` when the identity store is unavailable. Non-streaming Agent failures
return a structured JSON `500` response.

For streaming requests, 容大AI waits up to 30 seconds for the Agent to produce
the first event. An Agent failure before the first event returns a structured
JSON `500` response because the SSE response has not started. If no first event
arrives within 30 seconds, the API cancels only that request's in-flight Agent and
returns the same JSON `500` shape with error code `timeout`.

After the SSE response has started, its HTTP status can no longer change.
A later Agent failure is therefore emitted as a `cow_event.type=error` chunk,
followed by a terminal chunk with `finish_reason=error` and then
`data: [DONE]`.

## Features

### Account Menu

After signing in with an individual account, the card
at the bottom left of the sidebar shows an avatar, your display name (or
username), and `@username`. It stays visible as you scroll the navigation, and
switching tenants keeps the same account identity.

Click the card to open its six-entry menu upward. Each item opens without
leaving the current page:

- **Personal profile** — a read-only drawer showing your name, login username,
  platform-identity flag, and the current tenant's member name, roles,
  department and position. Global account and tenant-member fields are shown
  separately; the member name never overwrites the account card. Empty values
  show **Not set**, and a user with no tenant shows **Not a member of any
  tenant**. When the profile cannot be read, a retry is offered while keeping
  your confirmed login and the password/logout entries.
- **Change password** — a modal with current, new and confirm password fields.
  On success the session is revoked and you are asked to log in again; a note
  explains that other logged-in sessions also expire. If your account is
  flagged to change password (first login / temporary password), the same form
  is shown as a gate before tenant selection and business data load, and you
  can only finish the change or log out.
- **Interface preferences** — light/dark theme and Simplified/Traditional
  Chinese/English, applied locally in the current browser only and kept in
  sync with the header toggle. A personal choice never writes the instance
  default; if browser storage is unavailable the change applies to this page
  and the limitation is shown.
- **Switch tenant** — lists only the tenants you are an effective member of and
  marks the current one. With zero tenants it reports **Not a member of any
  tenant**; with one it shows the current name; with several you can choose.
  Switching reloads the page and the new page validates the target before
  committing, so cancelling leaves the old page unchanged and an invalid
  target never silently enters another tenant.
- **About current brand** — shows the current brand and version and opens the
  original release-notes link.
- **Log out** — ends the current login session and returns to the login page,
  with single-flight submission and a retry if logout is not confirmed.

Press Escape or click outside to close the menu; the drawer/modal closes return
focus to the card trigger. On mobile and in short viewports the entries stay
reachable and the hidden menu never receives focus.

If the initial login check fails, select **Check again** on the login screen.
If account information becomes unavailable inside the console, open the card
and select **Check again**; your current page and draft are preserved. When your
login is confirmed but your profile cannot be displayed, **Log out** remains
available. If you see **Logout not confirmed**, use **Retry logout** or
**Check again** to recover.

### Chat Interface

Supports streaming output with real-time display of the Agent's reasoning process and tool calls, providing intuitive observation of the Agent's decision-making. Deep thinking can be toggled via configuration or the "Agent Configuration" switch in the console.

#### Multi-Session Management

The chat interface supports multi-session management. All session records are persistently stored in the database:

- **Session List**: Open **Workbench → Session History** to view all accessible past sessions, with scroll-to-load support and project/date grouping
- **Search Sessions**: Enter a title keyword in the search box above the list to search all accessible session history, including sessions not yet loaded. Chinese and English text are supported, and letter case is ignored. Clear the search box to return to the full list
- **AI-Generated Titles**: After the first exchange in a new session, the model is automatically called to generate a short summary title
- **New Session**: Click the "New Chat" button at the top of the session history page or the `+` button in the input area to create a new session
- **Session Actions**: Click the **⋯** button on a session item to pin or unpin, rename, or delete it. Deleting requires confirmation and permanently removes the session and all its messages
- **Clear Context**: Click the clear button in the input area to insert a divider in the current session. Messages above the divider are still displayed but no longer included as context for the model
- **Workspace / Model**: Set a workspace and model for the current session below the input box. When you work across several projects, past sessions are grouped by project automatically. See [Architecture - Project Workspace](/intro/architecture#project-workspace)

#### Permission Modes

What the Agent may reach into files and commands is governed by the permission mode: read-only, workspace-write, or full-access. On a single-tenant install you pick the global default in **Settings → Security** and new sessions inherit it. On a multi-tenant install the setting is read-only and execution is decided by the caller's **role resource authorization** — which tools and resources a role may use is assigned by an administrator, so the conversation itself cannot widen it. When a tool call is blocked the console still explains why, but there is no in-conversation switch to raise the permission.

#### Files and the Workspace Panel

The console file panel (workspace tree, search, preview, download and upload) and the file interfaces share one ownership rule: *whose* file it is comes from the path itself, not from the Agent or tenant a request names.

- **A shared Agent stores files per account**: when several members share one tenant Agent, files uploaded or generated through the platform land under that Agent's `user/<account-id>/` (`uploads` / `outputs` / `work`). Expanding `user` lists only your own folder, and asking for a colleague's folder is refused rather than answered with an empty list — an empty list would confirm that the path exists.
- **Shared material is unchanged**: files outside `user/` in an Agent workspace (skills, knowledge, documents) keep their previous sharing semantics for members of the same tenant.
- **Previews and downloads belong to the owner**: files under `user/<account-id>/` are checked against the *current* identity when they are opened, and their responses are marked `private, no-store`. Forwarding a preview link does not grant access, and an old link stops working when the identity does not qualify.
- **No implicit publishing**: a private file is not copied to the public web directory just because a tool sends it or the platform returns it.
- **Administrators are no exception**: neither platform nor tenant administrators obtain the contents or file names of another member's `user/<account-id>/` files; governance pages expose only counts and usage metadata.
- **Existing boundaries are unchanged**: the rules for private Agents, cross-tenant access and sensitive system paths are not relaxed.

<Note>
  This is file isolation **between application accounts**, not an execution sandbox. Python / Shell / skills / coding inside a shared Agent still run as the Agent workspace, so a script that reads the disk directly stays outside what this rule guarantees (unchanged from before).
</Note>

#### Agents

"Agents" has two entry points: **Management → Agent Configuration** (management mode) and **Workbench → Agents** (usage mode).

- **Workbench → Agents (usage page)**: shows a read-only card gallery of **saved and enabled** Agents, marking the default one and listing a `Start chat` action per card. Clicking a card opens a new chat bound to that Agent: it shows the Agent's name and avatar, focuses the input, and uses that Agent's default workspace without inheriting other project/session settings. The entry is only offered when the Agent can run in the current mode. The `view=workbench` read is a whitelisted projection and never exposes workspace paths, channel instances, core files, or other management data.

- **Management → Agent Configuration (management mode)**: fully editable CRUD for Agents (name, responsibilities, avatar, model, knowledge base, core files, etc.), backed by the same data source as Workbench → Agents. Here you can edit; the usage page is read-only. Concurrent edits are detected via the roster revision and surfaced as a conflict rather than silently overwritten.

### Todos and Delegation

**Workbench → Todos** is a personal todo list with create, edit, start/complete/cancel, reopen, and a processing history. A todo always belongs to whoever created it: delegating moves only the **current handler**, never the ownership.

- **Two sections**: "My todos" lists what you are currently handling; "Delegated by me" lists what you created and somebody else is handling now. The counts and totals are kept separate, and only "My todos" feeds the top-bar badge.
- **Assign**: hand one of your own todos to a colleague in the same tenant. It leaves "My todos" and appears under "Delegated by me".
- **Transfer / Reject**: the current handler can pass the item to a third person (multi-hop is supported) or reject it back to the creator. Rejecting is not assigning: use "Reject" to hand it back to the creator.
- **Recall**: the creator can always take the item back, with no approval from the handler.
- **Who may act**: only the current handler can edit the content, complete it, or cancel it. While an item is delegated, the creator can still read it and recall it, but cannot process it on the handler's behalf. Delegating never changes the due date, category, priority, or notes.
- **Status boundary**: only an open (pending) item can be delegated. A completed or cancelled item must be reopened first.
- **Visibility**: delegation stays inside the tenant and only reaches active members. Cross-tenant targets are always refused, and "not a member of this tenant" returns the same answer as "does not exist", so it cannot be used to probe whether an account exists in another tenant.
- **Trail**: assign, transfer, recall, and reject all append to the processing history with the actor, the receiver, and the time, and are written to the audit log (successful actions as `todo.assign` / `todo.transfer` / `todo.recall` / `todo.reject`, refusals as `result=denied`).
- **Permission**: delegation is gated by "Delegate todos" (`todo.assign`), granted to Member and Tenant Admin by default and adjustable under Management → Roles. Without it the UI withholds the receiver picker and says so, while every other todo action keeps working. The receiver list returns only the username and display name of delegatable members in the same tenant — never roles, departments, or contact details.
- **In conversation**: you can ask the Agent to assign a todo for you, but only when you **name the receiver explicitly in that turn**. The Agent will not infer a person from the participants of the conversation, the member directory, or history, and will not assign to several people at once.
