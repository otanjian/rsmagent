## Purpose

规定控制台前端的模块化布局与 fork 定制交付方式：fork 定制以独立的覆盖模块承载而非原地改写上游视图模块、两侧都改过的区域逐处裁定并留痕、fork 模块记录上游来源指纹以支持漂移检测，以及单体脚本/样式表退役的前置条件与可执行校验。

## ADDED Requirements

### Requirement: 前端采用模块化布局且 fork 定制以覆盖模块交付

控制台前端 SHALL 采用与上游同构的模块化布局：核心能力、视图与对话分别位于各自模块目录，样式按组件拆分，MUST NOT 依赖单一巨型脚本或单一巨型样式表承载全部前端逻辑与 fork 定制。

fork 前端定制（外观、身份管理、待办、场景工作台、外部连接、品牌等）SHALL 以 `static/js/fork/<上游子路径>`、`static/css/fork/<上游子路径>` 下的独立模块交付，经服务端覆盖映射把 `assets/js|css/**` 引用替换为 fork 版本后装载；MUST NOT 原地改写上游视图模块以插入 fork 专属逻辑。上游对视图交互的改进 SHALL 在 fork 侧继续生效。

fork 定制 MUST NOT 以「在上游模块之后装载并重新声明同名顶层符号」实现：前端是无打包器的共享全局作用域经典脚本，同一顶层名在两处声明即整体解析失败、页面不可用。

#### Scenario: fork 定制以独立模块交付

- **WHEN** 审查任一 fork 前端定制（外观、身份管理、待办、场景工作台、外部连接）
- **THEN** 其实现位于 `static/js/fork/**` 或 `static/css/fork/**` 的独立模块，经覆盖映射装载到对应视图，上游视图模块内不含该定制的原地实现

#### Scenario: 上游视图改进在 fork 侧生效

- **WHEN** 上游修改某视图的交互或渲染行为并合入
- **THEN** fork 侧该视图采用上游新行为，fork 定制仍在覆盖模块处生效，不因 fork 模块而回退上游改进

#### Scenario: 移除 fork 片段仅回退展示

- **WHEN** 停用或移除某 fork 前端片段模块
- **THEN** 对应定制不再展示，上游视图保持可用，且后端授权不因此放宽

#### Scenario: 以之后装载并重名声明的方式叠加被拒绝

- **WHEN** 一次实现把 fork 定制作为在上游模块之后加载、且重新声明上游顶层 `const`/`let` 的脚本
- **THEN** 该实现被判定为不通过，不得以「文件未改动上游模块」为由接受

### Requirement: 前端定制迁移逐处裁定并留痕

两侧都改过同一区域的冲突区域（fork 的定制与上游对该区域的重构），系统 SHALL 逐处记录裁定为 `fork` / `upstream` / `merged` 及理由后再生效，MUST NOT 以整函数照抄 fork 版本或整体取上游一侧的方式处置。

裁定 SHALL 检查上游在该区域的改动是否携带功能或安全修复；MUST NOT 因「fork 版本可用」而默认覆盖。裁定结果 SHALL 并入移植器输入并可重跑，产出 SHALL 以独立校验工具复核「fork 独有行零未交代」，该校验 MUST NOT 依赖移植器自述。

#### Scenario: 两侧同区域冲突被逐处裁定

- **WHEN** 某区域 fork 有定制且上游在同一区域有改动
- **THEN** 存在一条裁定记录，给出 `fork` / `upstream` / `merged`、理由，以及被否决一侧的处置说明

#### Scenario: 判定整函数照抄被拒绝

- **WHEN** 一次处置以 fork 的整个函数替换上游同名函数，从而丢弃上游在该函数内的改动
- **THEN** 该处置被判定为不通过，需补出逐处裁定记录

#### Scenario: 校验发现未交代的 fork 独有行

- **WHEN** 移植产出遗漏了 fork 单体中存在的某段独有逻辑，且未出现在裁定清单上
- **THEN** 独立校验失败并指出该行位置，不得以移植器自述的统计通过

#### Scenario: 移植器可重复运行

- **WHEN** 以同一组输入重复运行移植器
- **THEN** 产出逐字节一致，使「是否有内容漂移」可回答

### Requirement: fork 模块的上游来源与漂移可检测

`static/js/fork/manifest.json` SHALL 以 `{fork_path: {upstream_path, upstream_sha256}}` 记录每个 fork 模块的上游来源路径与移植时的内容指纹，并 SHALL 提供可执行门禁：上游来源模块内容变化时门禁失败，并指出需人工重新应用的上游路径。

门禁 MUST NOT 要求 fork 模块与上游模块内容相同（fork 模块本就有意不同），SHALL 只比对登记的上游指纹。

#### Scenario: 上游改动已登记的来源模块

- **WHEN** 上游修改了某 fork 模块登记的上游来源模块
- **THEN** 门禁失败并列出该 fork 模块与上游路径，提示需人工评估重新应用

#### Scenario: 上游未改动已登记的来源

- **WHEN** 上游在两次校验之间未改动任何已登记的上游来源模块
- **THEN** 门禁通过，不产生噪音告警

#### Scenario: 重新应用后更新指纹

- **WHEN** 完成一次上游改动的人工重新应用
- **THEN** 该模块的上游指纹更新为当前上游内容，后续门禁以新基线比对，不再重复告警

#### Scenario: 上游新增视图模块未纳入

- **WHEN** 上游新增一个视图模块而覆盖映射与 manifest 未同步登记
- **THEN** 门禁失败并指出该模块，避免上游新增改进被静默忽略

### Requirement: 单体退役不留兼容层且前置条件可判定

`console.js` 与 `console.css` SHALL 在迁移完成后删除，MUST NOT 保留兼容层或双装载路径。删除的前置条件是本 capability 的裁定记录齐备且独立校验报零未交代；前置条件未满足时，保留单体 SHALL 作为显式基线决策而非默认状态。

装载顺序 SHALL 在上游契约下校验（`tools/check-load-order.mjs`），且全部产出模块 SHALL 通过语法校验。四个装配状态中的「仅缺失可选 UI 扩展」SHALL 仍可组装：缺少 fork 前端模块时上游视图保持可用。

#### Scenario: 前置条件未满足时不删除单体

- **WHEN** 裁定记录仍有未决项或独立校验报出未交代的 fork 独有行
- **THEN** `console.js` / `console.css` 仍在仓库中，且该状态在冲突基线中被登记为显式决策

#### Scenario: 前置条件满足后删除且无兼容层

- **WHEN** 前置条件满足并完成删除
- **THEN** 仓库中不存在 `console.js` / `console.css`，也不存在指向它们的兼容层、条件装载或降级分支

#### Scenario: 装载顺序与语法校验通过

- **WHEN** 以覆盖映射装载 fork 前端并运行 `tools/check-load-order.mjs` 与全量 `node --check`
- **THEN** 两者通过，`boot.js` 仍最后加载，且无重复顶层声明

#### Scenario: 缺少 fork 前端模块时保持上游形态

- **WHEN** 以独立上游装配运行且未加载任何 fork 前端模块
- **THEN** 上游视图保持可用，不因缺失 fork 模块而白屏或报错

### Requirement: 被延后的上游前端增量不留未交代的活跃消费方

每一条被延后的上游前端增量（含其依赖的未路由接口）SHALL 在 `evidence/deferred-upstream-frontend.md` 逐条登记，并在交付前给出「已随本 change 生效」或「显式转交下一轮同步」的结论。若某未交付能力存在**活跃消费方**（独立前端或客户端已调用该能力依赖的接口），该消费方 SHALL 被登记并说明受影响界面与失败形态，且 SHALL 在本 change 内二选一收口：交付其后端路由与授权判定，或降级/隐藏该入口。MUST NOT 以「该能力属拆分后前端」为由留空。

桌面渲染进程（`desktop/src/renderer/**`）是独立前端：它按上游版本合并、不装载 Web 控制台前端，因此会在控制台仍保留单体时成为未路由接口的活跃消费方——此情形适用本条要求，而非「不在本表范围」。

#### Scenario: 未路由接口存在活跃消费方

- **WHEN** 某被延后能力依赖的接口从未注册，而某独立前端已调用它
- **THEN** 登记该消费方与受影响界面、失败形态（空态/报错），并在本 change 内完成「补路由与授权」或「降级入口」之一，附两侧验证证据

#### Scenario: 以「属拆分后前端」为由留空被拒绝

- **WHEN** 一次处置把存在活跃消费方的未路由接口仅标注为「该能力属拆分后前端」而不给出消费方与收口结论
- **THEN** 该处置被判定为不通过，需补出消费方清单与逐条收口结果
