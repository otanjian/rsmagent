# 07 — fork frontend divergence, measured against upstream's split

Phase 3 task 4.1. Upstream deleted the fork's two frontend monoliths and split
them by concern:

| deleted | fork size | upstream replacement |
|---|---|---|
| `static/js/console.js` | 20184 lines / 932 KB | `static/js/{core,chat,views}/*.js` (33 files) |
| `static/css/console.css` | 6048 lines / 197 KB | `static/css/*.css` (8 files) |

Both are `modify/delete` conflicts: the fork modified a file upstream removed, so
there is no common file to merge. Porting the fork's customization onto upstream's
layout needs to know *what* the customization is and *which upstream module now
owns each customized region*. This records both, generated by
`scripts/migration/analyze_frontend_divergence.py`; raw output in
`07-frontend-divergence.txt`, per-hunk detail in `frontend_divergence.json`.

## Method

1. Take the fork's copy and the merge base's copy of each file (upstream's new
   files share no filename, so the base is the only valid reference).
2. Diff them with whitespace collapsed and blank lines dropped. An exact-line
   diff is useless here: it reports 2 hunks and 18671 added lines for
   `console.js`, because the fork reformats blanks/indentation throughout. The
   normalized diff reports the real change set.
3. Index upstream's modules by normalized line, keeping only *distinctive* lines
   (length ≥ 8, carried by ≤ 3 modules). Short structural lines (`}`, `});`)
   appear in every module and would attribute everything to everything — the
   first run of this analysis did exactly that and produced a uniform
   "≈7000 lines per module" for all 36 modules, which is meaningless.
4. Map every base line to the module carrying it, filling gaps from the
   preceding anchor, then attribute each changed hunk to the module(s) owning
   the base lines it replaces.

Result: **100 % of base lines map to a module** (14413/14413 JS, 3671/3671 CSS).

### Caveat on the numbers

A hunk that *replaces* base lines is attributed correctly. A hunk that *inserts*
with no base lines of its own inherits the preceding anchor, so a fork block
appended at the end of `console.js` is attributed to whichever module owns the
file's tail. The 894 added lines attributed to `js/core/version.js` are mostly
this effect (fork branding that was appended, not a redesign of `version.js`).
For the port this is harmless — appended fork code becomes fork-only modules
rather than a port into an upstream module — and the portability measure below
flags exactly those hunks as non-anchorable, which is the correct classification.

## Scope of customization

| | statements (base → fork) | hunks | added | removed | similarity |
|---|---|---|---|---|---|
| `console.js` | 13313 → 18679 | 365 | 7832 | 2061 | 0.71 |
| `console.css` | 3514 → 5829 | 79 | 2606 | 229 | 0.71 |

The fork's frontend is ~60 % unchanged upstream code and ~40 % fork work. That
is the real work item for Phase 3 — it is the same order of magnitude as the
backend (290 symbols) but with a structural difference that decides the port
strategy: **there are no separable symbols to slice out.** The customizations are
interleaved edits inside existing functions.

## Portability: can a tool re-anchor these hunks?

A port needs a landing site. For each hunk, the three base lines before it and
the three after it must still exist, in order, in whichever upstream module
inherited that region; if they do, a tool can locate the offset and apply the
hunk. If upstream rewrote the surrounding code, the hunk must be re-expressed by
hand.

| | hunks | re-anchorable | needs hand port | ratio |
|---|---|---|---|---|
| `console.js` | 365 | 258 | 107 | 70.7 % |
| `console.css` | 79 | 67 | 12 | 84.8 % |

Worst modules for hand porting: `views/sessions.js` (21), `views/agents.js` (20),
`core/nav.js` (12), `views/config.js` (7), `core/auth.js` (7),
`chat/new-chat.js` (5), `core/i18n.js` (4), `views/knowledge.js` (4), and
`css/sessions.css` (7), `css/agents.js` (3), `css/base.css` (2).

**Conclusion: a tool-assisted port is viable.** ~71 % of the JS and ~85 % of the
CSS can be re-anchored mechanically, leaving ~119 hunks for hand porting. That
reframes Phase 3 from "rewrite 10 000 lines" to "run a porting pass, then
hand-port ~119 hunks and review the result" — a bounded task, comparable to the
backend phase.
