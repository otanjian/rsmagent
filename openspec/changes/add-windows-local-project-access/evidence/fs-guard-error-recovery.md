# project-fs-guard 错误与恢复说明

本文件说明写入入口 `project-fs-guard` 的错误词汇、每种错误之后**磁盘上到底发生了什么**、以及调用方可以安全地做什么。它对应变更 `add-windows-local-project-access` 的任务 2.4（"更新错误/恢复说明"）。

**读法约定**：下表"磁盘状态"一列描述的是**实测行为**，不是设计意图。凡未实测的组合都在最后一节列出。

## 1. 为什么这张表重要

写入路径会在目标文件所在目录里创建一个**暂存文件**，然后把它发布到目标上（见 `fs-guard-platform-support.md` 与设计 D3）。因此"这次调用失败了"并不足以让调用方判断磁盘状态：失败可能发生在**暂存之前**、**暂存之后但发布之前**、以及**发布期间**。这三种情况下调用方的正确动作完全不同——第一种可以直接重试，第二种也可以，第三种**不能**重试，因为改写可能已经生效。

所以错误码不是给用户看的文字，而是**恢复契约**。

## 2. 错误码与恢复动作

| 错误码 | 何时返回 | 磁盘状态（实测） | 调用方可安全执行 |
|---|---|---|---|
| `invalid_params` | 路径缺失/非法；内容超过 48 KiB 上限；`edit` 的 `old_string` 为空或**未找到**；`edit` 有多个匹配但未给 `replace_all`；父目录不存在；未知参数（含 `cwd`/`root_path`/`absolute_path`/`env`/`module`/`argv_path`） | **目标与暂存都未被创建或修改** | 修正参数后重试 |
| `path_outside_root` | 路径含 `..`、绝对路径、盘符/UNC、分隔符混入 | **无任何变化** | 不要重试；路径本身不被接受 |
| `rejected_entry` | 目标是符号链接/reparse point、设备、`nlink>1`，或父目录在打开后被替换 | **无任何变化**，且根外无文件产生 | 不要重试；请用户确认目标 |
| `no_such_grant` | grant 不存在、已关闭或已撤销 | **无任何变化** | 重新选择项目根 |
| `unsupported` | 平台/卷不支持（如网络盘），或清理无法验证 | **无任何变化**；若已暂存则残留（见 §4） | 不要重试；记录原因 |
| `file_changed` | 覆盖/编辑时 `expected_version` 缺失、格式非法或与当前不符 | **无任何变化**——版本检查发生在暂存**之前** | 重新 `read` 后再改；**不要**强行重试 |
| `invalid_frame` / `frame_too_large` | 帧无法解析或超过 64 KiB | **无任何变化**；`frame_too_large` 后流已失步，helper 退出 | 重新连接 helper |
| `cancelled` | 请求被后续 `cancel` 中止 | 读取类：无变化。写入类：见 §3 | 见 §3 |
| `io_error` | 文件系统错误 | **不确定**——可能发生在暂存前、发布前或发布中 | 见 §3：**不要自动重试** |
| `internal` | helper 内部缺陷 | **不确定**，同 `io_error` | 同 `io_error`，并记录诊断 |
| `unknown_op` | 操作不在允许表内（只读入口收到 `write`/`edit`/`mkdir` 也会得到这个） | **无任何变化** | 不要重试 |

**关键区分**：`file_changed` 是**冲突**，不是错误参数——调用方的文件视图过期了。它保证"一个字节都没写"，所以恢复动作是"重新读取"而不是"重试写入"。

## 3. 不确定结果（`io_error` / `internal`）的处理

这是唯一需要调用方谨慎的类别。它的含义是：**helper 无法判断目标文件是被替换了还是没被替换**。

helper 在此时的行为是刻意的：

- **不删除暂存文件。** 发布可能已经生效，暂存内容可能是新内容的唯一副本；清掉它可能销毁用户刚写下的数据。
- **返回错误，而不是返回成功。** 把"可能成功了"报成成功，会让调用方在后续版本检查里得到一个莫名其妙的 `file_changed`。

调用方应当：

1. **不要重放同一请求。** 合同规定的 `unknown outcome 待确认不重写`。
2. 重新 `read` 目标文件，与预期内容比较，据此判定是否已生效。
3. 若残留了 `.fsguard-tmp-*` 文件（见 §4），在确认目标内容正确后再手动清理；**不要**在确认之前清理。

**未见到的行为、因而不得声称的**：目前没有把"暂存残留"作为结构化字段返回给调用方（见 §5）。

## 4. 暂存对象：可以清理什么，绝不可以清理什么

暂存文件名为 `.fsguard-tmp-<hex>-<n>`，创建在**目标所在目录**内。设计 D3 的清理规则是硬约束：

> 用户原文件禁止作为清理目标，清理只根据本任务已记录的暂存对象身份执行，绝不通过 dirname 向上推算根目录。

实现上由 `src/temp.rs` 的注册表落实，三条性质使这条规则**成立而非仅仅被声明**：

1. **只有被登记的对象可删。** 注册表之外没有任何函数接受外部路径；成为可删对象的唯一途径是被 `track` 登记，而唯一的调用者是暂存步骤。
2. **删除通过持有的目录句柄，而不是拼出来的路径。** 走 `paths::remove_relative`，由内核在**创建暂存文件时那个目录对象**内解析名字。事后目录被改名或替换都不会把删除引到别处。
3. **删除前复核对象身份。** 若该名字已不再指向当初创建的对象，删除被拒绝并上报残留。"清理不掉"是一个答案；"把那里现有的东西删了"不是。

实测覆盖（`src/temp.rs` 单元测试 + `tests/write.rs` 集成测试）：

| 场景 | 期望 | 实测 |
|---|---|---|
| 已登记对象 | 被删除 | `Discard::Removed` |
| 用户自己的文件（未登记） | **不受影响** | 内容原样 |
| 名字已被别的对象占用 | **拒绝删除**，该对象存活 | `Discard::IdentityChanged` |
| 对象已不存在（发布已消费） | 报告"已消失"而非失败 | `Discard::AlreadyGone` |
| 目录被改名，旧路径被放入同名诱饵 | 只删**我们**的对象（在被改名后的目录里），旧路径诱饵原样 | 通过 |
| 根外哨兵（W02 语义） | 字节、大小、mtime 全部不变 | 通过 |

**根外哨兵回归**（`tests/write.rs::no_write_path_touches_a_file_outside_the_root`）把这条约束摆在最外层：在授权根**旁边**放一个可区分的文件，然后依次走完 7 条拒绝路径与 3 次**真实**写入（create → overwrite → edit），最后要求哨兵的字节、大小与 mtime **完全不变**。一个靠 `dirname` 向上推算来清理的实现，或者"把暂存样子名字下的东西删掉"的实现，会在这里露出来。

## 5. 已知未覆盖 / 不得读作已支持

- **暂存残留没有结构化上报。** 发布结果不确定时 helper 有意保留暂存文件，但当前把它作为 `io_error` 返回，调用方只能靠目录里是否出现 `.fsguard-tmp-*` 自行判断。把"残留清单"并入响应属后续接入面（任务 3.4 一带）。
- **`read` 已返回 version 字段**（任务 4.2 加入，`ops::read` 的每个分块都带）。此前这里是"读—改"闭环的缺口：调用方只能从 `write`/`edit` 的返回里取得版本，即**必须先写一次才能得到版本**，而覆盖又要求版本——先有鸡还是先有蛋。现在版本由读铸造（`version_for`），写入前用它比对。**已实测**：`version.rs` 的 4 项单测（含 FNV-1a 公开测试向量），以及读结果字段本身。
- **`cancelled` 在写入路径上没有实测。** 读取类的取消有测试；写入的取消语义（取消发生在暂存中/发布中分别如何）尚未逐项验证，不得声称已覆盖。
- **`io_error` 的"不确定"分支没有强制注入测试。** 该分支的正确性目前由代码结构与单元测试（`publish_is_ambiguous` 的分类）保证，**没有**通过故障注入真的制造一次"发布期间失败"。要声称它被验证，需要注入。
- **POSIX 侧为编译级验证。** `cargo check --target x86_64-unknown-linux-gnu`（两种 feature 组合）通过，但无 POSIX 主机做运行级回归；本文件的磁盘状态一列是在 Windows 11 x64 上实测的。
