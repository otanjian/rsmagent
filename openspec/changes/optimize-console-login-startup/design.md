## Context

排查见 [evidence/baseline.md](evidence/baseline.md)。当前 `chat.html` 头部有同步脚本，`console.js` 末段才调用 `refreshAccountIdentity()`。该函数已有 `_authEpoch`、检查序号、请求去重和错误重试；登录、租户选择、强制改密及桌面重登录均已实现。

最小改动应利用这些机制，而不是为消除一段串行等待重新装配整个控制台。原方案的过度设计已在 [evidence/review.md](evidence/review.md)中删除。

## Goals / Non-Goals

**Goals:**

- 压缩现有响应体，减少首次下载量。
- 让一次只读账号检查与现有资源下载重叠，正常启动只消费一次结果。
- 在请求挂起时结束等待并沿用现有 UI 提供重试，保持真实认证语义。

**Non-Goals:**

- 不拆分登录应用、账号核心或完整业务脚本，不改变 DOMContentLoaded 及脚本执行顺序。
- 不增加动态资源加载器、业务加载超时体系、配置开关、身份缓存或数据库迁移。
- 不在本 change 强制启用 HTTP/2，不承诺解决尚未定位的公网停顿。
- 不保证主脚本缺失时表单仍可用；压缩后如果脚本等待仍是主要瓶颈，再依据新数据提出针对性拆分。

## Decisions

### D1. 使用代理已有 gzip 能力

为目标站点不含用户数据的公开 HTML 外壳和静态 JS/CSS 配置 gzip，覆盖实际 `text/javascript` MIME，使用常规压缩级别并保留 `Vary: Accept-Encoding`。继续使用当前应用静态处理、逐文件版本和 ETag；公开外壳保持 no-store，API、用户数据、SSE 和 WebSocket 不纳入压缩规则。

修改 `docker/nginx.conf.example` 及既有生产运维说明，给目标 Windows 配置形成同范围补丁。候选配置先验证、备份后重载；确认 gzip/identity 解码内容一致、条件请求正确，以及流式响应没有被缓冲。无需迁移静态文件服务或升级 Nginx。

HTTP/2 是独立传输优化，现有证据没有证明它是本次必须完成的修复。不把模块探测、软件升级及完整协议矩阵加入此 change。

### D2. 提前只读请求，保留原账号状态机

在 `chat.html` 的重型脚本之前加载一个小型 fork 请求脚本，立即发出 `GET /auth/check`，保持 `credentials: same-origin`、`cache: no-store`，不附加所选租户头。它只封装固定端点的请求、正文读取、取消、期限和一次性结果，不读取用户名输入、不更新 DOM、不声明另一份账号状态，也不改写全局 fetch。

现有 `refreshAccountIdentity()` 在页面首次启动时取走该句柄，并继续执行原来的状态归一化、未认证、强制改密和应用入口分支。手动重试始终发起新检查，不再取用启动结果。请求层返回已捕获错误的结果，避免主脚本尚未就绪时出现未处理的 Promise rejection；保留 HTTP 状态，不能把 401、503 或非法正文吞成成功。

预取只在本页首次消费、身份未变化且从发起起未超过 5 秒时可复用。已完成但过期的成功结果被丢弃，由现有流程重新检查；预取已经超时或失败时，UI 就绪后显示错误并提供手动重试，不自动重放检查。消费后释放引用。登录提交、退出或身份失效时丢弃/取消尚未消费的预取，已消费的结果继续由原身份代次与检查序号隔离。如果调用时没有预取句柄，原入口使用同一个限时请求函数正常检查；请求函数仍是显式加载的依赖，不另外复制一套回退实现。

现有测试中部分用例独立执行 `console.js` 片段，需要显式加载或注入这一个请求依赖，不能把测试夹具当作生产另设认证回退逻辑的理由。此改动不影响 `/auth/me`、`/auth/context`、登录写接口或原有轮询资格门槛。

取舍：这只重叠网络等待，登录 UI 仍在原脚本就绪后显示。相比完整拆分，改动小且不触碰大量身份消费者；压缩负责缩短仍存在的脚本下载阶段。

### D3. 只给账号检查加期限

固定 5,000 ms 从请求发出到响应正文读取完成，首次预取、普通检查和手动重试共用相同逻辑。使用 AbortController，并保证期限可独立结算；正常、失败、取消均清理计时器。当前请求的迟到回调不能覆盖超时后重试结果，旧 finally 不能清空新请求；沿用已有 `_accountCheckRequest`、`_accountCheckSeq` 和 `_authEpoch`，不新建状态框架。

主脚本已就绪时，超时立即进入现有错误面板；若期限在脚本下载期间届满，网络检查先结束，面板在现有 UI 就绪后显示。这个期限不是“打开网址 5 秒内一定出现提示”的承诺，也不解决任意脚本永久下载失败。

补充简体、繁体、英文“账号检查超时”文案，使用已有重试按钮和状态区域。超时不等于 401，不清除服务端会话，不开放业务访问；控制台内重试保持当前草稿和页面。登录、改密及退出写请求不加自动重试。

### D4. 用少量对照和关键故障测试验证

利用现有测试与浏览器资源时间线，不建设新的性能平台。使用同一浏览器、网络及候选资源，修改前后分别采集至少 5 次冷缓存和 5 次暖缓存，记录文档响应、脚本完成、账号请求开始/完成、表单可操作时间及传输字节，报告中位数和范围。服务器本机及公网接口耗时有必要时作同期对照。

验收关注三个可直接验证的结果：实际返回 gzip 且主要 JS/CSS 传输变小；首次账号请求确实早于主脚本执行并被复用；挂起请求能结束并重试成功。冷启动表单等待应有可重复改善，暖缓存和已认证进入流程无可重复回退。如果未改善，保留结果并继续定位，不能只凭配置和请求前移就宣布登录加速完成。

取消原先没有数据支持的 2 秒/1 秒 P95、200 KiB、300 ms 和已认证 P95 10% 硬门槛。主要资源可核对压缩前后字节，但不把压缩率推算成公网耗时保证。故障测试覆盖超时、正文挂起、重复重试、过期预取、旧响应及身份变化；复用既有账号/桌面回归，不重复创建完整认证测试体系。

## Risks / Trade-offs

- [提前读到的身份结果变旧] → 一次性、短时有效，身份变化时丢弃；后端仍逐请求授权。
- [压缩后资源加载仍慢] → 如实记录剩余等待，凭新瀑布决定是否另行拆分。
- [取消未立即结束底层请求] → 期限独立结算，旧结果由现有序号隔离。
- [压缩配置影响编码缓存或流式接口] → 限制响应范围，验证 gzip/identity、缓存和实际流式请求。

## Migration Plan

1. 保存同环境基线及目标站点配置备份，确认实际生效代码和资源。
2. 实施 gzip、提前请求和限时处理；完成账号/资源关键回归和前后对照后再交付目标版本。
3. Nginx 配置先校验后定向重载；应用仅按实际变更需要部署或重启，不影响其他站点。
4. 使用真实授权账号确认登录、有效会话刷新和桌面重登录，保存资源与时间证据。
5. 需要回退时恢复上一应用版本或代理备份并刷新验证。没有新 feature flag、双装配路径或数据库迁移，也无需删除用户会话。
