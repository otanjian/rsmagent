## Context

当前菜单、归档、恢复和编码删除接口都已存在。`deleteSession` 删除当前最后一条时调用 `newChat(false)`，而 coding 分支仍会创建远端会话；这一行为已通过真实前端函数隔离执行复现。`coding.js` 已有 `leave`、定时器清理与挂载代次，历史区已有缓存失效和请求上下文，无需重新设计这些机制。

另一个可直接从代码确认的问题是：fork `_coding_link` 及服务 `link_for` 将读取异常吞为无关联，删除处理器随后可能走普通会话清理。这里只修复删除分流的错误处理，不扩展成会话修复或迁移系统。

此前 6 项相关后端测试及 14 项前端测试通过，但未访问目标部署，不能据此断言线上归档正常。归档的具体根因仍待请求和部署版本证据确认。

## Goals / Non-Goals

**Goals:**

- 让现有 code 历史归档、恢复、删除链路正确工作，成功与失败有可见反馈。
- 删除当前最后一条后保持空态，操作回调不影响后来选择的会话或身份。
- 保留原有授权、远端确认后清理及文件保留边界。

**Non-Goals:**

- 不增加归档搜索、分页、归档页删除、当前归档状态栏或额外状态投影。
- 不建设通用 mutation 框架，不重写列表缓存、同步轮询或创建／删除生命周期。
- 不新增运行状态必须查询成功、停止后轮询确认等删除前置条件；沿用现有运行取消和远端删除契约。
- 不迁移数据库、不新增开关或 API，不改造其他 change。

## Decisions

### D1. 按请求证据修复归档，保留已有服务端能力

在实际装配的页面上使用自有测试会话，检查点击是否发出请求、平台会话 ID 和所属 `agent_id` 是否正确、响应状态及刷新结果；同时核对 fork 处理器与静态资源版本。归档的最小修复由证据决定，不预先要求修改所有前后端模块。

归档／恢复继续调用现有 PUT，仅改变平台归档标记。当前会话保持打开、任务继续，已有成功提示及“已归档”弹窗承担反馈和恢复，不添加新的状态栏。OpenCode 离线／关闭时仍按平台权限进行本地归档，不调用远端来判断是否可归档。

若拿不到目标部署，只记录缺少的线上证据；已复现的本地缺陷修复和测试继续进行。测试环境通过不等于目标部署的问题已解决。

### D2. 用已有离开逻辑收尾，只分离编码空态

归档和删除始终使用所选行的会话 ID 与所属 Agent。删除当前会话的未保存内容保护及确认在发送请求前完成；取消不发送删除。

成功回调重新检查身份和当前选中会话。目标仍为当前项时，复用 coding 模块的离开逻辑清理目标 iframe、定时器与旧回调，再接续已有相邻会话；没有相邻项或打开失败时显示空态、清除已删除会话引用并保留智能体选择。成功后不再重复询问已完成的离页确认。若用户已切换到 B，则只刷新列表，不卸载 B 或自动导航。

编码空态不调用 `newChat`／`launch`，不展示可将 coding Agent 发送给普通执行器的输入；重载或恢复选中状态也不能因没有会话而自动创建。用户显式新建沿用既有创建入口。选中编码智能体而没有挂载编码视图时，普通发送（含恢复的文本／语音回调）由 `guardCodingMessage` 直接拒绝：既不再代用户 `openCodingSession`，也不进入普通执行器，草稿保留并提示编码入口 —— 空态下唯一会创建远端会话的入口是显式新建。普通会话仍使用原来的未持久化新对话行为，不做全局空态重构。

### D3. 在现有函数内补齐小范围反馈和保护

归档、恢复、删除请求同时判断 HTTP 和业务结果；失败保留记录并使用现有 toast 展示原因，解除等待后允许用户再次操作。必要的操作中状态用按目标 Agent／会话区分的简单在途标记实现，防止同一目标重复提交；不建设通用状态机或单独重试面板。

复用 `_sessionListContext`、现有身份上下文、`_sessionReqSeq` 和 `_refreshHistoryList`。确认期间换身份使旧确认失效，完成后换身份使旧回调失效。用延迟请求测试检查操作后旧列表是否回跳，仅对复现出的缺口补失效处理；不预先合并所有列表、分页、搜索与 coding 同步状态。

### D4. 删除分流失败明确返回，保留远端协议

在现有服务端授权之后，从目标会话 store 严格读取关联。确实无关联的普通会话仍走原删除分支；查询异常不得变成普通删除。若 coding 记录存在却缺关联，明确报错保留记录；已确认不存在的重复删除仍沿用既有幂等行为。严格读取只用于需要确定来源的删除路径，不全局改变普通会话的探测语义。

沿用 `CodingSessionService.delete` 和 OpenCodeClient 的远端删除契约，包括已知运行中的目标先中止、远端失败保留记录、远端明确不存在可清理、本地事务清理和项目文件保留。本次不引入“状态接口不可用就禁止调用删除”的新规则，不增加停止完成轮询。若实际联调发现服务协议不兼容，则依据该缺陷作最小适配并记录，不能在没有证据时预设重写整条生命周期。

## Risks / Trade-offs

- [线上归档根因仍未确定] → 保留具体请求和版本诊断任务，分别报告代码验证与线上确认结果，不用猜测替代修复证据。
- [删除等待期间切换会话或身份] → 请求固定目标，提交前及回调检查上下文，当前视图的收尾只作用于仍匹配的目标。
- [复用离开逻辑可能再次触发保护] → 在请求前完成必要保护，成功后使用已有跳过确认选项，不另建卸载系统。
- [关联读取失败只删除本地会造成两端不一致] → 保留最小服务端拒绝和测试，不能为了缩小范围而省略这项正确性修复。

## Migration Plan

1. 先完成已确认缺陷和归档请求定位，再执行针对性回归与实际页面验证。无额外 P0／P1 阶段门禁；独立工作可以继续，不把生产访问作为开始修复的前置。
2. 复用既有测试，新增最后一条删除、删除失败、在途切换、归档／恢复及关联读取异常用例；检查普通会话与原权限行为。新增文案沿用三语和现有控件的键盘／触摸能力。
3. 在可用测试环境用真实页面及配套 OpenCode 做一次自有会话的归档→恢复→删除验证，并验证服务关闭／离线时归档仍本地可用、删除按原规则失败保留。目标部署的静态资源和反向代理行为在上线确认时核对，不用本地测试冒充生产通过。
4. 无数据迁移。静态资源沿用版本戳；升级保留旧会话、归档值及关联，代码回退不改写数据。删除的远端会话不会因代码回退恢复。
5. 更新历史面板说明并记录本次验证范围。其他 change 只需处理实际重叠文件，不作为新增功能依赖；保留现有 `opencode.enabled` 和全部授权边界。
