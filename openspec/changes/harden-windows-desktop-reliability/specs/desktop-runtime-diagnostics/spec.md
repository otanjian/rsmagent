## Purpose

定义桌面宿主在终端断开、后端启动失败和开发环境不完整时的可观察行为，使日志占用有界、失败原因可定位、恢复动作与实际运行模式一致，并保持原有业务、身份及服务器数据边界。

## ADDED Requirements

### Requirement: 桌面日志故障不得递归传播

桌面宿主 SHALL 在 stdout/stderr 同步或异步写入失败时隔离对应终端输出，继续使用独立文件诊断通道。日志格式化、文件写入及异常处理 MUST NOT 再次通过失败通道报告自身错误。故障记录 SHALL 保持有界且保留可定位原因，不要求建立通用异常聚合系统。

#### Scenario: 父进程退出导致断管
- **WHEN** 桌面运行期间父进程退出使终端输出返回 EPIPE
- **THEN** 不产生递归异常或持续日志风暴，桌面仍可使用，文件诊断记录终端输出已停用

#### Scenario: 日志输入或文件写入失败
- **WHEN** 待记录对象不可序列化，或日志目录不可写、磁盘空间不足
- **THEN** 日志失败不触发递归记录，系统保留有限的降级状态且不无限缓存记录

### Requirement: 桌面日志存储与诊断导出有界

桌面宿主 SHALL 为自己的日志采用明确的文件大小和保留数量策略，不与后端竞争轮转同一个文件；失败或持续输出不得造成无限内存积压。系统 SHALL 复用现有日志入口定位宿主与后端文件，不要求新建日志面板或导出流程。现有诊断导出仍 SHALL 脱敏并保持访问资格，MUST NOT 收集认证秘密或个人记忆正文。

#### Scenario: 持续输出超过阈值
- **WHEN** 主进程日志持续写入并超过大小阈值
- **THEN** 只由对应写入者轮转，文件大小保持上限，后端日志继续正常工作

#### Scenario: 升级前已有超大日志
- **WHEN** 操作者按说明处理旧超大日志
- **THEN** 停止对应写入者后才受控处理，不一次性加载整文件或删除业务/审计数据；不要求客户端自动识别和迁移混合历史日志

### Requirement: 本机开发模式选择经过实际验证的解释器

开发启动 SHALL 使用当前平台可执行且符合项目版本要求的 Python，并提供显式解释器配置。每个候选探测 SHALL 有期限；显式配置失败 SHALL 明确报错而不静默换环境。Windows SHALL 拒绝不可运行的跨平台虚拟环境与 Store 占位解释器，失败 SHALL 列出脱敏的候选原因及恢复动作。

#### Scenario: 显式配置指向有效环境
- **WHEN** 开发者指定具备必要依赖的可用解释器
- **THEN** 使用该解释器启动，并在本机诊断中显示选用环境

#### Scenario: macOS venv 与 Windows Store 别名
- **WHEN** Windows 检出仅含 POSIX venv，且 PATH 的 Python 为不可运行的 Store 别名
- **THEN** 在有界探测后报告解释器不可用，提示配置真实解释器，不以退出码 9009 作为唯一说明

#### Scenario: 显式配置失效或探针挂起
- **WHEN** 显式指定的解释器不可运行或候选探测超时
- **THEN** 返回具体失败类型及诊断摘要，显式指定时不改用其他环境，探测子进程被清理

### Requirement: 启动失败与依赖缺失提供准确恢复动作

桌面 SHALL 区分解释器缺失或无效、必要依赖缺失、后端缺失、启动崩溃和超时，并经现有错误界面提供诊断摘要、日志入口及有意义的重试动作。核心依赖缺失 SHALL 阻止就绪；可选工具 SHALL 在首次使用前检查依赖并提供明确缺项和修复提示，不要求启动扫描全部工具。健康轮询 MUST NOT 被描述成已发生的进程重启。

#### Scenario: 必要或可选依赖缺失
- **WHEN** 后端启动因核心模块缺失失败，或用户首次调用的浏览器工具缺少运行依赖
- **THEN** 前者显示缺失原因并停止启动；后者保留核心业务且执行前返回明确缺项，不裸露 ModuleNotFoundError 或静默安装依赖

#### Scenario: 安装包后端被移除
- **WHEN** 打包安装的后端可执行文件缺失
- **THEN** 提示修复安装，不自动搜索系统 Python 或创建开发环境

### Requirement: 同一桌面实例的后端生命周期串行且可追溯

本机后端 SHALL 保留可定位启动来源、子进程和端口的诊断；并发启动、手动重试与自动恢复 SHALL 保持最多一个有效后端，旧进程回调不得破坏当前状态。系统 SHALL 优先复用已有去重和恢复预算，只有确认其不足才补保护，不要求新建生命周期框架。端口冲突不得通过杀掉不属于本实例的进程解决。

#### Scenario: 手动重试与自动恢复并发
- **WHEN** 同一实例同时收到多个启动或恢复请求
- **THEN** 最多产生一个有效后端子进程，日志能关联触发来源且错误状态一致

#### Scenario: 旧子进程迟到退出
- **WHEN** 旧进程的回调晚于新代次启动到达
- **THEN** 回调只清理旧代次资源，不将新进程改成停止或触发额外启动

### Requirement: Windows 开发入口不继承错误 Electron 运行形态

Windows 开发入口 SHALL 在启动 Electron 子进程前清除使其进入 Node 模式的继承变量，并提供可复现的虚拟环境与依赖准备步骤。环境准备 MUST NOT 覆盖其他平台 venv、业务配置、身份库或已有记忆；失败 SHALL 返回非零及可定位原因。

#### Scenario: Electron 宿主发起开发启动
- **WHEN** 启动环境含 ELECTRON_RUN_AS_NODE
- **THEN** 包装入口以 Electron 形态启动应用，不静默作为 Node 退出

#### Scenario: 已有跨平台环境和业务文件
- **WHEN** 开发准备发现已有 macOS venv 与用户数据
- **THEN** 创建或复用明确的 Windows 环境，不删除或覆盖原环境及用户数据
