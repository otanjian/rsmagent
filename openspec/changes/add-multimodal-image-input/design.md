平台当前把入站图片降级为文本路径标记，图像字节从不进入模型请求。已核实的关键接入点（行号为本变更开始时的现状）：

| 环节 | 位置 | 现状 |
| --- | --- | --- |

- `deepseek-v4-flash`、`deepseek-flash`、`deepseek-v4-flash-vision-exp` 三者对同一张图均返回 HTTP 200；`deepseek-v4-flash` 返回准确的中文画面描述，`finish_reason=stop`，`usage.prompt_tokens=1004`、`completion_tokens=1055`。

- 结论：`deepseek_bot.supports_vision` 的断言（`deepseek-v4-flash` 遇图返回 400）与真实行为不符。**该模型当前是否持续可用需在实现阶段以回归测试钉住，不得只依赖本次一次性实测。**

## Goals / Non-Goals

**Goals**

- 图片以图像内容进入该轮对话，Web 控制台与企业微信均可用。
- 图片投递相关失败对模型可见，模型不再有「不知道图未被解析」的余地。
- 模型图像能力判定与该轮实际选定模型的真实行为一致。
- 含图片会话的历史回放与上下文裁剪行为明确、可验收。
- 机制在渠道间复用，新增渠道不需要重复实现编码与降级。

**Non-Goals**

- 视频、音频与文档的多模态化（本次只做图片；既有路径标记行为对它们保持不变）。
- 回复方向的图片能力（企业微信流式回复仍为文本；`send`/图片生成链路不变）。
- 引入 OCR 预抽取或本地视觉模型。
- 改造视觉工具本身的提供方链（仅在能力判定修正后恢复其主模型通道）。

## Decisions

### 1. 投递形状：结构化附件 + 内容块，而非解析文本标记

渠道层只产出「本地可读路径 + 媒体类型」的结构化附件；由 Agent 边界（`run_stream` 的用户轮次构造处）统一转成内容块：

```
{"role": "user", "content": [
  {"type": "text",  "text": <原文本 + 降级说明>},
  {"type": "image_url", "image_url": {"url": "data:image/png;base64,<...>"}}
]}
```

- 选择理由：`image_url` 块已被既有 OpenAI 兼容适配层透传（已验证），多模态实现落在单一处，所有渠道共享。
- **保留** `[图片: <path>]` 文本标记：它是历史展示与非视觉模型降级的载体，也是人工排查入口。标记保留但不再作为唯一投递形式。
- 备选方案（在 Agent 侧解析 `[图片: path]` 标记）被否决：隐式、脆弱，且会把渠道格式细节泄漏进 Agent。

### 2. 附件载体：扩展 `Context`

`Context` 增加结构化附件描述（路径、类型、可选原始文件名与稳定存储位置）。渠道不再仅靠拼接 `content` 传递附件；文本标记与结构化附件同时存在，前者服务可读性，后者服务投递。

### 3. 编码与上限：本地文件 → 校验 → 归一 → data URL

- 支持格式限定为 jpeg / png / webp / gif；其余不投递。
- 超过最大边时等比缩放并重编码，以控制请求体与令牌开销。
- 单张字节上限与单轮图片数量上限均需有界（默认值见「未决实施参数」）。
- 超限、格式不受支持、无法解码一律走**明确降级**：不投递该图，并把原因写进该轮文本。

### 4. 能力判定：以实际回答模型为准，并与真实行为对齐

- 判定入口保持既有 `supports_vision` 声明 + `_main_bot_supports_vision` 的兜底结构，但要求声明与该模型真实行为一致。
- 修正 `models/deepseek/deepseek_bot.py` 的判定，使其与实测一致（同时覆盖 `deepseek-v4-flash` 与既有两个名字）。
- 兜底的前缀启发式**不得**作为唯一依据（当前它才是不一致判定的来源）。
- 要求增加回归测试：对「声明支持」的模型，断言判定为真；对「声明不支持」的模型，断言判定为假。防止能力表再次漂移。

### 5. 非视觉模型降级 = 保持今天的行为

该轮回答模型不接受图像输入时，不发送任何图像块，沿用既有 `[图片: <path>]` 标记。理由：这是当前非视觉模型的唯一可用行为，改变它会引入回归；也让本变更的失败模式收敛为「与今天相同」而不是「更差」。

### 6. 失败可见性：降级说明进入该轮文本

未投递图片时，该轮文本追加可读说明（例如「该图片未能解析：超过大小上限」）。这是本次事故（模型声称已读图）直接对应的防线：模型始终能据文本如实回答。说明文案需 i18n（既有 `i18n.t` 机制）。

### 7. 历史回放与图片持久化

- 图片需落在**不会被例行清理**的每会话稳定目录，而非当前会被清理的 `tmp`（`channel/web/fork/runtime.py:1317-1337` 会清理过期录音等临时文件）。
- 会话消息需记录该轮含哪些图片（附件描述），使回放能重建内容块。
- 回放时图片已缺失或不可解码 → 显式占位说明，不静默省略。
- 旧消息（无附件描述）保持现状回放，不尝试猜测重建。

### 8. 上下文裁剪：先剥图片，保留文本与工具配对

既有裁剪逻辑（`agent/protocol/agent_stream.py:2742` `_trim_messages`、`:2501` `_validate_and_fix_messages`）在压缩时需先把较早轮次的 `image_url` 块替换为文本占位，再按既有规则裁剪。约束：不得产生失去配对的 `tool_use`/`tool_result`，不得产生空内容消息。

### 9. 企业微信优先路径

企业微信图片已在 `wecom_bot_message.py` 落地为本地文件，改动集中在 `wecom_bot_channel.py` 的装配处：把 file_cache 中的图片作为结构化附件传给该轮，而非只拼标记。必须保留既有语义：

- 「图片先到、文字后到」的合并（同一轮里的图片归属其后第一条文字）；
- file_cache 的 5 分钟 TTL 与 `clear(session_id)` 行为；
- 群聊与单聊的既有前缀处理不变。

### 10. 分阶段门槛

- **阶段 1（Web + 企业微信 + 能力判定）**：具备图像能力的模型能直接读图；非视觉模型行为不变。
- **阶段 2（上限与失败可见性）**：超限/不支持/缺失场景都有可验收的明确降级文本。
- **阶段 3（回放与裁剪）**：含图会话重开可重建；超预算会话可压缩且不失败。
- **阶段 4（其它渠道复用与文档）**：其余 IM 渠道接入同一机制，不做逐渠道专有实现。

各阶段完成不等于整体完成；阶段 3 的验收不得用阶段 1 的证据替代。

## Risks / Trade-offs

- **令牌与费用上升**：一张图片约千级 prompt token；多图会话成本明显上升。缓解：单轮数量上限 + 尺寸归一 + 压缩时优先剥离旧图。
- **请求体变大**：既有 Web 请求体上限（`channel/web/fork/runtime.py:2159` 附近）需复核是否容纳多张折图后的 base64。
- **隐私边界变化**：图片内容由此进入模型提供方。缓解：仅当回答模型支持时才投递，非视觉模型沿用路径；不新增外部存储；上限约束减少外泄面。
- **Provider 兼容性**：data URL 形态对部分提供方可能不被接受。缓解：投递失败按明确降级处理并可回退到路径标记；不做「静默失败」。
- **能力判定再次漂移**：供应方模型更新可能让静态判定再次失真。缓解：回归测试 + 投递失败可观测。
- **图片长期存储占用**：稳定目录会累积图片。缓解：保留策略与配额需在实现阶段定值（见未决参数）。
- **企业微信时序**：图片与文字的合并依赖 file_cache，改造需避免破坏既有合并与 TTL 语义，否则会出现「图片丢失」或「图片挂到错误轮次」。

## Migration Plan

- 无数据库结构迁移；新增的是消息附加描述与配置项。旧会话按现行路径标记回放，不做重建。
- 图片存储位置调整只影响新入库的图片；旧图片文件按原路径尽力回放，失败则显式占位。
- 回滚：关闭本变更的投递开关后回到今天的路径标记行为；已写入的附件描述可忽略，不影响旧逻辑。

## 实现期新增的判定

- **非视觉模型的降级也写说明**：不只保留路径标记，而是在文本中明说「当前模型不支持图像输入，图片内容未送达」。比 design 的「保持今天的行为」更进一步，仍然满足 6 号决策（模型始终能如实报告）。
- **`image_url` 块的令牌计价**：`Agent._estimate_message_tokens` 原先只认块类型 `image`，`image_url` 会被算成 0 token，使包含图片的 prompt 在预算检查中「免费」而可能直接撞上提供方窗口上限（`_trim_messages` 注释里警告的 400 循环）。现按 `Agent.IMAGE_BLOCK_TOKENS`（1200）计价，且不把 base64 当文本计数。
- **媒体类型以字节探测为准**：企业微信下载的图片文件名固定为 `.png`，与真实字节可能不符，因此渠道不得断言媒体类型；编码时由 PIL 探测真实格式（`ImagePart.media_type`）。
