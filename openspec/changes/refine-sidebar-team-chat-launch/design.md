## Context

动机与范围见 [proposal.md](proposal.md)。本文件基于当前仓库的只读检查描述拟实施方案，未表示下述能力已完成实现或测试。

当前实际页面从 `channel/web/chat.html` 加载 `static/js/console.js`。侧栏包含 `sidebar-new-chat`、功能导航、最多 10 条的 `sidebar-recent` 及底部账号；`templates/layout/sidebar.html` 和 `static/js/chat/new-chat.js` 存在较旧的相似代码，不能直接假定它们是运行入口。

团队创建相关接入点如下：

| 接入点 | 当前行为与本次处理 |
| --- | --- |
| `openTeamChatModal` / `renderTeamChatList` | 以当前智能体预选；当前为 coding 时拒绝打开，成员列表来自普通聊天候选。改为独立的普通团队草稿及统一团队候选。 |
| `startTeamChat` / `newChat` | 先切换 activeAgentId、新建 session，再异步写 members。改为保存确认后的显式会话提交。 |
| `setTeamMembers` | 依赖全局当前 session/agent，业务失败未统一抛出。引入显式目标参数与错误反馈，避免准备新团队时误写原会话。 |
| `renderComposerAgentMenu` 与 @ 候选 | 切换单人智能体和邀请成员共用部分数据。仅团队相关候选使用 normal 过滤，保留 coding 单人切换。 |
| `SessionSettingsHandler.POST` | 已拒绝 members 中的 coding 并在名册变化后退休运行时；实施时补核 owner、完整名册的授权和持久化失败语义。 |
| `agent/workspace/session_prefs.py` | 允许首条消息之前按 owner/session 保存偏好；现有落盘异常处理可能仅记录日志，不能据此承诺创建成功。 |
| 最近会话与历史页 | 共用授权历史及归档/重命名能力；调整预览数量和表现，不替换数据源。 |

`add-opencode-coding-agents` 已有产物与代码但尚未归档；本 change 不修改其产物，以已落地的类型投影、运行拒绝和编码历史切片为依赖，实施前验证证据。`add-multimodal-image-input`、`port-upstream-tasks-page` 仍有进行中任务，修改共享页面时需避免覆盖其附件和任务行为。

## Goals / Non-Goals

**Goals:**

- 使用现有 Web 壳、会话模型和团队运行时，提供统一、可重试的团队启动事务边界。
- 将「可用于单人聊天」和「可加入团队」分成不同候选投影，所有团队选择表面共享后一规则。
- 让侧栏布局与历史数据更新独立，保留原身份作用域、会话寻址、后台流式响应和编辑保护。
- 把 coding 完全不可见及服务端不可加入作为持续约束，覆盖旧入口和新版侧栏回退。

**Non-Goals:**

- 不引入团队模板库、多个智能体自动轮流发言、新的编排引擎或团队管理后台。
- 不更改现有团队 owner 的存量锚定，不把会话默认响应者写成用户或租户通用默认。
- 不改变 Desktop 原生导航、渠道绑定、任务调度或 coding 的普通执行边界；Web 公共接口收紧后做兼容验证。
- 不在本次规划阶段修改产品代码、运行数据、数据库或已有 change。

## Decisions

### 1. 快速发起与导航分区

保留页面外壳，顶部只放一个「新建对话」控件：主按钮直接开始单人对话，按钮右侧的折叠箭头展开选择菜单（逐个智能体的单人对话，以及「多智能体对话」）。不为「多智能体对话」注册独立页面或路由。中间只保留一个滚动容器，底部控制台和账号使用原组件。

```text
容大AI
［＋ 新建对话            ⌄］

工作台
  对话
  智能体
  场景应用
  知识库
  定时任务

最近会话               查看全部
  团队图标 月度经营分析
  对话图标 采购比价演示
  编码图标 SAP 数据查询
  团队图标 合同联合评审
  对话图标 用户表疑问
  已归档

控制台
账号卡片
```

桌面展开宽度初始取 240px，水平留白 16px、导航行高 42px，触摸目标至少 44px；团队弹窗桌面宽度约 560px，手机全屏适配。默认主题绿色主按钮、低强调的折叠箭头；跟随既有外观变量，不覆盖其他配色。沿用会话列表折叠偏好；折叠时标题区「查看全部」仍可用；桌面折叠侧栏把该选择菜单作为侧栏右侧浮层打开。最近会话选中态与完整历史入口的当前页状态分别表达。

取舍：一级菜单项容易让用户以为会打开另一个管理页；顶部动作与新建对话同组更符合发起语义。与会话历史页的「新对话」共用同一个控件与同一份菜单实现，避免两个入口的候选、顺序与失败处理各自演化；因此不再保留侧栏第二个启动按钮，团队入口收进折叠菜单。账号区保持单行及既有大小约定。

### 2. 单独定义团队候选且在渲染前过滤

拟增加共享的团队候选投影（例如 `availableTeamAgents`），从真实使用范围投影读取，并应用 enabled、can_chat 和 normal 类型限制。实际 `agent_type` 缺失的旧档案兼容 normal，未知对象/未加载结果不能当作缺字段旧档案。database 模式下候选加载失败不回退管理目录，不以旧缓存冒充当前授权。

过滤发生在搜索、计数、预选、列表渲染之前。创建弹窗、默认响应选择、已选摘要、邀请成员及团队 @ 候选均复用该规则；旧缓存回填也须重新求交集。界面不渲染 coding 的名称、头像、禁用行或「不支持加入」列表。普通单人智能体切换、工作台目录和编码历史仍使用原完整使用范围。

从 coding 会话进入时，不调用当前编码会话的普通团队 guard；只创建弹窗草稿。合格当前 normal 优先预选，否则调用统一默认解析并确认结果是合格 normal。无候选时显示普通智能体空态；仅一位时可查看但不可开始。不得硬编码一个 default id，也不得任取未授权对象。

取舍：全局修改 `availableChatAgents` 会让合法 coding 单聊消失；使用局部过滤而不共享又容易漏掉邀请或 @。独立共享投影能同时满足这两个约束。

### 3. 草稿中显式记录默认响应者

弹窗草稿包括 selectedIds、ownerId、搜索词、状态和来源焦点。ownerId 必须属于 selectedIds；删除 owner 后令 ownerId 为空并要求用户显式指定。搜索只影响列表，不清空其他有效选择。至少选中两位不同对象方能提交。

UI 文案统一用「默认响应」，并解释「未指定成员时由它接收消息，输入 @ 可指定其他成员」。此字段映射既有会话 owner，持久化仅保存其余成员到 members，不新增 coordinator、team_id 或持久化选中顺序。管理成员继续沿用原会话 owner，不提供误导性的存量 owner 切换。

### 4. 准备后再提交活动会话

使用状态流程 `editing → validating → saving → committing → ready`，失败返回可重试编辑态，取消/离页/身份变化使本次尝试失效。

1. 点击开始时捕获用户、租户、认证代次、原会话上下文、owner、成员和本次 attempt；防重入。先完成现有未保存编辑及编码视图离页保护，取消不修改活动状态。
2. 刷新使用范围并校验草稿。有效成员不足、owner 失效或权限变化时显示原因，不自动替换用户明确选择的对象。
3. 在局部状态生成一个 preparedSessionId。调用现有 settings 接口时显式传入该 id 和 owner（现有 `agent`/`agent_id` 契约），使用捕获并验证的租户身份，不能依赖全局 activeAgentId 或 fetch 包装器替当前页面附加的默认 agent。准备会话只写本次完整 members，不继承旧项目、模型或成员覆盖。
4. HTTP 成功且业务成功并能确认持久化后，再检查 attempt、身份及原页面上下文是否仍有效。用户在校验期间新产生编辑时再次执行离页保护，取消不提交视图。
5. 使用 preparedSessionId 初始化普通对话视图，不在 `newChat` 内再次生成另一 id。此刻才更新当前 owner、活动会话偏好、工作空间、成员展示和输入焦点。新团队从空输入开始，原会话草稿仍保存在原作用域；普通新建对话的既有草稿/附件继承保持原样。

现有 `newChat` 应提取或增加可复用的「提交指定新会话」能力，让普通新建和准备后的团队初始化共用渲染而不重复产生 id。`setTeamMembers` 需接收明确目标快照，不使用提交期间可变的全局变量寻址；保留现有调用的兼容适配。

同一尝试重试复用 preparedSessionId 和目标快照。响应丢失时先读取同一 settings 核对 owner/members，再决定重试保存，禁止盲目再建。改变选择相当于新草稿版本，旧请求不得覆盖新版本。准备写入完成后用户已取消时，不跳转、不显示成功历史、不发送消息；可能残留的无消息偏好不生成可见会话，复用既有偏好回收机制处理，不能用通用删除会话接口清理以免误删已被使用的数据。

取舍：单纯把当前链路加上 loading 并不能阻止失败前已切换会话；准备写入利用现有首轮前偏好能力，避免新建一套团队数据库及创建 API。

### 5. 服务端校验及真实失败传播

沿用当前作用域解析与会话授权，在团队创建/变更路径独立校验 owner 和每个提交成员的真实注册、normal 类型、租户归属、启用及使用资格。授权旁路仍取现有统一规则，但管理员也不能绕过 coding 类型限制。只返回调用者有权得知的失败信息。

校验全部通过后一次保存标准化成员集合：去重、排除 owner 自身，空 members 仍支持既有退回单人语义。前端创建要求两位，后端通用成员修改不能因此禁止移除最后一位成员。无效提交整次拒绝，不静默过滤后写入；模型与其他设置沿用已有授权合同。

确认 `session_prefs` 的落盘错误可向调用者传播：写入失败不返回成功，也不退休原运行时。针对该路径补足持久化错误处理及调用兼容，而不将存储整体迁移至新系统。只有名册变更保存成功后调用原运行时退休逻辑；相同集合不重建，合法清理时对无法解析的旧参与者容错。新要求取代「允许新请求携带未知成员写入成功」的旧场景，保留清理历史无效名册时的容错能力。

历史无效成员仅展示通用提示，不在选择界面泄露 coding 身份。用户显式清理时提交其余合法成员；若只剩 owner，按既有规则退回单人。历史 owner 自身异常为 coding 的团队不能被静默迁移到普通 owner；保持消息可按授权读取，禁止其作为普通团队执行，并引导重新创建合法团队。

### 6. 最近会话是历史的紧凑投影

继续通过 `/api/sessions?scope=all` 的既有授权、未归档和排序规则读取，前 5 条作为侧栏预览。不会为追求名称上的「最近」改动置顶语义；恢复归档后不属于前 5 条的记录通过完整历史可达。标题区「查看全部」始终显示，保留「已归档」入口和两项并列行操作、双击/F2 编辑。

团队图标及摘要取统一历史响应中的持久化名册投影，不额外按每条记录发请求。若字段不足，只给现有列表增加向后兼容的只读投影字段；不新存一份会话类型或复制名册。coding 记录继续显示其原身份和打开方式。

### 7. 发布开关与依赖门槛

新增临时呈现开关 `workbench_sidebar_launch_v2`，开发/验收阶段缺省关闭，通过现有页面配置投影读取；完成门槛后显式开启。开关仅控制布局：折叠箭头与它的选择菜单、导航顺序和 5 条紧凑预览；关闭后使用原侧栏（不含折叠箭头的原按钮）、原数量约定，团队入口回到历史页「新对话」菜单。统一候选过滤、服务端拒绝与安全创建对新旧团队入口同时生效，不由呈现开关控制。

分阶段门槛：

- A：核实实际加载入口、依赖 change 的 normal/coding 投影和授权拒绝、历史归档与重命名基线。记录真实检查结果后进入实现阶段。
- B：先完成团队候选和服务端校验、可确认保存、幂等重试及失败隔离；真实授权与存储故障场景通过后，侧栏入口才能接入新创建链路。
- C：完成侧栏、弹窗和最近会话，在开关关闭与开启两种状态下执行主流程、coding 边界及三语/主题/响应式检查。
- D：只有接口集成与实际页面验收均通过，才在目标环境启用；仅有模拟前端测试不作为发布凭据。

## Risks / Trade-offs

- [旧副本与在用文件混淆] → 以 `chat.html` 的真实加载链和现有测试边界定位，避免同时维护两套运行逻辑。
- [异步结果污染活动会话] → 显式捕获 owner/session/身份代次；准备保存和视图提交分开，所有旧回调在写 UI 前校验代次。
- [筛掉 coding 却漏掉 owner 或邀请入口] → 团队候选共享投影，服务端同时验证 owner 与 members，矩阵覆盖所有入口。
- [底层落盘异常被吞掉] → 故障注入验证失败可传到弹窗，成功必须代表真实保存；失败不触发运行时退休。
- [取消后可能留下无消息偏好] → 不生成可见历史及执行副作用，重试以同一 id 核对；不对可能已使用的会话执行激进删除。
- [紧凑历史缩小可见范围] → 保留始终可达的查看全部、已归档及原操作，恢复排序不为预览限额改写。
- [与在途附件/任务改动冲突] → 实施前记录共享文件边界，改动后针对草稿、附件、任务导航和后台流式回复回归。
- [新增视觉样式破坏主题] → 跟随现有变量，使用三配色×明暗组合、长英文标签和 360px 手机宽度验收。

## Migration Plan

不创建新业务表，不迁移会话 id、owner、消息、项目或 coding 关联。不自动清理旧团队名册；用户明确清理后才写入。旧侧栏历史折叠偏好继续使用，旧中间栏偏好继续忽略，账号与外观偏好不重置。已有历史路由及别名继续解析到同一页面。

发布先上线通用团队资格与可靠创建，再上线默认关闭的侧栏呈现开关，完成阶段门槛后启用。界面回退只关闭 `workbench_sidebar_launch_v2`，保留团队校验与已保存数据；后端合同兼容旧客户端，旧客户端提交 coding 仍被拒绝。此阶段只做文档规划，以上发布步骤均为待执行任务。

## Open Questions

没有影响行为合同的待决事项。实施时可在既有视觉变量范围内微调宽度和间距；240px 侧栏、560px 弹窗、5 条预览及仅 normal 可选为本次起始验收基准。图标选用项目已安装的图标集合，不增加图标或 UI 框架依赖。
