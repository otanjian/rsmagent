## Context

工作区面板的读路径已经成熟：`channel/web/static/js/workspace.js` 负责列举（`loadWorkspaceDir`）、面包屑、搜索、预览与编辑，服务端由 `channel/web/fork/handlers/workspace.py` 的 `tree|search|resolve|meta|read|write|user-dir` 支撑，作用域与归属集中在 `_workspace_request_scope`、`_db_path_visible`、`_authorize_db_file_path` 与 `_workspace_path_allowed` 四个 seam 上。

写路径只有两条，都不满足本需求：

- `POST /api/workspace/write`：仅**文本**、仅**单文件**，不适合二进制与批量。这里有个容易踩的误解：服务端并**没有**「只允许文本」的授权约束——扩展名白名单 `WS_EDITABLE` 只存在于前端（`static/js/workspace.js:193`，用于决定是否给用户编辑入口），而服务端的 `_editable_target`（`channel/web/fork/runtime.py:3160`）管的是「文件属于哪个工作区」，是**作用域**而不是**类型**。它的不适合是形态上的（文本编码 + 单文件语义），不是一道靠扩白名单就能绕开的闸门。
- `POST /upload`：附件通道，支持目录（`files[]` + `relative_paths[]` + `upload_id`），但落盘在 `<agent workspace>/user/<uid>/uploads/webdir_<id>/<根目录>/…`，与面板当前目录无关。

删除路径**完全不存在**：全仓库没有任何针对工作区文件的删除端点（`workspace.py` 里唯一的 `DELETE` 属于 `ProjectManageHandler`，删的是项目而不是文件）。面板因此只能增不能减。

拖拽侧还藏着一处冲突：`#workspace-panel` 与 `#chat-main` 同属 `#view-chat` 的子节点，而 `console.js` 在 `#view-chat` 上注册了 drop 处理，把任何 `Files` 拖拽交给 `handleFileSelect`。面板新增落点若不阻断冒泡，一次拖拽会同时走上传和附件两条路。

面板的落点规则由 `land-shared-agent-panel-on-own-files` 与 `isolate-shared-agent-user-data` 定义，且已经是**按 Agent 可见性分两支**的：**私有** Agent 落在 `agents/<agent id>`（整根都是属主的），**租户共享** Agent 落在 `agents/<agent id>/user/<登录用户ID>`。本次的可写范围判定沿用同一个分法，因此与面板现有落点天然对齐。

## Goals / Non-Goals

**Goals**

- 拖入文件或文件夹（含 5000 个文件的量级）上传到**面板当前浏览目录**，且该目录**必须落在调用者本人的可写范围内**，越界即拒绝并给出可读原因；文件夹层级按所含文件保真。
- 可在同一范围内**删除**单个文件或目录（含递归），删除经**回收站**软删除，回收站可浏览、可恢复到原位置、可彻底删除。
- 上传过程有**准确**的实时进度（总字节、项数、百分比），超限项有逐项提示且不阻塞其余文件。
- 落盘与删除严格遵守既有归属规则：不新增任何越权路径，也不因客户端自报的 agent/路径放宽。
- 单文件 100–200MB 可用，且并发上传下服务端内存不随文件大小线性放大。

**Non-Goals**

- 不做断点续传与分片合并，不支持 GB 级单文件（见 D6）。
- **不做服务端跨请求状态**：不实现批次幂等记录、不做按拖拽累计的服务端判定（见 D4、D7）。
- **不保留空目录**（不含文件的目录不建）；结构保真只针对所含文件的位置，不丢任何内容。
- **不做移动/重命名**：本次只增「上传」与「删除」两类操作，`move`/`rename` 不在范围内（这也是恢复遇到占用时只能改名而无法腾挪的原因，见 D14）。
- 不做版本历史与「按内容恢复」：回收站每次删除只保留一份副本，同一文件删两次就是两份彼此独立的回收站条目。
- 不做磁盘余量预检、不做与 `resource-quota` 的联动（属于该能力责任域）。
- 不改聊天区的附件拖拽行为，不改 `/upload` 的契约与落点。
- 不改面板落点规则（`user/<user_id>`、项目目录、回落链均不动），不改执行层边界。
- 不改桌面端 `WorkspacePanel`（`desktop/` 下的独立实现）。

## Decisions

### D1 新增独立端点，而不是改写既有写路径

五条新 wire 都标着「新增」，而不是改造 `/upload` 或 `/api/workspace/write`。以上传为例说明为什么不复用 `/upload`（其余同理）：

`/upload` 的落点由服务端按 `_get_upload_dir(agent_id)` 决定，改成接受客户端目录等于把「写到哪儿」交给请求体，而该端点的授权语义（`agent.use` + 附件工作流）不是文件面板的语义；且它的响应契约（`preview_url` 带 `agent_id`、回读走 `/uploads/(.*)`）已被多处依赖。

五条新端点与面板的其它路由**同构**：`session` / `agent` 走 `_workspace_request_scope`，写闸门走 `require_management_write()`，登记进 `route_registry.py` 的 fork 段并更新 `scripts/route-baseline.txt`。

本次新增五条 wire（全部为 POST/GET，与既有 `/api/workspace/write`、`/user-dir` 的写法一致，不引入 `DELETE` 方法的策略分支）：

| 路由 | 作用 |
|---|---|
| `POST /api/workspace/upload` | 一批文件落盘到 `dir` 之下的相对路径 |
| `POST /api/workspace/delete` | 一批条目软删除到回收站 |
| `GET /api/workspace/trash` | 列出本人回收站条目 |
| `POST /api/workspace/trash/restore` | 把回收站条目恢复到原位置 |
| `POST /api/workspace/trash/purge` | 彻底删除回收站条目（含清空） |

`route_registry.py` 有一条**覆盖不变式**：注册的方法集合必须与 handler 类实际实现的方法一致（`check_route_coverage` 会内省比对）。因此这五条都必须逐条入册，`test_route_registry.py` 的冻结基线也要同步。

### D2 可写范围按 Agent 可见性分两支，判定复用既有原语

范围判定不新造规则，而是**复用已有的用户目录解析器**：`common/state_dir.agent_user_root(ident, ensure=False)` 就是 `classify_agent_user_path` 判定「`user/<uid>` 子树」时使用的同一个解析（同一个 `user/` 容器、同一个 uid 来源、同一套 `O_NOFOLLOW` 加固），本次取它的**返回值**而不是再解析一次 `classify_agent_user_path` 的四态字符串——范围要的正是那个目录本身，四态字符串是它的中间结果：

- **私有** Agent：范围为 `agents/<agent id>`（工作区整棵树，因为整根都是属主的）；
- **租户共享** Agent：范围为 `agents/<agent id>/user/<调用者 user_id>`。

「私有还是共享」不新查一次数据库：`land-shared-agent-panel-on-own-files` 已经在工作台投影上补了 `visibility`，服务端取其同一处派生即可。**范围判定与既有的 `_db_path_visible` 是两道独立闸门，两者都必须放行**——范围闸门回答「这是不是本人的空间」，归属闸门回答「这个人能不能看这个路径」。二者不可互相替代：`_db_path_visible` 对私有 Agent 的整个工作区都放行（包括他人的 `user/<uid>`，因为它是私有 Agent），范围闸门则把删除收窄到工作区根的第一层之外的合理面。

两条额外的失败分支在实现中显式存在，且都带稳定 code：会话打开了项目目录时 `agents/<id>` 已不在服务根之内（`not_agent_workspace`），身份缺失时没有 uid 可锚定（`no_user`）。这两种状态下**没有诚实的范围可发放**，因此拒绝而不是挑一个能解析的根。

越界时返回**稳定错误码**（`outside_own_directory`）而不是含糊的 403：前端要能区分「越界」与「目录不存在」，否则无法给出可读提示。

### D3 目录结构从显式 `relative_paths[]` 来，不从 multipart 的 filename 来

`/upload` 的目录上传已是这个形状（`files[]` 与 `relative_paths[]` 等长配对），沿用它可以复用既有的清洗与配对校验思路。不依赖 multipart 的 `filename` 字段承载相对路径，是因为中文、超长名与各浏览器的 filename 编码差异（RFC 5987 / 裸 UTF-8）会让「层级」变成不可控输入。

落盘直接用 `common/safe_fs.py` 的原语（`mkdir` + `write_bytes_atomic`）：它逐级以 `O_NOFOLLOW` 打开、写入先落临时文件再替换，逃逸形态与「校验后替换」一并被拒。这**比手写「清洗 + realpath + 前缀比较」更少代码，而不是更多**——`_resolve_upload_path` 的写法（仅 `realpath` 加前缀比较）对检查后替换是敞开的，新端点不复制它。

### D4 同名冲突按 `name (1).ext` 自动重命名，服务端裁决

需求方明确不要覆盖、不要跳过。`(n)` 递增在服务端做，因为只有服务端知道竞态下的真实结果（两个并发批次写同一个名字）；回传 `renamed[]` 供前端如实展示。前端不做「先探测再决定」——那既多一轮往返，又会在并发下必然猜错。

### D5 重试只重传失败项；不引入服务端幂等记录

最初的设计是「服务端按 `upload_id` 记录已完成批次、重试回放上次结果」，带 TTL 与清理钩子。**该设计被移除**，理由：

- **客户端已具备判定所需的信息**：响应逐项报告成功/失败/跳过，重试只要重传 `errors[]` 里的项即可，服务端可以完全无状态。
- **那份复杂度是自己造出来的**：为该记录辩护的理由之一是「按文件记会产生 5000 条记录」，但按批次记同样无界（25 条/拖 × 任意次拖），于是不得不追加 TTL、清理点与并发写入语义。为省掉一个客户端数组而引入一套跨请求存储，得不偿失。
- **它换来的好处极窄**：只在「服务端已写盘但响应丢失」这一种情况下避免副本，而该情形下的副本是**可见的**（以 `(n)` 落盘并出现在 `renamed[]` 汇总里），语义上等同用户拖了两次。

契约因此改为：客户端只重传未成功项，服务端不承诺去重，同一文件重复提交按同名冲突处理。

**残余风险（显式接受）**：响应丢失时重传整批，已落盘项会得到 `(n)` 副本。若实测证明该情形常见（而非理论偶发），再另立变更引入服务端幂等记录——那时才有证据支撑那份复杂度，这里刻意不预先建设。

（也考虑过照抄 `/upload` 的 `webdir_<upload_id>` 技巧：靠「重试写进同一个目录」天然幂等、零额外状态。但它要求目标是**暂存目录**，而本变更写的是用户正在浏览的真实目录，无法移植。）

### D6 前端进度必须换成 XHR，且总字节在遍历之后才确定

`fetch()` 没有上传进度事件（`ReadableStream` 请求体在 Chromium 也未就绪），要拿到 `upload.onprogress` 只能用 `XMLHttpRequest`。这一点直接推翻了「照抄 `handleFileSelect`」的做法（`chat/state.js:808` 是 fetch）。

进度分三层且必须一起显示：总字节、项数、百分比。**总字节要等目录遍历完成才能算出**，所以进度分两阶段：遍历阶段只显示「已发现 N 项」，不做百分比；上传阶段才给出百分比。否则百分比会在遍历途中反复回退，比没有进度更糟。

批内字节要按比例换算：`onprogress` 的 `loaded/total` 含 multipart 边界与字段头开销。**这一步经核算是必要的**，不是洁癖：每部分开销约 200–300B，对一个小文件的请求它可能占总量 20% 以上，不换算就是系统性错报。做法是 `scale = 本文件字节 / event.total`、`curLoaded = event.loaded * scale`，使显示字节与落盘总字节同量级（验收 < 1%）。实现与前端用例都钉住了这一点。

**最初的方案是「按批发送」（每批 ≤256MB 且 ≤200 个条目，批内比例换算、批间串行推进），实现时替换为「每个文件一个请求」，并发 3。** 理由是替换后每个目标都严格更好或持平：

- **同一份代码覆盖两个极值**：5000 个小文件与一个 200MB 大文件走的是同一条路径，不需要「批内再分片/单文件独占一批」这类特例分支，也不需要 `batch_max_bytes` 这个只为一类文件存在的上限；
- **失败可单点重试**：批失败要重传整批（或引入批内偏移续传，那是另一套状态机），单文件失败只重传那一个文件，D5 的「只重传未成功项」因此不需要任何额外设计；
- **服务端内存与单文件大小解耦**：一个请求只搬一个文件，峰值是「并发数 × 单文件上限」量级，且请求体由浏览器缓冲而不是页面拼装的 `FormData`（页面侧峰值与文件数无关）；
- **进度是精确的而非换算出来的**：已完成字节来自已结算的文件，进行中的字节来自该文件自己的 `onprogress`，不需要靠「本批总字节 / event.total」去反推一个混合量；
- **多出的是往返次数**：5000 个小文件约 5000 个请求，而不是 25 个。这是这次替换唯一付出代价的地方，且它换来的是上面四条。请求开销本身在网络内网部署下不是瓶颈（每个请求都要过一遍鉴权与租户解析，这正是原方案反对小批的理由，但那个论断针对的是「20 个/批」这种量级，与「1 个/请求」的取舍不同：后者买到的是可重试与内存解耦）。

并发取 3（同时 3 个 XHR）。**峰值内存 ≈ 并发数 × 单文件接受的字节**，这是该常数唯一的取舍依据；内存受限的部署可降到 2，实现时把它作为可调常量并在代码注释里写明这个公式。拖拽本身允许在传输中切换目录：落点在 `drop` 时已解析并固定在 upload 对象里，切换目录只影响结束后的刷新目标。

百分比按**字节**加权，因此当文件大小严重不均时（例如 4999 个 1KB + 1 个 200MB）进度条会长时间贴着 0% 再突然冲完。这是按字节计权的固有表现，不靠伪造百分比去掩盖：界面必须**同时**显示项数（`已传 3120 / 5000 项`），使用户能分辨「在传大文件」与「卡住了」。这也是「三层进度同时显示」的原因，不是冗余。

### D7 单文件 200MB 上限，本轮不做分片

单请求直传 + 无断点续传，200MB 在常见的局域网/内网部署下是可接受的；再往上（GB 级）需要「分片 + 服务端合并 + 校验」，那是另一个变更的工作量，本轮明确放弃并**显式提示**（超限文件在汇总里说明原因，不做静默失败）。

与之配套的服务端改动不可省：现有 `_read_uploaded_file_bytes()` 是 `.read()` 一次性读进内存（`channel/web/fork/runtime.py:607`），**新端点不沿用它**。上传 handler 自己按 `WS_UPLOAD_CHUNK_BYTES`（1MB）分块读取并写盘，写入完成后**校验实际写入字节数**与传输层声明的字节数一致，不符即判该项失败并清掉临时文件（避免把截断的文件当成成功）。写盘先落到同目录下的 `.ws-upload-<rand>.part` 再改名，因此连接中断不会在真实名字上留下半截文件。

（既有 `/upload` 附件通道仍走 `_read_uploaded_file_bytes()`：本变更不改它的契约，也不顺手改它的内存行为——那是另一处调用面的回归风险，不属于本变更的责任域。）

### D8 上限分两层，但服务端只做**单批**的无状态校验

上限收敛为四个可判定项，其中只有**每一项请求内可判**的部分属于**服务端权威校验**：

| 上限 | 判定方 | 性质 |
|---|---|---|
| 单文件大小（200MB） | 客户端 + 服务端 | 服务端权威（无状态，单请求内可判） |
| 单请求条目数（`WS_DELETE_MAX_TARGETS`，删除用） | 服务端 | 服务端权威（无状态） |
| 单次拖拽条目数（5000） | 仅客户端 | 体验护栏，**非**安全边界 |
| 单次拖拽总字节（5GB） | 仅客户端 | 体验护栏，**非**安全边界 |

「每文件一请求」（D6）消掉了「单批条目数」与「单批字节」这两个量：它们在有批的世界里需要服务端复核，在无批的世界里恒等于 1 与单文件大小，于是自然合并进第一行。

最初的方案要求服务端按 `dragId` 跨请求累计单次拖拽的总量。**该设计被移除**，因为它**对攻击者零作用**：`dragId` 由客户端自报，换一个即可绕过；真正想刷量的客户端本来就可以无限次调用端点。这份跨请求状态只约束诚实客户端——而诚实客户端已被客户端检查约束住了。**纯粹的成本，没有收益。**

（原方案的另一条理由「既有知识库限额是 per-request 的，分批正好绕过」成立，但它证明的是「单请求上限要定得合理」，不是「服务端要维护跨请求计数」。真正的磁盘背压属于资源配额的责任域，本变更不重复实现。）

数值：`WS_UPLOAD_MAX_BYTES=200MB`（服务端常量，同时是客户端与规范的上限）、`WS_UPLOAD_CHUNK_BYTES=1MB`（服务端流式写入粒度，不是用户契约）、`WS_DELETE_MAX_TARGETS=2000`（服务端常量）。前端常量：单次拖拽 5000 个条目、单次拖拽 5GB、遍历深度 32（深度是遍历护栏、不是用户契约，因此不进入规范要求）。**全部取固定常量，不登记 `config-template.json`**：上限值在实现前定档，做成配置项只会多一处需要读取与验证的入口，而本变更没有「不同部署需要不同上限」的证据。

`WS_DELETE_MAX_TARGETS` 取 2000 而不是与前端 5000 对齐，是因为两者的量纲不同：面板一次只能删除**已渲染的行**，而列举本身以 `MAX_ENTRIES=500` 封顶（`agent/workspace/service.py`），所以 2000 在真实交互里永远够用，它唯一的职责是给「一个请求体能要求多少工作」封一个上界。删除只是重命名，代价与字节无关，因此不需要字节上限。

删除上限的取向**与上传不同**：删除不需要「请求次数少」这个目标（一次删除就是一次请求），因此没有理由为了减少请求而放大单请求条目数。

### D9 面板是落点，聊天区拖拽不受影响；两者靠阻断冒泡与类型判定分开

面板落点绑在 `#ws-body-files`（工具栏 + 面包屑 + 列表的容器），`dragover` / `drop` 必须 `preventDefault()` **并 `stopPropagation()`**，否则 `#view-chat` 的处理会把同一批文件当附件上传。**落点不可写时必须在 `dragenter`/`dragover` 阶段就以不同的视觉态与提示语表明会被拒**，而不是等 `drop` 之后再报错——规范里这条是「拖入前就可见」的由来。

反向的区分沿用既有约定：从面板往外拖是 `application/x-cow-workspace-file`（`initWorkspaceDropTarget` 已有），只有 `dataTransfer.types` 含 `Files` 才走上上传。搜索态下 `wsCurrentDir` 仍是落点（搜索结果只是视图），这一点要在 UI 上说清楚（提示语显示目标目录名）。

### D10 不改「租户与 Agent 工作区文件服务按作用域隔离」的正文

那条要求是一整段超长正文，且其端点枚举（`GET .../tree|search|resolve|meta|read` 与 `POST .../write`）并未包含新端点。把新端点塞进枚举需要整段复述，风险是复述过程中改变既有语义（`check_change_deltas.py` 会逐场景比对，但语义漂移它看不出来）。本次改为四条 ADDED 要求自足表述，并在新增要求的正文里**引用**既有规则，而不是复制它——新增要求自身也遵守这一点，不复述 `user/<user_id>` 那四类情形的细则。

### D11 目录遍历的工程约束（不满足就会静默丢文件）

- `dataTransfer.items` 在 `drop` 回调返回后失效，但 `webkitGetAsEntry()` 返回的 `FileSystemEntry` 是持久的：**必须在 `drop` 回调里同步把所有 item 转成 entry 存起来**，之后才异步遍历。
- `FileSystemDirectoryReader.readEntries()` **每次至多返回 100 条**，必须循环读到返回空数组为止；漏掉这一步的表现是「大目录只上传了前 100 个」，且没有任何报错。
- 遍历并发限 8–16：Chromium 同时挂起的文件系统操作有上限，超了会以错误回调结束。
- 空目录不保留：`File System API` 能枚举到空目录，但保留它需要额外的清单字段与服务端建目录分支，而这些目录不含任何内容。列表里出现一个空目录行与不出现它，对用户没有差别——因此不计入契约。

### D12 删除是软删除，回收站放在本人目录内且自我隐藏

删除实现为**同文件系统内的原子重命名**到 `<workspace>/user/<本人 user_id>/.trash/<批次 id>/`，而不是在原地 `unlink`。理由：

- 需求明确要求「可恢复」，硬删除无法满足；
- 重命名是**原子**的，因此不存在「删到一半」的中间态，目录递归删除也天然满足这一条（整棵目录一次重命名，不需要逐文件删）；
- 不需要「先复制再删除」的降级路径：回收站与来源在同一个工作区、同一个文件系统。跨设备重命名（`EXDEV`）在本布局下不应发生；真发生了就以该项失败报告，绝不复制成中间态。

**回收站位置选在本人 `user/<uid>/.trash/` 而不是工作区外的状态目录**，因为它自动继承了同一套归属规则（他人看不到、本人看得到），不需要为回收站再造一套授权。代价是它**必然落在面板的可浏览范围内**，因此必须显式排除：

- `.trash` SHALL 不出现在列举与搜索中；
- `.trash` MUST NOT 作为上传落点或删除目标；
- `.trash` MUST NOT 是可写范围根，删范围根的动作一律拒绝。

**这里有个陷阱：`.trash` 的点前缀看似已经够用，其实不够。** `WorkspaceService.list_dir` 在 `show_hidden=False` 时跳过 `.` 开头的条目（`agent/workspace/service.py:140`），`search` 也跳过（`:207-212`）——但 `show_hidden` 是**客户端可达的查询参数**（`channel/web/fork/handlers/workspace.py:132,149` 直接透传 `params.show_hidden == '1'`），所以「命名为 `.trash` 就看不见」只在默认调用下成立。因此排除必须是**与点前缀无关的显式准入规则**，加在与既有的他人 `user/<id>` 过滤**同一个 seam** 上：`list_dir` 的 `allow_entry`（`service.py:119-129`，且它在条目上限之前生效）与 `search` 的 `allow_dir`（`:195-198`）。这样 `show_hidden=1` 也带不出回收站。

（`meta()` 不必处理：它只返回 `root`/`exists`/`server_time`，根本不枚举条目，`service.py:286-291`。原先把「元信息」列进需要处理的面是多余的。）

**删除的两类破坏性操作在 `safe_fs` 里没有原语可复用，这是本变更必须自己补的一块。** `common/safe_fs.py` 提供 `resolve_within`、`exists`/`is_file`/`is_dir`/`is_symlink`/`stat`、`list_names`、`mkdir`、`write_bytes_atomic`、`write_text_atomic`、`unlink`、`contains`——**没有 rename/move，也没有递归删除**（`unlink` 只能删单个文件）。所以 D3 里「复用 `safe_fs` 比手写更少代码」这个判断对**上传**成立，对**删除不成立**：删除需要新增 `rename`（源、目标两侧的父目录链都要走同一套逐级 `O_NOFOLLOW`）与 `remove_tree`（递归时同样不得跟随符号链接）两个原语。它们应当落在 `safe_fs`（加固过的链式打开器在那里）并由 `WorkspaceService` 调用，MUST NOT 在 `service.py` 里另写一份路径校验——注意 `service.py` 现有的 `_replace_atomically`（`:463`）就是一处自己实现的写路径，不要跟着它再加一个自己实现的移动。

位置选在本人目录里还带出一条**必须显式保护**的路径：私有 Agent 的可写范围是整个工作区，而不可删集合的第一类只作用于工作区根的第一层，因此 `user/<本人 user_id>`（第二层）默认是可删的——删掉它会把**回收站本身一并移走**，同一次删除立刻变得不可恢复。所以本人 `user/<uid>` 目录与其父容器 `user/` 一并列入不可删集合（D13 的第二类）。这类「不可删集合的粒度选项会互相拆台」的坑，只有把回收站放进可删范围里才会出现，是 D12 这个位置选择的直接后果，不是额外需求。

批次结构刻意做成「一次删除请求 = 一个批次目录」而不是「一个条目一个目录」：删 5000 个文件若按条目建目录，就是 5000 个目录加 5000 份元信息，纯粹是浪费；按批次存则一份元信息记录整批，恢复仍可逐条进行。批次内条目**保留原相对路径**（放在批次目录的 `files/` 下），因此恢复不需要任何额外映射，也不会因为两个同名文件落在同一批次而互相覆盖。

批次粒度带来一个**必须一并设计的后果**：恢复与彻底删除是**逐条**进行的，而批次目录是整批的。因此元信息必须记录**每条的状态**（在回收站 / 已恢复 / 已彻底删除），否则「恢复某一条之后，回收站列表里不再保留该项」无法实现，同一条也可能被恢复两次。另外，一个批次里所有条目都不再处于「已恢复/已彻底删除之外」的状态时，批次目录应当被移除——否则用户逐条清空一枚批次后会留下空壳目录，虽然保留期限的清理点最终会收走它，但在此之前它会让「回收站里有 N 项」与目录数对不上。实现上这一条很便宜：把状态写回元信息，并在写完后按元信息判断是否整批清空即可。

浏览、恢复与彻底删除三条路径都**只解析到调用者本人的回收站根**：批次标识来自请求体，但它只能用于在本人回收站内**选中**条目，MUST NOT 参与路径拼接，因此猜一个批次标识既够不到他人的回收站，也够不到回收站之外的目录。这是「把回收站放进本人目录」这个位置选择的第二个好处——越权在构造上不可达，不需要额外写一条所有权判定。

### D13 不可删集合以工作区根的**第一层**为单位，不递归

私有 Agent 的工作区根第一层里混着 Agent 的运行内部（`AGENT.md`、`USER.md`、`RULE.md`、`BOOTSTRAP.md`、`MEMORY.md`、`knowledge/`、`memory/`、`scheduler/`、`skills/`、`subagents/`、`system/`、`tmp/`、`websites/`、`plans/`）。把它们删掉会让 Agent 直接不可用，而且软件层面无法区分「用户想清理自己的文件」与「用户把自己 Agent 的记忆删了」。

判定刻意**只看工作区根的第一层条目名**，不递归：用户自己目录里的 `memory/`、`knowledge/` 是**用户自己的内容**，删它没有任何风险，把它也保护起来反而是把简单规则复杂化（要区分「谁的 memory」就得引入路径来源分析）。这个取舍同时让规则可一句话说清、可稳定测试。

除运行内部，不可删集合还包含三类，各自理由不同、不能互相推导：

- **`user/` 容器与调用者本人的 `user/<本人 user_id>` 目录本身**——理由不是「内部不可动」，而是 D12 的回收站就落在 `user/<uid>/.trash`：第一层粒度的清单保护了 `user/`，但保护不了第二层的 `user/<uid>`，而删掉它会把回收站一起移走、让同一次删除当场失去可恢复性。这一条是 D12 位置选择的直接后果，不是额外需求。
- **回收站目录本身**——它不能被自己当作目标。
- **可写范围根自身**——不允许把范围根整体删掉。

不可删集合**只约束删除，不约束上传**——这是两边的性质差异，不是疏漏：上传是**追加**，往 `memory/` 里多放一个文件不会毁掉 Agent；删除是**抹除**，删掉 `memory/` 会让 Agent 失去记忆。把上传也一并限制，除了让用户不能把资料放进自己的 Agent 目录之外没有任何收益。

实现上沿用仓库已有的写法（`agent/knowledge/service.py` 的 `PROTECTED_FILES` + `_ensure_not_protected` 就是这个形态），集合是模块级常量，不做成配置项。

共享 Agent 只受后三类影响：它的可写范围已经是 `user/<uid>` 之内，够不到工作区根，因此运行内部那一类天然不适用。

### D14 恢复要重校验目的地，因为可见性会在删除之后改变

回收站里的条目记录的是**删除当时**的原相对路径。恢复到该路径前必须重新判定：

- 目的地是否仍在该 Agent 当时的可写范围内；
- 目的地是否已经变成不可删集合中的条目（私有 Agent 的工作区根条目）。

会变的原因是 Agent 的可见性可以被改（私有 ↔ 租户共享），一次删除之后工作区可能已经从「整根可写」收窄成「只有 `user/<uid>` 可写」，此时把条目恢复回工作区根就等于**绕过收窄**。因此恢复不是「原样搬回」，而是一次**受同一套闸门约束的写操作**；不合规就拒绝该项并说明原因。

原位置被占用时以可用的新名落盘（复用 D4 的 `(n)` 递增）并如实报告实际路径：本次没有 `rename`/`move`，如果选择「拒绝恢复」而不是自动改名，用户就会卡在一个无法自行解决的状态里。改名虽然改变了落点，但无损且可见，是这里唯一可行的选择。

### D15 样式落在 `console.css`，不是 `workspace.css`

`chat.html` 只链接了 `assets/css/console.css`；`static/css/workspace.css` 虽然内容完整（含 `.chat-main.ws-drop-active::after`），但**没有任何页面引用它**，是死文件。改错地方的直接后果是「样式不生效且没有报错」。

（同类的死代码还有 `channel/web/api/workspace.py`：它是**上游**的实现，只被 `build_app()` 用，而 fork 的活体应用是 `build_web_app()`；fork 的 handler 一律从 `channel/web/fork/handlers/` 取。改动不要落进 `api/`。）

## Risks / Trade-offs

- **代理阈值**：`client_max_body_size` 的默认值（nginx 为 1MB）会直接以 413 拒绝。**每文件一请求（D6）把这条风险缩到「单文件」量级**：一个 200MB 文件被 1MB 的阈值拒绝，与一个 256MB 批被拒绝是同一个现象，但现在不会因为「批里有小文件」而整体全废——其余文件各自的请求不受影响。部署侧仍须把阈值放到 ≥ 单文件上限 + 余量，仓库内没有随代码下发的代理配置（已确认），因此这是必须写进部署验收的前置条件。前端把 413 直接读作「超过单文件上限」（响应没有 `code` 可读，因为请求没到应用层）。
- **临时盘**：web.py 的 multipart 解析会把带 `filename` 的部分落到系统临时文件，因此**单请求的临时占用就是一个文件的大小**（≤200MB），而不是一个批的总和。风险在容器化部署下最明显（临时盘可能是内存盘），但量级已由「批」降到「单文件」。
- **响应丢失会产生副本**（D5 的残余）：重传时已落盘项得到 `(n)` 副本，副本是可见的、不是静默的。用户如今**可以删除**它，因此这条残余的后果比之前轻。
- **回收站会占磁盘**：软删除不释放空间，这是「可恢复」的直接代价。缓解有两条腿——用户可在回收站里彻底删除，加上保留期限的清理点（实现常量）。刻意**不做**成配置项：这是运维参数而不是产品参数，做成配置只会多一处需要登记与验证的读入口。若线上真的需要按租户调，再另立变更。
- **可见性翻转会让部分回收站条目变成不可恢复**：D14 要求恢复前重校验目的地，因此当 Agent 从「私有」变为「共享」时，那些原路径在工作区根（现已落在可写范围之外）的条目**恢复会被拒绝**。它们不会自动消失，但保留期限到期后会被清理点收走——也就是说，这条路径的终点是**静默的最终数据丢失**。当前设计选择「拒绝并说明原因」而不是「自动改放到新的范围根之下」，因为后者会让文件出现在用户没指定的位置。后果是用户可以看得到、删得掉、但恢复不了；若产品认为这不可接受，对策是给它加一个显式的「恢复到 <当前可写根>/回收站恢复/<原相对路径>」的降级去向（见 Open Question 2）。
- **回收站的清理不能误删**：清理点必须在 `.trash` 之内枚举，且 MUST NOT 跟随 `.trash` 内可能存在的符号链接（回收站里的内容来自用户目录，可能含链接）。清理只按批次目录的修改时间判定，不做递归内容分析。
- **删除是破坏性操作**：即使有回收站，一次 `drop` 式的目录删除误触代价很高。对策是二次确认（把**条目数与体积**都写进确认文案，而不是只说「确定删除吗」）+ 软删除兜底 + 恢复入口可见。
- **进度失真**：multipart 开销已用比例换算修正，但换算依赖「该文件字节」准确——若源文件在遍历与发送之间被改动，偏差会出现。验收标准定为 < 1%，并说明这是「同一时刻读取的快照」而非严格一致。
- **内存峰值**：每个在途请求承载一个文件，峰值 ≈ 并发数 × 单文件上限（3 × 200MB 量级），且请求体由浏览器缓冲而非页面拼装的 `FormData`；页面侧峰值与文件数无关。
- **i18n 快照冲突**：`tests/fixtures/console_i18n_snapshot.json` 是逐键冻结快照，多个并行变更同时追加键时会互相干扰（仓库历史已多次出现）。本次按「只增不改、逐键复核增量后再重写」处理：本次新增 51 个键 × 3 语言，快照由合并表生成并断言「任何既有键的既有值都不变」后才写回。
- **与本变更无关但会误导验收的一点**：单文件 200MB 时若代理或 web.py 的 body 限制更小，失败会表现为「前端进度到某个百分比后卡住」或该文件单独报 413，排查时先看代理日志，不要先怀疑前端。

## Migration Plan

无数据迁移，也不改变既有文件的归属或布局：新端点只写调用者本来就能写的位置，已有的 `uploads/` 目录结构保持不变。

上线后**已存在的**代理与技能脚本仍按原方式读写；本变更只增加面板的入口，不改变执行层边界。

回滚：

- 撤下前端落点、分批上传与删除入口、撤下五条路由登记与 `route-baseline.txt` 的新行，即可恢复原状。
- **回收站需要显式处置**：已软删除的条目仍留在 `user/<uid>/.trash/` 下。回滚前应先提示用户恢复或彻底删除；回滚后这些目录会变成面板里的一个可见普通目录（因为排除逻辑随之撤下），这正是需要人工确认的原因，不是可以忽略的残留。
- 服务端无新增持久状态（除回收站本身，见上），没有需要清理的数据库行。

## Open Questions

1. ~~上限数值是否要产品定档为固定值（而非配置项）？~~ **已定档（实现前）：全部取固定常量**，数值见 D8。理由是该变更没有「不同部署需要不同上限」的证据，而配置项会多出读取入口与验证面。
2. 可见性翻转后不可恢复的回收站条目要不要给一个降级去向（例如恢复到当前可写根下的专属恢复目录），而不是只拒绝？拒绝会让这些条目最终被清理点收走（见 Risks）。**当前实现选择「拒绝并说明原因」**，因此这是一条仍未关闭的产品问题，不作为本次交付的前置。
3. 回收站的保留期限取多久？**已定档：30 天**（`TRASH_RETENTION_SECONDS`，实现常量，随 `GET /api/workspace/trash` 以 `retention_days` 返回给界面显示）。
4. 是否需要「拖到某个子文件夹行上即上传到该子文件夹」的增强？本次落点是当前浏览目录（已与需求确认），行级落点是可选的后续增强。
5. 是否需要一个「上传/删除中禁止切换目录」的约束？**当前实现允许切换**（目标在开始时已解析并固定），切换后刷新的是新目录、结果汇总仍在面板上显示；前端用例覆盖了「切换后旧落点结果不落进新目录」。
6. 删除的二次确认要不要提供「本会话内不再询问」？对高频整理文件的用户是有意义的减负，但它也让误删更容易发生；本次规范只要求二次确认，不加记忆选项。
7. 是否需要补一个可点击（键盘可达）的上传入口？拖拽对键盘用户不可达，本设计把删除做成工具栏按钮（本身可键盘触发），但**上传**仍只有拖拽一条路；若需对等入口应作为独立要求补入。
