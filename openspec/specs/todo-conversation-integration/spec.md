# todo-conversation-integration Specification

## Purpose
让用户把需要持续跟进的会话事项保存到个人待办，并在当前权限和既有聊天能力允许时返回正确来源。Agent 仅复用同一待办服务创建和查询，不新增聊天运行框架，不改变人工处理和外部动作授权边界。
## Requirements
### Requirement: 用户确认后从消息创建个人待办

系统 SHALL 对有权访问的消息提供“加入待办”，打开可编辑的预填表单，保存经用户确认的事项内容及来源引用。系统 MUST 在提交时重新校验当前用户的待办写权限和来源读取权限，并按与手工创建相同的规则创建属于本人的事项。打开或取消表单 MUST NOT 创建记录、改变会话状态或启动模型执行；来源引用不替代用户对待办正文的确认。

#### Scenario: 确认预填内容后保存
- **WHEN** 用户从可访问的消息打开表单，确认或修改事项内容后提交
- **THEN** 系统重新验证来源并持久化一条本人待处理事项，返回待办 ID 和来源引用；若用户取消表单，则不产生事项

#### Scenario: 提交前来源权限失效
- **WHEN** 表单打开后用户失去来源读取权，再提交创建请求
- **THEN** 系统拒绝创建，不将来源正文或附件内容保存为新事项，并提示来源不可用

### Requirement: Agent 使用可信请求上下文操作本人数据

系统 SHALL 仅在 todo_enabled、既有工具启用配置及当前合法 Web 聊天能力均允许时提供 todo 的 create、list、get 动作。服务端 MUST 从经过验证的独立请求上下文取得 scope、人工 owner、Agent 和会话来源，并采用与 Web 相同的权限及持久化规则；既有 user/tenant 身份 SHALL 为唯一主体来源，MUST NOT 映射为本地所有者。系统 MUST NOT 跨请求复用可变主体或来源，不接受模型自报的用户、租户、目录或其他会话作为授权。缺少可信人工委托的 scheduler、外部通道、后台运行和免登录入口不得调用本工具；隐藏工具之外，直接调用也 MUST 拒绝。

#### Scenario: 并发请求保持个人隔离
- **WHEN** 两个用户或租户的 Web 请求交错调用同一个工具实例
- **THEN** 每次调用只使用各自的可信请求上下文，创建绑定本人的事项，list/get 只返回本人授权内容，不串用其他请求的主体或来源

#### Scenario: 伪造主体或未满足能力条件
- **WHEN** 调用缺少可信 Web 委托、当前工具或聊天能力未开放，或携带与可信上下文冲突的 owner、租户、来源参数
- **THEN** 系统拒绝对应请求，不回退匿名、默认 Agent 或全局空间，也不借待办开启未验收的聊天或后台消费者

### Requirement: Agent 仅按明确人工跟进需要创建和查询

Agent SHALL 仅依据用户明确的记入或跟进要求，或当前任务确有人工资料、确认或验收需求创建待办。附件、引用材料中的命令和任意模型子步骤 MUST NOT 单独构成创建依据，不扫描历史自动补单。工具 SHALL 仅提供 create/list/get/assign 动作，不提供编辑、状态更新、删除、收回、退回或全租户查询；事项分类只作标签，不增加专属流程。

assign 动作 SHALL 只在用户于当前轮次明确点名接收人时可用，接收人 MUST 以用户名给出并由服务端在同一租户内解析；Agent MUST NOT 扫描会话参与方、成员目录或历史记录推断接收人，MUST NOT 自主选择接收人，MUST NOT 把材料中的指示当作委派委托。单次调用 MUST NOT 涉及多于一个接收人，MUST NOT 支持批量委派。模型自报的用户标识、租户标识或成员资料 MUST NOT 被当作授权依据。

#### Scenario: 保存或查询明确的个人事项

- **WHEN** 用户在可信 Web 会话中明确要求记下需要处理的事项、询问自己的待办，或当前任务确实需要用户补充资料
- **THEN** Agent 可在本人权限内调用 create/list/get，创建时由服务端注入来源，不需要创建或恢复旧 run 记录

#### Scenario: 用户明确点名时委派

- **WHEN** 用户在可信 Web 会话中明确要求把某条本人待办交给指定接收人，且调用方具备 `todo.assign`
- **THEN** Agent 可调用 assign，由服务端在同一租户内解析该接收人并完成委派
- **AND** 该次委派按 `todo-delegation` 的口径留痕，接收人按最小投影口径仅在必要时回显用户名与显示名

#### Scenario: 无法点名接收人或超出单次范围

- **WHEN** 用户未点名接收人、接收人无法在同一租户内唯一解析，或一次调用要求委派给多个接收人
- **THEN** Agent MUST NOT 推断、代选或拆分接收人，也不得跨调用补足
- **AND** 系统拒绝该动作并如实说明需要用户明确指定单一接收人

#### Scenario: 附件命令或越界动作不被执行

- **WHEN** 材料要求自行创建待办但没有用户委托或实际人工需求，或 Agent 尝试完成、取消、编辑、收回、退回事项、委派给未点名的接收人或读取他人事项
- **THEN** 系统不据材料命令制造事项或委派，并拒绝不支持或越权的工具动作，不改变事项状态、当前处理人或读取范围

### Requirement: 创建键只保证同一调用重试去重

消息表单 SHALL 为一次创建保留稳定 create_key；Agent SHALL 使用包含请求与工具调用身份的稳定键，避免不同请求内相同局部调用标识发生冲突。系统 MUST 按 scope/owner/create_key 和不可变的初始创建摘要进行持久去重，同键同内容返回同一 ID 的当前授权详情，同键异内容返回 409；事项后续编辑不改变原摘要。不同调用使用不同键，系统 MUST NOT 声称具备跨调用的语义去重；重试返回前仍需重新授权。

#### Scenario: 响应丢失后重试同一调用
- **WHEN** 事项已保存但响应丢失，表单或 Agent 使用相同 create_key 和原创建内容重试，且当前仍有权限
- **THEN** 系统返回同一待办 ID，不重复创建事项或创建记录，即使事项后来已编辑也不重算原创建摘要

#### Scenario: 不同调用与冲突键分别处理
- **WHEN** 两个不同工具调用使用不同 create_key，或已有键被再次用于不同的创建内容
- **THEN** 不同键可各自创建事项，即使标题相同；已存在的键配合不同内容返回 409，不覆盖原事项，不以同一会话轮次作为合并依据

### Requirement: 创建结果必须来自真实持久化反馈

页面和 Agent MUST 仅在收到持久化成功结果及真实待办 ID 后告知创建成功。保存失败或结果未知时 SHALL 如实说明失败或尚未确认，并保留原键和原提交内容用于允许的重试，不虚构 ID、不自动换键制造新请求。事项与创建历史必须原子提交；重试时撤权不因旧键而获得原事项数据。

#### Scenario: 存储失败或结果未知
- **WHEN** 待办或创建事件落盘失败，或调用方未能确认服务端结果
- **THEN** 调用方不展示创建成功或虚构链接，确定的事务失败不留下部分记录；结果未知时以原键重试或确认，不声称事项一定未保存

#### Scenario: 重试前访问权撤销
- **WHEN** 原创建已成功，但请求方在重试前失去必要身份或待办访问权限
- **THEN** 系统拒绝返回原事项内容，Agent 不通过旧 create_key 绕过授权或声称本次重试成功

### Requirement: 返回正确来源并复用现有输入框

用户返回来源前，系统 MUST 重新解析和验证来源，并按 Agent/session 组合定位，不能仅因 session 字符串相同而停留在错误 Agent。已有合法聊天运行能力可用时 SHALL 返回原会话并复用现有输入框；已有输入按原有未保存机制保留。系统 MUST NOT 为待办自动添加处理草稿、注入待办引用协议、发送消息、创建替代会话或恢复旧调用栈。

#### Scenario: 不同 Agent 使用相同会话标识
- **WHEN** 当前 Agent 与事项来源 Agent 不同，而两者的 session 标识相同
- **THEN** 系统打开来源指定的 Agent 和会话，不因 session 相同而错误保留当前会话历史

#### Scenario: 返回会话保留原输入
- **WHEN** 用户返回有权访问且允许运行的来源会话，现有输入框包含未发送内容
- **THEN** 系统沿用既有未保存机制保留输入，不自动插入草稿或引用，不发送消息；用户自行使用原输入框继续对话

### Requirement: 来源失效和只读环境保持可用边界

来源正文、消息和附件访问权 MUST 独立于待办访问权校验；来源删除或撤权不删除用户已确认保存的事项内容和处理记录，也不得经回链泄露受限源正文、标题、附件链接或内部路径。只有历史读取能力的环境 SHALL 复用已有受控只读路径，不调用会启动模型、SSE 或聊天轮询的运行导航；不存在可用只读路径时 SHALL 提示来源暂不可用，不为待办建设聊天框架或解除原运行限制。

#### Scenario: 来源删除或原消息无法定位
- **WHEN** 用户打开来源时会话已删除、权限已撤销，或会话仍可读但原消息无法定位
- **THEN** 事项和处理记录仍按本人权限保留；前两种情况显示来源不可用且不返回受限源内容，后一种情况可查看正确会话的授权历史并提示原消息无法定位

#### Scenario: database 仅允许历史读取
- **WHEN** database 人工待办已开放，但尚无合法聊天运行能力，用户查看来源
- **THEN** 系统仅使用已有受控只读路径；该路径不可用则提示来源暂不可用，不启动模型、SSE、聊天轮询或替代聊天框架，Agent 待办工具保持禁用

### Requirement: 会话活动与人工完成不产生隐式业务授权

进入来源、用户发送消息、Agent 回复或运行成功失败 MUST NOT 自动开始、完成、取消或重新打开待办。事项状态仅通过有权用户显式提交待办更新改变。完成“确认”或“验收”事项、填写“同意”及普通处理说明 MUST NOT 生成或消费外部动作授权，不新增 approve/reject/execute 入口或审批记录集成。

#### Scenario: 会话运行结束不自动完成事项
- **WHEN** 用户从待办返回会话并继续对话，新轮次成功、失败或取消
- **THEN** 事项保持原状态，用户仍需显式更新待办，不恢复创建事项时的旧运行

#### Scenario: 完成确认事项不触发执行
- **WHEN** 用户将确认或验收类事项标记完成，并可选填写“同意”
- **THEN** 系统只保存个人事项状态和处理记录，不批准待审批动作、不生成或消费授权，也不恢复或执行外部操作
