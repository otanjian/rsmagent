# web-console-module-seams Specification

## Purpose
规定 RongAI 控制台 Web 后端层的模块布局与接缝契约：fork 定制逻辑的归属模块、上游模块不得含 fork 专有分支、路由权威清单跨模块解析，以及上述约束的可执行校验，使上游模块重构（如 `api/`+`core/` 拆分）不再与 fork 定制正面相撞。

前端模块化布局与 fork 前端定制的交付方式由独立 change `adopt-upstream-web-frontend-split` 的 `web-console-frontend-modules` capability 承载；本 capability 只约束后端布局与接缝，故本 change 的交付不以该前端迁移完成为前置。
## Requirements
### Requirement: Web 后端模块布局与上游保持一致

控制台 Web 后端 SHALL 采用与上游同构的模块布局：按视图划分的 handler 模块、承载共享管道的公共模块，以及只负责 URL 表与 `build_app()` 的入口模块。

fork 侧的 handler 实现 SHALL 位于 fork 命名空间下、按上游 `api/` 的视图划分组织的模块中，MUST NOT 写入上游视图模块，MUST NOT 与上游模块路径重合。上游视图模块 SHALL 保持上游形态、可被上游单独演进，且 MUST NOT 被 fork 改写。

当某路由的实现由 fork 承载时，系统 SHALL 明确该路由的活跃实现位于 fork 模块；上游同名模块中的实现对该路由不生效，其后续改进 SHALL 按「上游 handler 变更可检测且需人工移植」的要求处理。

入口模块 MUST NOT 再次承载业务 handler 实现：其职责限定为登记 URL 表、暴露应用构建入口，以及为渠道工厂与启动流程转出既有公开符号。上游发布形态在缺少 fork 模块时 SHALL 保持上游布局与语义不变。

该布局的收益以可观察结果度量：上游再次重构同一批视图模块时，冲突 SHALL 限于 fork 自有模块与上游模块的登记边界，MUST NOT 再次出现 fork 业务实现与上游实现同处一个巨型文件的整文件冲突。

#### Scenario: 按视图解析 handler 归属

- **WHEN** 审查控制台任一业务视图（对话、会话、文件、知识库、调度、技能、模型、配置、工作区、渠道、智能体）的请求处理入口
- **THEN** 其 handler 实现位于与该视图对应的模块中，入口模块内不存在该 handler 的实现体

#### Scenario: fork 实现不与上游路径重合

- **WHEN** 审查 fork 承载的任一 handler 实现的模块路径
- **THEN** 该路径位于 fork 命名空间且不与上游 `api/` 或 `core/` 的路径重合，上游同名模块保持上游内容

#### Scenario: 入口模块仅保留 URL 表与构建入口

- **WHEN** 审查入口模块内容
- **THEN** 其中只包含 URL 表、应用构建入口与必要的公开符号转出，不包含业务 handler 实现与授权判定实现

#### Scenario: 缺少 fork 模块时保持上游形态

- **WHEN** 以独立上游装配运行且未加载任何 fork 模块
- **THEN** Web 后端起服务并保持上游路由与语义，不引用 fork 专有模块，也不因缺失 fork 模块而失败

#### Scenario: forked 路由的活跃实现唯一

- **WHEN** 某路由在上游模块与 fork 模块各存在一份实现
- **THEN** 路由权威清单登记的组合使该路由只解析到 fork 实现，不出现两条实现同时可达或依据注册顺序产生歧义

### Requirement: 上游模块不含 fork 专有分支

上游来源的 Web 模块（视图 handler 模块与共享管道模块）MUST NOT 包含 fork 专有分支、fork 专有路由字面量、fork 专有授权判定或 fork 产品定制条件。fork 所需行为 SHALL 经接缝提供：扩展注册、可选参数注入、上下文查找或授权目标解析。

反向亦 SHALL 成立：fork 模块的登记块 MUST NOT 要求改写上游模块才能生效，上游对同一文件的新增也不得被 fork 登记块覆盖。双方在同一视图各自新增符号时，合并结果 SHALL 同时保留两者。

#### Scenario: 上游视图模块零 fork 分支

- **WHEN** 审查任一上游来源的视图 handler 模块与共享管道模块
- **THEN** 其中不出现 fork 专有路由、fork 专有授权判定分支或 fork 品牌/产品条件，fork 行为由 fork 模块提供

#### Scenario: 双方在同一视图各自新增

- **WHEN** fork 在某视图模块之外新增一条 fork 路由与授权判定，同时上游在同一视图新增一个上游 handler 或改变其行为
- **THEN** 合并后 fork 路由与上游行为同时存在、互不覆盖，且上游新增不要求改写 fork 登记块

#### Scenario: 以整文件覆盖代替接缝被拒绝

- **WHEN** 一次合并以整文件取一侧的方式处置含双方业务逻辑的 Web 模块
- **THEN** 该处置被结构校验判定为不通过，不得以「无文本冲突」为由接受

### Requirement: 路由权威清单跨拆分模块解析且覆盖不变量保持

路由权威清单 SHALL 继续作为路由存在性与授权策略的唯一事实源，并 SHALL 支持从拆分后的模块布局解析 handler 名称，MUST NOT 依赖「全部 handler 与授权 helper 同处一个模块的全局命名空间」。清单条目 SHALL 继续按来源（上游 / fork）登记，使 fork 新增路由的合并不要求编辑上游模块的路由字面量。

既有三腿覆盖不变量 SHALL 保持并继续以 handler 实现为第三腿（内省实际实现的 HTTP 方法），任一不一致即失败。上游拆分引入新视图模块或调整 handler 归属时，该不变量 SHALL 在合并后立即暴露未登记或错位条目。

#### Scenario: handler 迁移后清单仍解析成功

- **WHEN** 某 handler 由入口模块迁入其视图模块后构建应用
- **THEN** 权威清单仍能解析该 handler 并派生 URL 表与策略表，路由可达且策略生效

#### Scenario: 拆分导致漏登记即失败

- **WHEN** 上游拆分引入某视图模块的新 handler，而权威清单未同步登记
- **THEN** 覆盖不变量校验失败并指出该路由与未登记方法，构建不得视为通过

#### Scenario: fork 路由无需编辑上游模块

- **WHEN** fork 经扩展注册新增一条业务路由
- **THEN** 该路由出现在 URL 表与策略表中，且上游视图模块与入口模块的路由字面量未发生 fork 专有编辑

### Requirement: 上游 handler 变更可检测且需人工移植

当某路由的活跃实现由 fork 承载时，系统 SHALL 记录该实现与上游对应实现的**来源对应关系**（上游来源模块与固定上游提交），并 SHALL 提供可执行校验：上游对该来源实现发生改动时校验失败，并指出需人工评估移植的路径与提交。

该校验 MUST NOT 以「文件内容相同」为唯一判据（fork 实现本就有意不同），SHALL 以固定上游提交的内容指纹与 fork 记录的来源指纹比对为准。校验 SHALL 可独立运行，使上游改进或安全修复不会静默丢失。

移植义务 SHALL 明确：上游对已由 fork 承载的 handler 的功能改进与安全修复，须经人工评估后移植，不得因校验未覆盖而默认视为无需处理。

#### Scenario: 上游修改了已由 fork 承载的 handler

- **WHEN** 上游改动了某个已由 fork 平行承载的 handler 的上游来源实现
- **THEN** 校验失败并列出该 handler、上游来源模块与相关上游提交，提示需人工评估移植

#### Scenario: 上游未改动已登记的来源

- **WHEN** 上游在两次校验之间未改动任何已登记的来源实现
- **THEN** 校验通过，不产生噪音告警

#### Scenario: 上游新增 handler 未被登记

- **WHEN** 上游在已登记来源模块中新增了一个 handler 或路由
- **THEN** 校验失败并指出该新增项尚未纳入来源对应关系，避免其改进被静默忽略

#### Scenario: 移植后更新指纹

- **WHEN** 完成一次上游改进的人工移植
- **THEN** 来源指纹更新为新的上游提交，后续校验以新基线比对，该次改动不再重复告警

### Requirement: 布局与接缝约束可执行校验

系统 SHALL 提供可执行校验，以代码事实而非文档声明判定上述约束，至少覆盖：上游来源模块不含 fork 专有分支标记；不存在仅存活于入口模块的业务 handler 或授权判定。校验 SHALL 可独立运行并在违反时失败，以便在 CI 与合并上游后立即发现回退。

前端侧的对应校验（fork 前端定制不存在于上游视图模块内）不在本 capability 范围内，须在后端布局校验之外**独立成立**，使本 change 不因前端迁移未完成而无法通过校验。

校验 SHALL NOT 以「文件内出现 fork 关键字」作为唯一判据，以免误伤上游自身的多租户语义命名；判据 SHALL 以 fork 专有符号、注册块与模块归属为基础。

#### Scenario: 回写 fork 分支到上游模块触发失败

- **WHEN** 一次后续变更把 fork 专有授权判定或 fork 路由重新写回上游视图模块
- **THEN** 校验失败并指出文件与违规符号，构建不得视为通过

#### Scenario: handler 或授权实现只留在入口模块触发失败

- **WHEN** 新的业务 handler 或授权判定仅在入口模块内实现，未归入其视图模块或 fork 模块
- **THEN** 校验失败并指出该符号，不得以入口模块可解析为由通过

#### Scenario: 校验在合并上游后运行

- **WHEN** 一次上游合并改变了 Web 模块布局或新增视图模块
- **THEN** 校验立即运行并在布局或归属不符时失败，不等待人工复核才发现
